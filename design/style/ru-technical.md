# Правила русского технического языка

Русские тексты ResticHub пишутся по этим правилам. Правила построены на тех же принципах, что и ASD-STE100 для английского: ограниченный словарь, один термин для одного понятия, короткие предложения, одна инструкция в шаге.

Правила действуют для документации, текстов интерфейса, сообщений об ошибках и переводов английских текстов.

## 1. Слова

<!-- vale off -->

1. Используйте термины из [глоссария проекта](#6-глоссарий-проекта). Один термин обозначает одно понятие. Не заменяйте термин синонимом.
2. Пишите общеупотребительные слова в прямом значении. Не используйте переносные значения и метафоры.
3. Не используйте канцелярские обороты. Пишите проще:

   | Не пишите | Пишите |
   |---|---|
   | данный | этот |
   | является | есть, или перестройте фразу |
   | осуществлять, производить (действие) | глагол действия: «запускать», «проверять» |
   | в целях, с целью | чтобы, для |
   | в случае если | если |
   | в связи с тем что | потому что |
   | при помощи | с помощью, через |
   | имеет возможность | может |
   | необходимо осуществить проверку | проверьте |

4. Не нанизывайте отглагольные существительные. Не пишите «выполнение проверки наличия обновлений». Пишите «агент проверяет, есть ли обновления».
5. Не используйте жаргон: «бэкап» → «резервная копия», «репа» → «репозиторий», «залить» → «загрузить», «задеплоить» → «развернуть».
6. Названия команд, параметров, файлов и интерфейсных элементов не переводите. Оформляйте их как код: `restic prune`, `--retry-lock`.
7. Не используйте слова «просто», «легко», «очевидно», «пожалуйста».
8. Для обязательного требования пишите «должен». Не пишите «желательно» и «рекомендуется» о том, что обязательно.

## 2. Предложения

1. Предложение в процедуре — не длиннее 20 слов.
2. Предложение в описании — не длиннее 25 слов.
3. Абзац — не длиннее 6 предложений.
4. Пишите в действительном залоге. «Агент отправляет результат», а не «результат отправляется агентом».
5. Не используйте причастные и деепричастные обороты, если без них можно обойтись. Разбейте фразу на два предложения.
6. Одна мысль — одно предложение.
7. Не используйте двойное отрицание.

## 3. Процедуры

1. Одна инструкция в одном шаге.
2. Пишите повелительное наклонение на «вы»: «Откройте файл», «Нажмите „Сохранить“». Не используйте инфинитив («Открыть файл») в шагах процедуры.
3. Условие пишите в начале: «Если агент не на связи, выполните шаг 4».
4. Предупреждение пишите до шага, к которому оно относится.
5. Нумеруйте шаги.

## 4. Предупреждения и примечания

| Тип | Когда использовать |
|---|---|
| Предупреждение | Риск потери данных или проблема безопасности. |
| Внимание | Риск повредить конфигурацию или службу. |
| Примечание | Полезные сведения без риска. |

Сначала короткий запрет или команда, затем причина: «Не запускайте `unlock --remove-all`, пока выполняется задание. Возможна потеря данных».

## 5. Оформление

1. Кавычки — «ёлочки». Внутренние кавычки — „лапки“.
2. Тире между словами — длинное (—) с пробелами. Диапазон чисел — короткое тире без пробелов: 5–10.
3. Буква «ё» обязательна там, где без неё возможна ошибка в чтении.
4. Между числом и единицей измерения — неразрывный пробел: 30 с, 100 МБ, 2 ГБ.
5. Названия элементов интерфейса пишите так, как они показаны в интерфейсе, в кавычках: кнопка «Запустить».
6. Списки: пункт с маленькой буквы и точкой с запятой, если пункты — части одной фразы; с большой буквы и точкой, если пункты — отдельные предложения.

| хост | компьютер с агентом | машина, тачка | host |

| план | профиль, назначенный на агенты, с расписанием | задача, расписание | plan |

## 7. Чек-лист проверки

Используйте этот чек-лист при каждой проверке текста (AC-DOC-02):

- [ ] Длина каждого предложения в пределах нормы.
- [ ] В каждом шаге процедуры одна инструкция в повелительном наклонении.
- [ ] Действительный залог.
- [ ] Каждое понятие обозначено одним термином из глоссария.
- [ ] Нет канцелярита, жаргона и слов-паразитов.
- [ ] Предупреждения стоят до шагов.
- [ ] Vale не показывает ошибок.
