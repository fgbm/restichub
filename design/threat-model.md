# Threat model

Status: draft. Date: 2026-10-12. The maintainers review this document before each release (NFR-SEC-02).

## 1. Assets

| Asset | Where it is |
|---|---|
| Backup data | restic repositories |
| Repository passwords and backend credentials | Control plane database, encrypted. Agent memory during a job. |
| Key encryption key (KEK) | File or environment variable on the control plane host |
| Job signing keys (current and next) | Control plane database, wrapped by the KEK (ADR-0026) |
| CA private keys (root and issuing) | Control plane database, wrapped by the KEK (ADR-0026) |
| Agent private keys | Each agent host |
| Trust mode file | Each agent host |
| Audit log | Control plane database |

## 2. Trust boundaries

1. Browser or API client and control plane.
2. Agent and control plane.
3. Agent and repository backend.
4. Control plane and PostgreSQL.
5. Tenant and tenant in one installation. The account rows are installation-wide (ADR-0025).

## 3. Threats and controls

| ID | Threat | Control | Residual risk |
|---|---|---|---|
| T1 | A compromised agent reads or deletes a repository during a job. | Secrets only for one job (ADR-0003). Dedicated maintenance agent. Storage controls in NFR-SEC-08. | **Accepted.** An attacker with root on the host during a job can delete the repository if the backend permits deletion. |
| T2 | A compromised control plane executes code on all hosts. | Server scripts only on hosts with the local trust mode (T33). Typed steps without raw arguments (FR-PR-01). A restore writes only below the restore roots of the host, and never on the files of the agent (ADR-0035). | The control plane can still send restic steps, for example `forget` with a short retention. It can restore any snapshot of a repository below a restore root of an agent. Storage controls in NFR-SEC-08 limit the damage. An administrator who sets the root `/` accepts an in-place restore of any path except the files of the agent. |
| T3 | An attacker writes to the database and inserts jobs. | None. The CP signs each job at dispatch from the state of the database. The job signing key is in the database, wrapped by the KEK (ADR-0026). An attacker who writes plans or profiles gets a signed job. Job signing protects the stream against a network attacker, a replayed or altered job, and a rogue CP without the key (T4, ADR-0005). | **Accepted.** An attacker who can write to the database, or who holds the KEK, can make the CP send any typed step. Database permissions and the audit log are the controls. A separate signing service is a later option. |
| T4 | Replay of an old job. | Job journal and maximum lifetime (ADR-0020). | A redelivered job returns the stored result. It does not run again. |
| T5 | A database dump discloses secrets. | Envelope encryption with a KEK outside the database (ADR-0017, ADR-0023). | If an attacker gets the KEK and the dump, all secrets are disclosed. |
| T6 | One agent impersonates another agent or another tenant. | Identity only from the mTLS certificate (FR-PR-08). The agent pins the installation root CA from the enrollment response (ADR-0026, ADR-0033). Row-Level Security (ADR-0006, ADR-0023). | None. |
| T7 | A user of one tenant reads data of another tenant. | Application checks, Row-Level Security (ADR-0006, ADR-0023), isolation test AC-TN-01. | Defects in new endpoints. AC-TN-01 fails on unchecked endpoints. |
| T8 | A stolen enrollment token enrolls a false agent. | One-time token with a short TTL. Optional quarantine mode (FR-ID-06). The enrollment endpoint runs on the agent listener and on the public web origin (ADR-0033). | A false agent can receive jobs of its tenant until an Admin revokes it. A TLS-intercepting proxy on the public origin can replace the installation root CA in the enrollment response. The agent then pins the wrong root for the stream. A token bound to an existing host (FR-ID-10) takes over the identity of that host with its plans. It lives one hour at most. A new bound token or a successful use revokes the other unused bound tokens of the host. The CP audits a refused use. The machine identifier (FR-ID-11) is a hint. The agent sends only a digest of it, and the CP stores a keyed hash. The replacement of a record needs an Admin action, the right direction and a silent old record (ADR-0041). |
| T9 | Secrets in process arguments, logs or crash dumps. | Environment variables or pipe only (FR-AG-06). Masking (NFR-SEC-05). Crash dumps disabled (FR-AG-07). | A local administrator can read the environment of a running process. |
| T10 | A malicious update of the agent, or a forged release. | Keyless signing: each file and each image gets a Sigstore signature. It comes from the GitHub OIDC identity of the release workflow at the release tag. No long-lived release key exists. The release workflow runs only for a tag on a commit of `main` whose CI run succeeded. A ruleset protects the `v*` tags: only an administrator creates one, and nobody updates or deletes one. The commands of the verification guide run in a job with read permissions only, and the release files come from the signing job. The `latest` image tag moves only in a separate workflow, in an environment that needs the approval of a reviewer and accepts only a `v*` tag. The workflow builds without a cache. It installs its tools at pinned versions with pinned checksums, and it signs only an expected list of files. The verification guide pins the identity to the workflow file and the tag. The release workflow runs the commands of the guide against its own output. The keys of the job signature and of the update stay separate from the release signature (FR-AG-13, ADR-0005). | An attacker can produce a valid signature with the official identity. The attacker needs the GitHub account of the owner, or a changed workflow on `main`. The ruleset and the `main` check raise the cost but do not remove the risk. The Windows executable has no Authenticode signature (deferred after the MVP). |
| T11 | Denial of service through enrollment. | Rate limit (FR-ID-05). | A distributed attack. Use a reverse proxy with rate limits. |
| T12 | Option injection through step string fields. | Argument construction and validation (ADR-0021, AC-PR-08). | Unknown restic behavior in new step types. |
| T13 | A forged signing key update. A forger without the signing key (that is, without both the KEK and the database) cannot make one. | Key update rules (FR-PR-11, AC-PR-09). A signing key compromise retires the key at once, and the signed update revokes it on every open stream (ADR-0030). | The first public key needs a trusted delivery path. An agent that was more than one rotation behind during a compromise enrolls again (ADR-0030). |
| T14 | A tenant Admin takes over an account of another tenant. | The account row is installation-wide and separate from the membership (ADR-0025). A tenant Admin cannot reset the password or change the display name of a shared account (HTTP 403 `shared_account`). It cannot attach an existing foreign account or disable the account. | None for an account with no membership in another tenant. |
| T15 | Username enumeration through the account create endpoint. | The create endpoint needs the Admin role and a rate limit of 20 creates per minute for each actor and tenant. Invitations by email arrive in 1.0 (ADR-0025). | **Accepted.** The answer HTTP 409 `username_taken` reveals an existing name. A tenant Admin can probe names. |
| T16 | Session fixation on the tenant switch. | The switch deletes the old session and rotates the cookie. The new session token is 256 random bits (ADR-0023, ADR-0025). | None. |
| T17 | A revoked agent stays connected or reconnects. | The control plane checks the registry status and the certificate serial at each handshake and stream open (ADR-0026, FR-ID-04). A revoke cancels the running jobs and closes the stream of the instance that serves the revoke at once. Each other instance checks the registry rows of its own streams every 2 seconds and closes the stream of a revoked agent. | A stream on another instance stays open for up to 2 seconds plus the query time. A person who steals the current private key of an agent can rotate it into an identity of their own. The next connection of the real agent then shows a superseded serial. The control plane refuses it, writes the audit record `agent_superseded_certificate_used` and marks the host on the Hosts screen. The real agent is pushed out until an Admin revokes the agent and registers the host again (ADR-0026). |
| T18 | A CA private key or a job signing key in a database dump. | The KEK wraps each key outside the database (ADR-0017, ADR-0023, ADR-0026). | An attacker with the KEK and the dump gets the keys, and can sign jobs and issue agent certificates. The keys are in the database, not in a separate store (T3). `rcgen` and `ring` keep some private key bytes in the heap in a buffer that they do not zeroize. The control plane holds the plaintext only for the current issuing CA. It drops every other copy at load. It refuses a core dump on Linux (ADR-0026). |
| T19 | An attacker swaps a stored key blob. | The AAD binds the ciphertext to the tenant and the key role. The start check binds the key to the certificate of its row (ADR-0026). | None. |
| T20 | A tampered restic binary on a host. | The agent installs restic only after it verifies the OpenPGP signature of the release `SHA256SUMS` with the pinned release key and the archive hash. The binary lives in a protected directory. A protected record holds its SHA-256, and the agent refuses a different binary at each start and spawn. The control plane cannot set the restic path (ADR-0038). On Windows, `register` and `install-service` repair a data directory that an older build left open to another account. They do not repair an open program directory in place. They move it aside and remove it. Then they make it again with the agent and a restic that they download and verify again. A handle to the old directory then points to the moved directory. The copy reads the agent through one handle and refuses a file at the start path that is not the running image. The service does not start with an identity that another account could change, or with a private key that another account can read. This includes the backup of an interrupted swap and the staged files of a rotation. It also includes the key updates, the restic record and the job journal. On Linux, an extended ACL is also a refusal. The service does the same check before each load of the identity at a reconnect. A refusal stops the service with the exit code 78. The service does not start when another account could change the agent program, a directory above it, or restic. A missing restic or a restic that differs from its record stops the service with the exit code 78. | **Accepted.** An attacker with administrator rights on the host can replace the binary and the protected record together. The check raises the cost of an accidental or a partial swap and stops a network attacker. On Windows, a process that opened `%ProgramData%\ResticHub` before the repair keeps the access of that handle until the handle closes. This applies to each level below `%ProgramData%\ResticHub`. A handle with `WRITE_DAC` can put back its access entry, and then remove or replace files on that level. The service then refuses the level at the next start or reconnect and stops with the exit code 78. It does not connect with the replaced files. The trust stays, but the service is not available. Thus the upgrade guide tells the administrator to restart the computer after a repair of `%ProgramData%\ResticHub`. After the restart, `install-service` must repair nothing. A process that keeps a file or a directory in an open `%ProgramFiles%\ResticHub` open stops the move of that tree, also through its current directory. The command refuses its own current directory in that tree before it stops the service. For another process the service stays stopped until the administrator closes that process and runs the command again. This is a denial of service only. |
| T21 | A token in the shell history or in a process argument. | The token is single use with a short TTL and an Admin can revoke it (FR-ID-01). A successful registration consumes it. The audit log records the create, the use and the revoke. | **Accepted.** The token stays in the shell history and in the process list until the registration ends. Before the first use, or after a failed registration until the TTL ends, the value is live. |
| T22 | A Platform Admin reads the tenant data of an organization through the platform right. | The right is an account attribute and gives no tenant data access (ADR-0029). A platform operation runs in the platform scope; the tenant data needs a membership and its role (ADR-0006, ADR-0025). AC-AU-17 checks it. | None for the right alone. The operator grants a membership on purpose. |
| T23 | A Platform Admin adds a membership for itself and hides the change. | The write needs the Platform Admin right, and it is an audit record in the platform audit and in the target organization's audit (ADR-0029). | A Platform Admin can add itself to any active organization. The operator reads the platform audit. |
| T33 | A Platform Admin resets the password of a member and signs in as that member. The tenant audit then shows the actions of the member. | The reset needs the Platform Admin right. In the same transaction, it ends every session of the account. It also writes an audit record in the platform audit and in the audit of each organization of the account. The record holds no password and no hash. The reset of the own account is refused (HTTP 403). The own password change needs the current password. | **Accepted.** A Platform Admin can sign in as any account. The reset of another Platform Admin is permitted. A ban gives no protection, because a Platform Admin can remove the right first and then reset the password. The API tokens that the account created stay valid after the reset. |
| T24 | A user-facing list shows the internal platform tenant. | The organization list, the switcher and the tenant API exclude the platform tenant (ADR-0029). AC-TN-08 checks it. | None. |
| T25 | An organization Admin takes over an account that holds the Platform Admin right, also when the account is a member of that organization only. | A tenant-scope write on such an account is refused (ADR-0029): the password, the display name, the disable, the role change and the membership removal. The guard is in the administrator functions and in a trigger on `memberships`. AC-AU-07 checks it. | None. |
| T26 | A password that an organization Admin knows survives a grant of the Platform Admin right. | A grant of the right to an existing account requires a new password chosen by the Platform Admin. The grant ends every session of the account in the same transaction (ADR-0029). A must-change flag is not enough, because the Admin signs in first with the known password. AC-AU-19 checks it. | None. |
| T27 | A `secret_delivered` audit record for a job that the control plane refused to send. | The dispatcher checks that the agent is online before it reads a secret, so a refused send normally writes no record. The record and the job carry the same `job_id`, so an operator can match them (AC-RP-03). | **Accepted.** If the agent disconnects between the online check and the send, the record exists while the job is `failed`; the secret never left the control plane. |
| T28 | A tenant Admin sets a webhook URL that points to an internal service or to the cloud metadata address (SSRF). | The control plane resolves the host name, refuses every forbidden address and connects to the checked address itself. It follows no redirect and reads no response body. The check includes the IPv6 forms that wrap an IPv4 address, `2001::/23`, `64:ff9b:1::/48` and `192.88.99.0/24`. The lookup and the connection share one time limit. The test button has a rate limit for each actor and tenant, and a bound on the tests that run at once. The installation allow-list is the only way around the check (ADR-0036, AC-MN-05). | The allow-list applies to every tenant of the installation. The operator adds a network only for a trusted installation. |
| T29 | The signing secret of a webhook or the SMTP password leaks through the API, the audit log or a log. | The signing secret and the path and query of the webhook URL (which often hold a token) are encrypted with the tenant key. The signing secret is shown once, and the URL path never. The generic secret API refuses the purposes of these secrets. The audit diff redacts it. The SMTP password comes from a file or the environment and never enters the database (ADR-0017, AC-MN-08). | A person who copies the secret at creation holds it. |
| T30 | An alert floods a channel or the outbox. | The partial unique index allows one open alert for a key. The outbox holds at most 1000 pending messages for a tenant. A failed message stops after five attempts (AC-MN-07). | A tenant with many failing plans gets one message for each plan. |
| T31 | A stolen Operator token or a compromised control plane restores a snapshot over the files of an agent: its identity, journal, binary or system files. The agent runs as root or LocalSystem, so it can write there. | The agent restores only below the restore roots that root or Administrators configure in a protected file. It always refuses a target that overlaps its own files, after it resolves links. It reports the roots, and the control plane refuses early. ADR-0035 and ADR-0004 use the same rule. AC-RS-05 checks it. | An administrator who adds the root `/` accepts a restore to any other directory. A file of the agent, a parent of one and a path inside one stay refused. A restore to the target `/` is not possible. A restore below a root still replaces files there. **Accepted** for the MVP on Windows: the agent has no repository roots there. Thus a restore root such as `D:\` lets a restore overwrite a local repository on that drive. The agent ignores a root that another account can change, and a root with a parent that another account can change. Such an account could replace a directory with a link. An earlier restore or a local user can leave a link in the target. This link does not move a restore outside the root, because restic replaces it with the directory or the file of the snapshot. |
| T32 | A snapshot list or a tree page with an explicit `agent_id` sends the repository keys to that agent. An Operator can name any active agent of the organization. | The agent must be active, online and in the same organization. Each delivery writes `secret_delivered`, and the job writes `browse_start` with the repository and the agent (ADR-0035, ADR-0017). A request has a limit for each actor and for each agent. | **Accepted.** An Operator can already restore to any agent of the organization, so the same trust applies. The operator reads the audit log. |
| T33 | A compromised control plane or a compromised tenant Admin sends a script that runs as SYSTEM or root on a trusted host. | The trust mode is local, off by default, and no job can change it (ADR-0037, AC-HK-07, AC-HK-08). The signature covers the script body, but it protects the transport only (T3). Only an Admin edits scripts and templates. Each change and each run is in the audit log with the SHA-256 hash of the script. The agent runs the script with fixed interpreter flags, bounds its output and masks secret values (AC-HK-09). | **Accepted** for a host whose administrator turns on the trust mode. On such a host the CP has code execution with the rights of the agent service, and it can run any command there. The documentation says so. A pinned-hash mode for scripts is planned after the MVP (issue #136). |
| T34 | A compromised control plane or a stolen Operator token sets the path of a local repository to a system directory. Restic then writes there as root on Linux. | On Linux the systemd unit keeps the file system read-only (`ProtectSystem=strict`, `ProtectHome=read-only`). Only the repository roots that root lists in a protected file are writable (ADR-0045). The agent and `install-service` refuse a root that is `/`, a system directory or a directory of the agent. The agent refuses a local repository outside these roots, or on its own files, before restic starts (`REPOSITORY_PATH_DENIED`). The file has the checks of the restore roots file. The agent also refuses `/home` and `/root` themselves, `/var/spool/cron` and `/var/lib/systemd`, and a line with a quotation mark, a backslash, `%` or white space, which systemd would split in `ReadWritePaths`. The repository roots file and each line of it are protected paths of a restore, also a line that fails the checks. | **Accepted** on Windows: the service has no sandbox there, and the agent checks neither the repository roots nor its own files for a local repository. A local repository path can be any directory that LocalSystem can write, also a directory of the agent. Restic writes only its own repository files at that path. |

## 4. Recommendations for operators

1. Turn on bucket versioning and lifecycle rules on S3 repositories.
2. Give each host group its own backend credentials.
3. Run the maintenance agent on a dedicated host.
4. Copy important repositories (`restic copy`) to a second repository that agents cannot access.
5. Keep the KEK outside the database backup. It wraps the CA keys, the job signing keys and every secret. Without the KEK, all of them are lost.
