# ADR-0035: Alerts, notification channels and the recovery point objective

- Status: accepted
- Date: 2026-10-15
- Requirements: FR-MN-01, FR-MN-03, FR-MN-04, FR-AU-01, AC-MN-01, AC-MN-02, AC-UI-02

## Context

[ADR-0010](0010-queue-and-scheduler-on-postgresql.md) gives the queue and the plan schedule. [ADR-0006](0006-multi-tenancy.md) and [ADR-0017](0017-secret-encryption.md) give the tenant isolation and the secret storage. The first release must tell an operator about three events. A backup fails. A plan misses its recovery point objective (RPO). An agent is offline. The control plane can run in more than one instance. A tenant Admin enters the webhook URL freely, so the URL is an SSRF risk.

## Decision

### Recovery point objective

- A plan has an optional `rpo_seconds`, from 900 (15 minutes) to 34 560 000 (400 days).
- Without a value, the default is the schedule interval plus a margin. The interval is the time between the next two fire times. The margin is one tenth of the interval, at least 15 minutes and at most 2 hours. A daily plan gets 26 hours, an hourly plan 75 minutes and a weekly plan 170 hours.
- The age of a plan is the time since its last succeeded backup job. A plan with no succeeded backup counts from its creation time, so a new plan is not violated before one RPO has passed.
- The state is `ok` below 75 % of the RPO, `at_risk` from 75 % up to the RPO, and `violated` above the RPO.
- A disabled plan and a plan of a revoked agent raise no RPO alert.

### Alert kinds and state

- The kinds are `rpo_violated`, `job_failed`, `job_dead_letter`, `job_warnings`, `agent_offline` and `stale_lock`. A tenant switches each kind on or off. `agent_offline` (default 30 minutes) and `stale_lock` (default 60 minutes) have a threshold. `job_warnings` is off by default.
- A job alert follows the latest finished job of a subject. The subject is the plan, or the repository and the job kind, or the agent and the job kind. The alert is open while that latest job failed. The next succeeded job of the subject resolves it. A cancelled job and an expired job do not count. A failure older than 24 hours at the first evaluation raises no alert.
- The table `alert_state` holds one open row for each `(kind, dedupe_key)`. A partial unique index enforces it, so an evaluation that runs again opens no second alert and sends no repeat while the alert is open.
- An alert that clears because its subject is gone (a deleted or disabled plan, a revoked agent, a disabled rule) resolves without a notification. An alert that clears because the condition is gone sends a recovery notification.
- The agent offline test uses `agents.last_seen_at` from the database, not the stream registry of one instance, so each instance gives the same answer.

### Evaluation and delivery

- A background loop in each control plane instance runs every 30 seconds. For each active tenant, one transaction takes `pg_try_advisory_xact_lock`, evaluates the rules under the tenant policy, changes `alert_state` and writes the outbox rows `alert_deliveries`. The state change and its deliveries commit together.
- A sender claims due deliveries with `FOR UPDATE SKIP LOCKED` and moves `next_attempt_at` forward as a lease. It sends outside the transaction and then records the result. Two instances therefore send a delivery once. A crash between the send and the record repeats the send after the lease, so a delivery is at-least-once. The webhook payload holds a delivery id for the receiver to deduplicate.
- A failed attempt retries after 30 seconds, 2 minutes, 10 minutes and 1 hour. The fifth failure ends the delivery as `failed`. A tenant holds at most 1000 pending deliveries; a newer delivery is stored as failed with the error `queue_full`. The control plane removes finished deliveries after 30 days and resolved alerts after 90 days.
- Each successful send writes an `alert_sent` audit record with the channel, the event and the alert. It holds no secret and no address. The channel records show the recipients and the URL origin, never the URL path.

### Channels

- A tenant Admin manages the channels. A tenant has at most 50.
- An `email` channel has 1 to 20 recipients. The SMTP server is an installation setting (host, port, TLS mode, user, from address). The password comes from `RESTICHUB_SMTP_PASSWORD_FILE` or `RESTICHUB_SMTP_PASSWORD`, like the database password. The control plane never writes it to the database.
- A `webhook` channel has an HTTPS URL. Plain HTTP is refused unless the installation sets `webhook.allow_http`. The payload is JSON with `schema_version`, `id`, `event`, the tenant, the alert and the link. The control plane signs `timestamp + "." + body` with HMAC-SHA256 and sends `X-ResticHub-Signature: sha256=<hex>` and `X-ResticHub-Timestamp`.
- The signing secret is generated by the control plane. It is encrypted with the tenant key like a repository secret (purpose `webhook_secret`). The create response and a rotation response return it once. No other endpoint, audit record or log returns it.
- SSRF protection runs at the connection. The control plane resolves the host name and checks every address. It refuses the send if one address is loopback, private, link-local (including the cloud metadata address 169.254.169.254), carrier-grade NAT, multicast, unspecified or documentation. It also refuses an IPv6 form that wraps such an IPv4 address. Then it connects to the checked address itself. A later DNS answer therefore cannot change the target. The installation setting `webhook.allow_networks` lists CIDR ranges that the check admits. A redirect is never followed. A send has a 10 second limit and a response body limit.
- The control plane never stores or logs the response body of a target.

### Links

The installation setting `public_origin` gives the base URL of the alert link. A job alert links to `/jobs/<id>`. Without the setting, the message holds no link.

## Consequences

- An operator sees alerts in the dashboard and in the channels within about one minute.
- A suspended tenant gets no evaluation.
- The outbox adds four tables, all with `tenant_id` and Row-Level Security.
- The rule that a delivery is at-least-once is in the operations guide.

## Alternatives

| Alternative | Why we did not select it |
|---|---|
| Send from the evaluation transaction | A slow target would hold a database transaction open. |
| One alert row per failed job | A failing plan would send a message for each failure. |
| A fixed 2 × interval RPO | A daily plan would tolerate 48 hours; 26 hours matches the daily case in FR-MN-01. |
| Resolve a webhook host name once at channel save | The DNS answer can change later (rebinding). |
| An HTTP client crate | The send needs the checked address pinned and no redirect; a small client over `tokio-rustls` does this with no new transport stack. |
