A job is one run of a plan or one manual operation. The control plane keeps the jobs in a queue in the database. The queue dispatcher sends each job to an online agent over the open stream.

## Job states

<Diagram name="job-lifecycle" label="The job states and the transitions between them" />

The diagram does not show the redelivery. A job stays in `sent` while the control plane sends it again after the lease or after a busy answer. A lock retry ends the job as `failed` and queues a new job. After the last retry the job goes to `dead_letter`. "Cancelled" and "Succeeded" with warnings are not separate stored states. The table below shows them.

| State in the web interface | Stored state | Meaning |
|---|---|---|
| <Ui k="jobs.status.queued" /> | `queued` | The job is in the queue. The control plane did not send it. |
| <Ui k="jobs.status.sent" /> | `sent` | The control plane sent the job. The agent did not confirm it. |
| <Ui k="jobs.status.running" /> | `running` | The agent confirmed the job and runs it. |
| <Ui k="jobs.status.succeeded" />, in green | `succeeded` | Every step succeeded. |
| <Ui k="jobs.status.succeeded_with_warnings" />, in yellow | `succeeded` | Every step finished, and restic reported warnings. The list shows a pill with this label. The tooltip shows "<Ui k="jobs.statusFull.succeeded_with_warnings" />". The result code is `succeeded_with_warnings`. |
| <Ui k="jobs.status.failed" /> | `failed` | A step failed, or the control plane refused the job. The result code and the reason give the detail. |
| <Ui k="jobs.status.cancelled" /> | `failed` | An Operator cancelled the job. The result code is `cancelled`. |
| <Ui k="jobs.status.expired" /> | `expired` | The job waited in the queue longer than its acceptance window. A running job never expires. |
| <Ui k="jobs.status.dead_letter" /> | `dead_letter` | The repository stayed locked after the last retry. |

A job in a final state never changes again.

## Delivery

The dispatcher builds each job when it sends the job for the first time. It compiles the stored profile of the plan again with the facts of the agent. If the profile no longer compiles, the job fails with the reason `compile_failed`. The control plane never sends a stored command.

A job carries the secrets of its own repository only. The control plane reads each secret when it sends the job and writes a `secret_delivered` audit record. The record holds no secret value.

The control plane always sends `--retry-lock` with a restic command. The value is 4 minutes. Four minutes is shorter than the shortest stall timeout of a profile. restic then ends a held lock with exit code 11 before the agent stops the step as stalled, and the control plane retries the job.

The control plane signs each job. The agent checks the signature before it runs the job. The control plane keeps the signed job, encrypted with the key of the tenant, until the job reaches a final state.

## Lease and redelivery

When the control plane sends a job, it starts a lease. The default lease is 60 seconds. The smallest lease is 15 seconds. If the agent does not confirm the job before the lease ends, the control plane sends the job again. It sends the same signed bytes and does not build the job again. A change to the profile does not change a job that the control plane sent. Each delivery writes the `secret_delivered` audit records. The job has the same identifier each time. The agent keeps a journal and runs a known job once.

If the agent answers that it is busy, the control plane sends the job again after 10 seconds. A busy answer does not count as a delivery.

If the control plane sent a job five times without a confirmation, the job fails with the reason `not_acknowledged`.

If the agent is offline, the job stays in the queue. The control plane reads no secret for an offline agent.

## Repository barriers

Some operations need a repository for themselves. These are `init`, `check`, `forget`, `prune`, `unlock` and `unlock_all`. The queue calls them exclusive.

- An exclusive job starts only when no other job runs on the repository.
- No other job starts on the repository while an exclusive job runs.
- The queue keeps the order of the jobs. A job that waits for the repository blocks the jobs that the control plane queued after it. A prune does not wait for ever behind a stream of new backups.

Several backups can run on one repository at the same time. The repository limit sets the largest number.

## Limits

The queue applies three limits:

| Limit | Default | Setting |
|---|---|---|
| Jobs on one agent | 2 | `RESTICHUB_QUEUE_AGENT_LIMIT` |
| Backups on one repository | 4 | `RESTICHUB_QUEUE_REPOSITORY_LIMIT` |
| Jobs in one tenant | 100 | `RESTICHUB_QUEUE_GLOBAL_LIMIT` |

The same values can be set in the `[queue]` section of the configuration file, with the keys `agent_limit`, `repository_limit` and `global_limit`. A job that exceeds a limit waits in the queue.

## Time limits

A running job has no short fixed time limit. A first backup of a large disk can take many hours. While restic makes progress, the job runs on until the maximum duration of its profile.

### Acceptance window

A job in the queue has an acceptance window. A manual job has a window of one hour. A scheduled job has a window of 24 hours, and the signature of a job is never valid for more than 23 hours. The agent refuses a job after this time. The job detail shows the end of the window as "Accept until" while the job is waiting or sent. A running job does not expire.

### Stall timeout

The agent watches the progress of each step. restic makes progress when the number of bytes or files changes. It also makes progress when the total number of bytes or files changes. A changed list of current files and a new line of text are progress too. A repeated status line is not progress. At a `restore` step, the number of skipped files or bytes is progress too. restic reads and hashes the files that the target already holds, and it counts them there. At a `backup` or a `restore` step, a line on the standard error is not progress. restic reports a warning about one file or a retry of a repository that it cannot reach there. Such a line says nothing about the work. The other steps print their only output on the standard error, so a line there is progress.

A `restore` step that verifies its files prints its last status line and its summary before the verification. It prints no line while it verifies. The agent does not stop this phase as stalled; the maximum duration of the job and a cancel still stop it.

The agent stops a step that makes no progress for the stall timeout. It stops the step in two stages: first the graceful signal, then the forced stop of the process tree after the grace period. The job fails with the reason `stalled`.

| Step | Default stall timeout |
|---|---|
| `backup`, `restore` and the short steps | 60 minutes |
| `check`, `prune` | 6 hours, also inside a backup job |

A profile sets the stall timeout for its jobs. The setting is "Stop after no progress (minutes)" in the section "Run limits" of the profile. The value is from 5 to 10080 minutes. A `check` or `prune` step in the job waits for the longer of this value and 6 hours. A status line that repeats the same content is not progress.

A `restore` job has no profile, so it carries no stall timeout. Its card shows the default stall timeout of a restore, unless the agent sets another value.

### Maximum duration

A profile sets a maximum duration. The setting is "Maximum duration (hours)" in the section "Run limits" of the profile. The default is 48 hours. Zero turns the limit off. When the job runs longer, the agent stops it, whatever its progress. The job fails with the reason `max_duration_exceeded`. The value is from 0 to 720 hours. The job detail shows the limits of a running job (see [Watch and cancel jobs](/restichub/guides/jobs/)).

### Environment variables

An operator can change the defaults. The values are in seconds. The page [Environment variables](/restichub/reference/environment-variables/) lists every variable.

| Variable | Where | Effect |
|---|---|---|
| `RESTICHUB_JOB_STALL_TIMEOUT_SECS` | control plane | The stall timeout of a new profile. From 300 to 604800. |
| `RESTICHUB_JOB_MAX_DURATION_SECS` | control plane | The maximum duration of a new profile. From 0 to 2592000. Zero means no limit. |
| `RESTICHUB_JOB_STALL_TIMEOUT_SECS` | agent | The stall timeout of a job that carries none, for all step kinds. From 60 to 604800. |
| `RESTICHUB_JOB_HARD_CEILING_SECS` | control plane | The time after which the control plane fails a running job whatever its limits. The default is 31 days (2678400). A smaller value than 3600 becomes 3600. |

For the stall timeout and the maximum duration, a value that is not a number, or is out of range, is ignored. The control plane rounds the value up to whole minutes. A profile that exists keeps its own values.

### Lost jobs

The control plane does not fail a running job because of the time that it ran. It fails the job with the reason `agent_lost` in two cases:

- The agent is offline and the control plane did not hear from it for 30 minutes.
- The agent connects again and does not list the job in its hello message. The agent restarted and lost the job.

A job also fails with the reason `timed_out` when it runs 10 minutes longer than its maximum duration and the agent did not report an end. A job with no maximum duration fails with the same reason at the hard ceiling. Maintenance jobs (forget, prune, check) have a maximum duration of 48 hours. The control plane marks the repository lock as possibly stale in each of these cases.

An agent that is older than this version does not know the stall timeout and does not stop a step that makes no progress. The control plane sends such an agent the maximum duration of the profile, or a fixed limit of 12 hours when the profile has none. The job detail shows only the maximum duration for such an agent.

## Lock retries

Restic exits with code 11 when another operation holds the repository lock. The control plane does not give up the plan. It queues the job again with a delay.

The control plane ends the job that reported the lock and queues a new job with a new identifier. The agent keeps a journal and returns the stored result for a known identifier, so a retry needs its own identifier. The new job has the same plan and fire time, and counts one more attempt. The first delay is 30 seconds. The delay doubles for each retry. The largest delay is one hour. After five lock results, the job moves to the final state `dead_letter` and the control plane writes a `job_dead_letter` audit record. Use this record as the alert.

| Setting | Default |
|---|---|
| `RESTICHUB_QUEUE_LOCK_RETRY_LIMIT` | 5 |
| `RESTICHUB_QUEUE_LOCK_RETRY_BASE_SECS` | 30 |
| `RESTICHUB_QUEUE_LEASE_SECS` | 60 |

## Stale locks

A hard stop of restic can leave a lock in the repository. The control plane marks the lock in two cases. The agent reports a possible stale lock, or the agent is lost while a job runs. A job on a lost agent fails with the reason `agent_lost`. The control plane counts an agent as lost only after it read the online agents for two minutes without a break. After the start of the control plane and after a database outage, an agent has that time to connect again. A running job fails with the reason `timed_out` when it stays past its maximum duration and a grace period of 10 minutes. The control plane marks its lock too. The agent stops a stalled step itself. It also stops a step past its maximum duration. It reports `possible_stale_lock` after a forced stop. A sent job that the agent did not confirm before it expired fails with the reason `unacknowledged_expired`, and its lock is marked too. A revoke of a host fails its running job with the reason `agent_revoked` and marks the lock too. When the maintenance host of the repository is revoked, the control plane runs the `unlock` on another active host. A local repository has no other host: its mark stays and the dashboard shows it.

When the mark is 30 minutes old and no job waits or runs on the repository, the control plane queues an `unlock` job. The job never removes the locks of a running operation. If a job that takes the exclusive lock of restic, or that removes the locks, succeeded after the mark, the control plane queues no unlock. A backup runs next to the lock, so its success does not show that the lock is gone.

Only an Admin can remove every lock. The action sends an `unlock_all` job. It needs the repository name as the confirmation. It refuses a repository that has a waiting or running job. The audit log keeps the event `repository_unlock_all`.

## Steps, summary and progress

The agent reports each step of a job as a typed result. The control plane stores one row for each step: the status, the exit code, the times and the error code. The agent can send a result twice, so a second write never changes a stored row. If the control plane cannot store a result because the database is not available, it closes the agent stream. The agent connects again and sends the job results that its journal holds. The journal holds no step result of a job that still runs, so such a step result does not arrive again.

A backup step also carries the restic summary. It holds the new, changed and unchanged files, and the data added to the repository. It also holds the processed files and bytes, the duration and the snapshot identifier. The control plane stores these values as they are. The web UI shows them without a change. A `check`, `forget`, `snapshots` and `stats` step carries its own typed summary.

While a step runs, the agent sends the progress of the step: files, bytes, percent and the file in work. The control plane keeps only the last progress of each job. The job detail shows it for a job that is `sent` or `running`, and removes it when the job ends. The web UI reads the job again every two seconds while the job can still change.

## Job log

The agent sends the log of a job in chunks. It removes every secret before it sends a chunk, and a job log holds at most 1 MiB. The control plane stores one row for each line. Each line has a number, the step, the source (`stdout`, `stderr` or `agent`) and a level. The control plane derives the level from the text of the line: `error`, `warn` or `info`. The agent sends no line time, so the stored time is the time when the control plane stored the line.

The agent keeps each chunk in a protected spool file on its disk until the control plane confirms that it stored the chunk. After a lost connection or a restart of the agent, the agent sends every chunk that is not confirmed, in order. The agent numbers its chunks for each source. The control plane keeps the number of the chunk with each line. It ignores a chunk that it stored before, so a repeated chunk never stores a line twice. The agent deletes the confirmed chunks from its disk.

The spool of all jobs on one host holds at most 64 MiB. Set `RESTICHUB_LOG_SPOOL_MAX_BYTES` on the agent to change the limit. If the control plane is away so long that the spool is full, the agent drops the newest lines. It then adds one line to the log, for example `120 log lines were dropped because the agent log spool was full or not writable`. A stalled connection never delays the cancel of a job. The control plane confirms chunks only to an agent that supports it. An older agent or an older control plane keeps the earlier behavior. In that case the agent sends the last 64 KiB of the log again after a restart.

Each line counts as its text, one line break and 64 bytes of overhead. The control plane stops at 1 MiB of this count or at 100 000 lines for each job, so empty lines cannot fill the database. After that it keeps no new line and marks the log as truncated. The web UI shows the note. The control plane removes control characters from each line, except the tab. It also removes the Unicode format characters (category Cf, for example U+202E). It cuts a line at 8192 characters.

A finished job takes step and log writes from the agent only during the log retention period after its end.

The log storage is a separate component with a `LogStore` interface. The `database` backend is the default. An `s3` backend is planned for the 1.0 release.

### Log retention

The control plane deletes log lines that are older than the retention period. A sweep runs each hour. The job, its steps and its summary stay: only the log text goes away. The job detail then shows that the log is deleted.

| Setting | Default | Variable |
|---|---|---|
| Days that the control plane keeps the log text | 30 | `RESTICHUB_LOG_RETENTION_DAYS` |

The configuration file holds the same value as `log_retention_days`. The value is the same for every tenant, and the control plane keeps the log text by age only. Retention by size and a different period for each tenant are planned for the 1.0 release. A value below 1 is raised to 1. A value above 36500 stops the start.

## Roles

| Role | Right |
|---|---|
| Admin, Operator | Run a plan and cancel a job. A plan holds one waiting manual run: a second run gives HTTP 409 `already_queued`. |
| Admin | Run `unlock_all`. |
| Viewer | Read the jobs, their steps and their logs. |

A suspended tenant sends no job. Its agents stay connected.

## API

| Method and path | Function |
|---|---|
| `GET /api/v1/jobs` | List the jobs, newest first. The parameters `plan_id`, `repository_id`, `agent_id` and `kind` filter the list and each takes a comma-separated list of at most 50 values. The parameter `status` filters by one status. The parameter `group` selects a state tab: `running`, `failed` (without the cancelled jobs), `succeeded` (without the jobs with warnings) or `succeeded_with_warnings`. The parameter `q` finds a part of the plan, host or repository name, at most 200 characters. The parameters `from` and `to` (RFC 3339) limit the creation time, and `to` must not be before `from`. The parameters `sort` (`created_at`, `started_at`, `finished_at`, `duration`, `status`, `plan`, `host`) and `order` (`asc`, `desc`) set the order. The sort by `duration` puts a job that did not finish at the end. The parameters `cursor` and `limit` page the list in the default order, and `offset` (0 to 10000) reads a numbered page. The field `total` gives the number of jobs that match the filters, at most 10000. When more jobs match, the field `total_capped` is `true`. The field `counts` gives the number of all jobs (`all`) and of the jobs of each state tab with the other filters. The parameters `status` and `group` do not change it. |
| `GET /api/v1/jobs/{id}` | Read one job with its steps, its summary and, for a running job, its progress. |
| `GET /api/v1/jobs/{id}/logs` | Read a page of the log. The parameter `after_seq` is the number of the last line that you hold, and `limit` is the page size (1 to 2000, default 500). Use the `seq` of the last line as the next `after_seq`. |
| `POST /api/v1/jobs/{id}/cancel` | Cancel a job. |
| `POST /api/v1/plans/{id}/run` | Run a plan now. |
| `POST /api/v1/repositories/{id}/unlock-all` | Remove every lock of a repository. The body holds `confirm` with the repository name. |

A job of another tenant gives HTTP 404.
