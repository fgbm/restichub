---
title: Компрометация ключа подписи заданий
description: Что делает оператор, когда ключ подписи заданий утёк.
---

Сервер управления подписывает каждое задание текущим ключом подписи. Тот, у кого есть этот ключ, может создавать задания, которые агенты примут. Используйте эту процедуру, если утёк ключ подписи, резервная копия сервера управления с этим ключом или ключ шифрования ключей (KEK).

## Перед началом

- Узнайте время утечки. Посмотрите в аудите платформы действия `signing_key_rotate` и `signing_key_retire`.
- Убедитесь, что агенты могут подключиться к серверу управления. Процедура отправляет подписанное обновление по открытым соединениям.
- Если утёк KEK, сначала замените KEK. Новый KEK заново шифрует все ключи.

## Порядок действий

Узнайте идентификатор текущего ключа. Для этого выполните команду на хосте, где есть файл конфигурации и KEK сервера управления:

```sh
restichub-cp show-signing-key --config /etc/restichub/cp.toml
```

Команда печатает идентификатор и ничего не меняет. Используйте его вместо `<current-key-id>` ниже.

Выполните одну из двух команд.

В режиме с несколькими организациями администратор платформы вызывает API:

```sh
curl -X POST https://<control-plane>/api/v1/platform/signing-keys/compromise \
  -H "Authorization: Bearer <platform-admin-token>" \
  -H "Content-Type: application/json" \
  -d '{"expected_current_key_id": "<current-key-id>"}'
```

В запросе указан ключ, который вы считаете текущим. Если другой вызов уже сменил текущий ключ, сервер управления отвечает HTTP 409 и ничего не меняет. Поэтому повторный вызов с тем же идентификатором ничего не выводит из обращения.

В любом режиме выполните команду на хосте, где есть файл конфигурации и KEK сервера управления:

```sh
restichub-cp compromise-signing-key --config /etc/restichub/cp.toml --expected-key-id <current-key-id>
```

Аргумент `--expected-key-id` обязателен. Если другой вызов уже сменил текущий ключ, команда останавливается и ничего не меняет. Команда печатает идентификатор каждого ключа, который она отозвала как скомпрометированный.

## Что делает команда

1. Следующий ключ становится текущим.
2. Создаётся новый следующий ключ.
3. Старый текущий ключ сразу выводится из обращения с причиной `compromise`. Ключ, который ждал в окне перекрытия, выводится из обращения вместе с ним.
4. Сервер управления добавляет записи аудита `signing_key_compromise` и `signing_key_retire`.
5. Каждый экземпляр сервера управления в течение 2 секунд отправляет агентам по открытым соединениям подписанное обновление. Его подписывает новый текущий ключ, который у агентов уже есть. В обновлении выведенные ключи названы отозванными. С этого момента агенты отклоняют все задания, подписанные старым ключом.

Если следующий ключ тоже утёк, узнайте идентификатор нового текущего ключа командой `show-signing-key` и выполните команду ещё раз с этим идентификатором.

Задание в статусе `sent`, которое подписал выведенный ключ, перед повторной отправкой подписывается заново текущим ключом. Агент не получит старую подпись.

## Агенты, которые были не в сети

Агент, который отстал не больше чем на одну замену ключа, хранит новый текущий ключ как следующий. При подключении он получает цепочку для повторной синхронизации. В ней нет скомпрометированного ключа, но есть шаг, подписанный новым текущим ключом. Агент проверяет этот шаг ключом, который у него уже есть, узнаёт новый следующий ключ и отзывает скомпрометированный. Ему не нужна новая регистрация, и он принимает следующее задание.

Агент, который отстал на две замены или больше (например, после двух компрометаций), не знает нового текущего ключа. Он не может проверить цепочку и не запускает задания. Зарегистрируйте такой хост заново новым токеном регистрации. См. [Регистрация агента](/restichub/ru/getting-started/add-a-host/).

## Результат

- Задания, подписанные старым ключом, агенты не принимают.
- У установки новый текущий ключ и новый следующий ключ.
- В журнале аудита одна запись о компрометации.
