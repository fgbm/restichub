---
title: Компрометация ключа подписи заданий
description: Что делает оператор, когда ключ подписи заданий утёк.
---

Сервер управления подписывает каждое задание текущим ключом подписи. Тот, у кого есть этот ключ, может создавать задания, которые агенты примут. Используйте эту процедуру, когда утёк ключ, резервная копия сервера управления с ключом или ключ шифрования ключей (KEK) (T13, ADR-0030).

## Перед началом

- Узнайте время утечки. Прочитайте аудит платформы: действия `signing_key_rotate` и `signing_key_retire`.
- Убедитесь, что агенты могут подключиться к серверу управления. Процедура отправляет подписанное обновление по открытым потокам.
- Если утёк KEK, сначала замените KEK. Новый KEK заново оборачивает все ключи.

## Порядок действий

Выполните одну из двух команд.

В режиме с несколькими организациями администратор платформы вызывает API:

```sh
curl -X POST https://<control-plane>/api/v1/platform/signing-keys/compromise \
  -H "Authorization: Bearer <platform-admin-token>"
```

В любом режиме выполните команду на хосте, где есть файл конфигурации и KEK сервера управления:

```sh
restichub-cp compromise-signing-key --config /etc/restichub/cp.toml
```

Команда печатает идентификатор каждого ключа, который она отозвала из-за компрометации.

## Что делает команда

1. Следующий ключ становится текущим.
2. Создаётся новый следующий ключ.
3. Старый текущий ключ сразу выводится из обращения с причиной `compromise`. Ключ, который ждал в окне перекрытия, выводится вместе с ним.
4. Сервер управления пишет записи аудита `signing_key_compromise` и `signing_key_retire`.
5. Каждый экземпляр сервера управления отправляет подписанное обновление по своим открытым потокам в течение 2 секунд. Подпись ставит новый текущий ключ, который агенты уже имеют. Обновление называет выведенные ключи отозванными. С этого момента агенты отклоняют каждое задание старого ключа.

Если следующий ключ тоже утёк, выполните команду второй раз.

## Агенты, которые были не в сети

У агента, который был не в сети, нет нового текущего ключа. Цепочка повторной синхронизации никогда не содержит скомпрометированный ключ, поэтому агент не может проверить обновление. Агент отклоняет каждое задание с причиной «unknown key». Зарегистрируйте такой хост заново новым токеном регистрации. См. [Регистрация агента](register-an-agent.md).

## Результат

- Старый ключ не подписывает ни одно задание, которое примет агент.
- У установки новый текущий ключ и новый следующий ключ.
- В журнале аудита одна запись о компрометации.
