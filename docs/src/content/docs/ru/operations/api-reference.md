Сервер управления предоставляет REST API по адресу `/api/v1`. Веб-интерфейс работает через тот же API. На этой странице показано, как пройти аутентификацию. Документ OpenAPI перечисляет все маршруты, поля и ошибки.

## Документ OpenAPI

Сервер управления отдаёт документ OpenAPI по запросу `GET /api/v1/openapi.json`. Для этого маршрута учётные данные не нужны.

```sh
curl -s https://<control-plane>/api/v1/openapi.json -o restichub-openapi.json
```

Откройте файл в просмотрщике OpenAPI или в генераторе кода. В документе описаны две схемы защиты: `cookie` для сессии и `bearer` для токена API.

## Вход с токеном API

Для скрипта используйте токен API. Токен принадлежит одной организации и имеет одну роль.

1. Откройте раздел «Токены API» в веб-интерфейсе.
2. Нажмите «Создать токен». Введите имя, роль и, по желанию, срок действия.
3. Скопируйте значение токена. Сервер управления показывает его только один раз.

Значение токена начинается с `rh_`. Передайте его в заголовке `Authorization`:

```sh
curl -s https://<control-plane>/api/v1/plans \
  -H "Authorization: Bearer rh_<token>"
```

Для запроса с токеном заголовок CSRF не нужен. Роль токена ограничивает маршруты. Если роль не допускает маршрут, сервер отвечает HTTP 403.

Чтобы создать токен через API, используйте сессию или токен с ролью администратора:

```sh
curl -s -X POST https://<control-plane>/api/v1/api-tokens \
  -H "Authorization: Bearer rh_<admin-token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "ci", "role": "viewer", "expires_at": "2027-01-01T00:00:00Z"}'
```

В ответе есть поле `token`. Повторно сервер управления его не возвращает.

## Вход с сессией

Веб-интерфейс использует cookie сессии. Скрипт может сделать то же самое:

```sh
curl -s -c cookies.txt -X POST https://<control-plane>/api/v1/auth/sign-in \
  -H "X-ResticHub-CSRF: 1" \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "password": "<password>"}'
```

Сервер управления устанавливает cookie `__Host-restichub_session`. Запрос, который изменяет данные, с этим cookie должен передавать заголовок `X-ResticHub-CSRF: 1`. Запрос входа тоже требует этот заголовок. Без заголовка сервер отвечает HTTP 403.

```sh
curl -s -b cookies.txt -X POST https://<control-plane>/api/v1/plans/<plan-id>/run \
  -H "X-ResticHub-CSRF: 1"
```

Не передавайте cookie и токен в одном запросе. Такой запрос получает ответ HTTP 400.

## Ошибки

Ответ с ошибкой использует тип данных из RFC 9457. В теле есть такие поля:

| Поле | Значение |
|---|---|
| `status` | Статус HTTP. |
| `code` | Устойчивый код в формате snake_case. Веб-интерфейс переводит его. |
| `title` | Короткий текст на английском языке. |
| `request_id` | Идентификатор запроса. Сообщите его администратору сервера управления. |
| `field`, `reason` | Неверное поле и причина. Их задаёт только код `invalid_argument`. |

## Списки

Маршрут списка возвращает `items` и `next_cursor`. Чтобы получить следующую страницу, передайте значение `next_cursor` в параметре `cursor`. Параметр `limit` задаёт размер страницы.

Списки хостов, заданий, оповещений и записей аудита читают и страницу по номеру. Передайте в параметре `offset` число записей, которые нужно пропустить. Тогда ответ содержит `total` — число записей, подходящих под фильтры. Сервер управления считает не больше 10 000 записей. Если подходящих записей больше, `total_capped` равно `true`. Значение `offset` больше 10 000 даёт HTTP 400 `invalid_argument` с полем `offset` и причиной `out_of_range`. Не передавайте `cursor` и `offset` вместе.

Списки заданий и оповещений возвращают и `counts` — число записей каждой вкладки состояния с остальными фильтрами. У каждой вкладки есть `count` (не больше 10 000) и `capped`. Списки хостов, заданий, оповещений и записей аудита ищут текст по параметру `q`, не длиннее 200 символов. Символы `%`, `_` и `\` ищутся как обычные символы. В журнале аудита `q` ищет часть кода действия, имени объекта или имени действующего лица.

Запись аудита содержит `object_name` и `actor_name` — текущие имена объекта и действующего лица. Значение равно null, если объект удалён или у него нет имени. В журнале платформы значение равно null и для объекта внутри организации.

```sh
curl -s "https://<control-plane>/api/v1/plans?limit=50" \
  -H "Authorization: Bearer rh_<token>"
```

## События в реальном времени

Маршрут `GET /api/v1/events` отправляет Server-Sent Events. Веб-интерфейс открывает один поток на сессию. Поток сообщает интерфейсу, когда читать данные заново. Поэтому интерфейс не опрашивает сервер.

```sh
curl -N "https://<control-plane>/api/v1/events" \
  -H "Authorization: Bearer rh_<token>"
```

Поток показывает только события вашей организации. Для каждого события нужно право на чтение. Роль «Наблюдатель» имеет все права на чтение.

| Событие | Значение |
|---|---|
| `resync` | Первое событие каждого потока. Прочитайте данные заново. |
| `job.progress` | Шаг задания продвинулся или закончился. |
| `job.status` | Задание изменило статус. Поле `status` содержит новый статус. |
| `job.log` | В журнале задания появились новые строки. |
| `host.online`, `host.offline` | Хост подключился или отключился. Поле `agent_id` называет хост. |
| `alert.changed` | Оповещение открылось или закрылось. |

Событие содержит только идентификаторы и статус. В нём нет секретов и строк журнала. Данные читайте через REST API.

Сервер управления не хранит историю событий. После повторного подключения поток сначала отправляет `resync`. Не используйте `Last-Event-ID`, а прочитайте данные заново. Строка-комментарий каждые 15 секунд держит соединение открытым. Поток закрывается не позже чем через 15 минут. Он закрывается раньше, когда доступ кончился: после выхода, при отключении пользователя, при смене роли, при приостановке организации или при отзыве токена API. Сервер проверяет это каждые 30 секунд. Поток также закрывается при остановке сервера и когда клиент не читает его 10 секунд. Затем клиент подключается снова. Одна сессия или один токен API держит 4 потока, один адрес — 100, одна организация — 200, сервер — 2000 (`RESTICHUB_EVENTS_MAX_STREAMS`). Запрос сверх лимита получает HTTP 429.

Одна сессия может держать 4 потока одновременно, а организация — 200. Остальные запросы получают HTTP 429.

Обратный прокси не должен буферизовать поток. Для nginx ответ задаёт заголовок `X-Accel-Buffering: no`. Для другого прокси отключите буферизацию ответов на этом маршруте и разрешите время ожидания чтения больше 30 секунд.
