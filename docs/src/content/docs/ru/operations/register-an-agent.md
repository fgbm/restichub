Агент регистрируется вручную одноразовым токеном регистрации (ADR-0032). Человек на хосте распаковывает пакет агента в любую папку, например в «Загрузки», и выполняет одну команду. Команда `register` делает всё: устанавливает агент, регистрирует хост, запускает службу и сообщает о подключении.

## Команда регистрации

Веб-интерфейс показывает полную команду на экране «Добавить хост». Команда использует адрес сервера управления и токен:

```sh
restichub-agent register --url https://<control-plane> --token <token>
```

- `--url` — адрес сервера управления. Схема должна быть `https`.
- `--token` — одноразовый токен регистрации. ADR-0032 делает этот флаг документированным по умолчанию.
- `--token-file PATH` читает токен из файла. Этот параметр использует скрипт.
- `--token-stdin` читает токен со стандартного ввода.
- `--ca-file PATH` проверяет сервер управления по удостоверяющему центру в файле. Без этого параметра агент использует системные корневые сертификаты.
- `--force` заменяет имеющуюся учётную запись агента. Используйте его для повторной регистрации хоста.
- `--no-service` только регистрирует хост и не устанавливает службу. Выполните `install-service` позже.
- `--restic-archive PATH`, `--restic-sums PATH` и `--restic-sums-sig PATH` задают файлы выпуска restic для автономного хоста (см. раздел «Бинарный файл restic»). Укажите все три параметра или ни одного.

Запускайте команду от имени `root` на Linux или в PowerShell с повышенными правами на Windows («Запуск от имени администратора»). Агент проверяет права, создаёт свои каталоги и убеждается, что может писать в них, до обращения к серверу управления. Неудачная проверка не расходует токен.

Если на хосте нет restic, команда устанавливает его (ADR-0038). Этот шаг выполняется после проверки прав и каталогов и до запроса к серверу управления. Хост без доступа в интернет и без файлов для автономной установки завершается ошибкой на этом шаге, а токен остаётся неиспользованным.

После успешной регистрации команда запускает службу и ждёт подключения к серверу управления до 60 секунд. Затем она печатает итог:

```text
registered as backup-host-01 (agent id 0192f1e0-0000-7000-8000-000000000001)
organization:  0192f1e0-0000-7000-8000-000000000002
service:       installed and running
connection:    connected to https://<control-plane>
```

Если шаг не удался, итог называет, что именно не удалось, и следующую команду. Если агент не подключён, код возврата не равен нулю. Учётная запись агента остаётся, поэтому следующая команда — `install-service` или `status`, а не новая регистрация.

Токен одноразовый. Сервер управления расходует токен при первой успешной регистрации. Использованный, просроченный и отозванный токен дают понятную ошибку.

## Часы хоста

Часы хоста должны отличаться от часов сервера управления не более чем на 5 минут. Сервер управления выпускает сертификат, который начинает действовать за 5 минут до момента выпуска. Агент принимает сертификат, который начинает действовать не позже чем через 5 минут после времени хоста. При большей разнице сертификат нельзя использовать.

Перед отправкой токена агент читает время из ответа сервера управления. Если разница больше 5 минут, агент останавливается и показывает местное время, время сервера управления и разницу. Токен остаётся неиспользованным. Если проверка выпущенного сертификата не проходит, агент также показывает, какой сертификат недействителен.

Поток к серверу управления использует проверку библиотеки TLS, у которой нет допуска. Держите часы хоста верными всё время работы агента.

Как проверить и исправить часы:

- Windows: выполните `w32tm /query /status` в PowerShell с повышенными правами, затем `w32tm /resync`. Или откройте «Параметры», «Время и язык», «Дата и время» и нажмите «Синхронизировать». Проверьте и часовой пояс.
- Linux: выполните `timedatectl status` и найдите `System clock synchronized: yes`. Выполните `timedatectl set-ntp true`, чтобы включить синхронизацию времени. С chrony выполните `chronyc makestep`.

## Сохранённые учётные данные

Команда записывает учётные данные в защищённый каталог конфигурации:

- Linux: `/etc/restichub-agent/`, владелец — служебная учётная запись или `root`. Права на каталог — `0700`.
- Windows: `%ProgramData%\ResticHub\Agent\`. Список ACL даёт полный доступ только SYSTEM и группе «Администраторы».

Каталог хранит эти файлы:

- `agent-key.pem` — закрытый ключ агента. Права на Linux — `0600`.
- `agent-cert.pem` — сертификат агента. Сертификат хранит идентификатор агента и идентификатор организации.
- `ca-chain.pem` — выпускающий и корневой удостоверяющие центры.
- `identity.json` — идентификатор агента, идентификатор организации, адрес сервера управления и адрес gRPC.
- `signing-keys.json` — набор ключей подписи заданий из регистрации.
- `signing-key-updates.json` — цепочка принятых обновлений ключей подписи заданий.
- `job-journal.json` — принятые и завершённые задания. Задание, которое сервер управления доставляет повторно, не выполняется второй раз (ADR-0020).

Токен никогда не попадает в файл и в журнал.

## Проверка соединения

Агент держит один поток к серверу управления (FR-ID-07). Поток передаёт сигнал активности и набор ключей подписи заданий.

Выполните эти шаги, чтобы проверить соединение:

1. Откройте экран «Хосты» в веб-интерфейсе.
2. Найдите хост.
3. Прочитайте состояние соединения.

Сервер управления записывает `last_seen_at` для активного агента. Значение сдвигается вперёд примерно каждые 30 секунд. Устаревшее значение означает, что агент не на связи.

Агент отвечает на каждый сигнал активности сообщением `Pong`. Сервер управления закрывает поток, который не отвечает на сигнал активности три интервала.

Выполните эту команду на хосте, чтобы прочитать локальные учётные данные:

```sh
restichub-agent status
```

Команда печатает идентификатор агента, идентификатор организации, срок действия сертификата и адрес сервера управления. Команда читает сохранённые учётные данные. Команда не проверяет сеть.

Отозванный агент не может подключиться. В журнале агента есть понятный отказ, и агент повторяет попытку с максимальной задержкой 60 секунд. Отзыв закрывает открытый поток сразу (FR-ID-04).

## Инициализация репозитория

Агент выполняет задание репозитория по требованию. Сервер управления передаёт задание через открытый поток. Задание содержит шаг `test_access` и, для инициализации, шаг `init`. Для шага test-access агент выполняет `restic cat config`, для шага init — `restic init`.

Агент выполняет `init` только тогда, когда `test_access` завершается с кодом restic 10. Код restic 10 означает, что репозиторий не существует. Любой другой результат останавливает задание, поэтому агент никогда не инициализирует существующий репозиторий второй раз. Неверный пароль даёт код 12, и задание сообщает `config_error`.

Пароль репозитория и учётные данные серверной части передаются только внутри подписанного задания. Агент передаёт их restic через окружение. Они никогда не попадают в аргумент, журнал, файл журнала заданий или текст ошибки. Агент хранит результат завершённого задания, поэтому задание, которое сервер управления доставляет повторно, не выполняется второй раз (ADR-0020).

Чтобы инициализировать репозиторий:

1. Откройте экран «Репозитории» в веб-интерфейсе.
2. Найдите репозиторий.
3. Запустите «Инициализировать». Для существующего репозитория запустите «Проверить доступ».
4. Прочитайте состояние задания. Состояние `succeeded` означает, что restic инициализировал репозиторий или что доступ успешен. Состояние `config_error` означает, что пароль или учётные данные неверны. Состояние `not_initialized` означает, что репозиторий не существует.
5. Прочитайте состояние репозитория. Сервер управления устанавливает `initialized` после успешной инициализации или успешной проверки доступа.

Инициализация и репозиторий с локальным путём выполняются только на обслуживающем агенте репозитория.

## Установка службы

`register` уже устанавливает службу. Используйте `install-service`, если вы зарегистрировали хост с `--no-service` или если службу нужно починить. Команда отказывает хосту без учётной записи агента и предлагает сначала выполнить `register`. Команда идемпотентна. Она запускает службу и ждёт подключения так же, как `register`.

Запускайте команды от имени `root` на Linux или администратора на Windows:

```sh
restichub-agent install-service
restichub-agent status
restichub-agent uninstall-service
```

- `status` печатает учётную запись агента, срок действия сертификата, версию и путь restic, состояние службы, последнее подключение, последнюю ошибку и адрес сервера управления. Если агент не подключён, код возврата не равен нулю.
- `uninstall-service` останавливает и удаляет службу. Данные остаются.

Агент устанавливает себя сам, копировать файлы вручную не нужно. Команда копирует запущенный агент в каталог программы. Писать туда могут только SYSTEM и «Администраторы» (на Linux — `root`). Если служба работает из этого каталога, команда останавливает её, заменяет файл и запускает службу снова. Служба запускается из каталога программы. Проверка угрозы T20 проходит по построению: команда отказывает исполняемому файлу, который может изменить другая учётная запись.

| Объект | Linux | Windows |
| --- | --- | --- |
| Исполняемый файл агента | `/opt/restichub-agent/bin/restichub-agent` | `%ProgramFiles%\ResticHub\Agent\restichub-agent.exe` |
| Restic | `/opt/restichub-agent/bin/restic` | `%ProgramFiles%\ResticHub\Agent\bin\restic.exe` |
| Учётные данные, файл состояния, запись restic, кэш, журнал | `/etc/restichub-agent`, `/var/lib/restichub-agent`, `/var/cache/restichub-agent` | `%ProgramData%\ResticHub\Agent` |

Прежняя установка хранила restic в `/var/lib/restichub-agent/bin` или в `%ProgramData%\ResticHub\Agent\bin`. Команды `register` и `install-service` переносят restic в каталог программы, переключают службу на новый путь и удаляют старые копии. Учётная запись агента сохраняется, поэтому хост не регистрируется заново.

На Linux команда записывает `/etc/systemd/system/restichub-agent.service` и включает юнит. На Windows команда записывает службу Windows, которая работает от имени LocalSystem. Служба запускается после перезагрузки.

### Устранение неполадок

| Сообщение или признак | Причина | Действие |
| --- | --- | --- |
| `register first: restichub-agent register ...` | `install-service` не нашла действительной учётной записи агента. | Выполните `register` с новым токеном. |
| `service: installed, not running` | Служба остановилась при запуске. | На Linux прочитайте `journalctl -u restichub-agent`. На Windows прочитайте журнал «Приложение». Устраните причину и выполните `install-service`. |
| `connection: not connected ... after the wait` | Агент не достигает сервера управления. | Проверьте часы хоста, межсетевой экран до порта 8443 и адрес. Выполните `status`, чтобы прочитать последнюю ошибку. |
| В журнале сказано, что учётная запись не загружается | Каталог учётных данных повреждён или пуст. Служба завершается с кодом 78 и не перезапускается. | Выполните `register --force` с новым токеном. |
| Команда отказывает каталогу или файлу (T20) | Другая учётная запись владеет объектом или может писать в него. | Верните владельца и доступ SYSTEM и «Администраторы» (Linux: `root`, права 0755). Повторите команду. |
| `cannot stop the service` на Windows | Задание ещё выполняется. | Дождитесь задания или остановите службу вручную. Повторите команду. |

## Компромисс усиления systemd

Юнит сохраняет пять возможностей: `CAP_DAC_READ_SEARCH`, `CAP_DAC_OVERRIDE`, `CAP_CHOWN`, `CAP_FOWNER` и `CAP_FSETID`. Restic работает от имени `root`, поэтому эти пять — единственные возможности в ограничивающем наборе. Без них restic не может прочитать файл другой учётной записи. Он также не может сохранить владельца и права восстановленного файла.

`ProtectSystem=strict` делает всю файловую систему доступной только для чтения. Исключения — каталог учётных данных через `ReadWritePaths` и каталог кэша. Чтение источника резервного копирования остаётся возможным. Restic пишет в локальный репозиторий, поэтому добавьте каждый путь локального репозитория в `ReadWritePaths`. Юнит также перечисляет там корни восстановления (`/var/lib/restichub-restore` и каждый корень из `/etc/restichub-agent-restore-roots.txt`). Команда `install-service` создаёт корень по умолчанию. Выполните её снова после добавления корня, потому что systemd читает список при запуске юнита. `ProtectHome` остаётся выключенным, потому что источник резервного копирования часто лежит ниже `/home`.

Юнит задаёт `CacheDirectory=restichub-agent` и `RESTIC_CACHE_DIR=/var/cache/restichub-agent`. Поэтому кэш restic остаётся в каталоге, в который юнит может писать.

## Бинарный файл restic

Пакет агента не содержит restic. Агент скачивает restic сам (ADR-0038). Команды `register` и `install-service` скачивают его, если на хосте его нет. Команда `run` ничего не скачивает: служба не выполняет сетевых запросов за restic.

Агент берёт последний выпуск restic с GitHub. Он проверяет подпись OpenPGP файла `SHA256SUMS` ключом подписи выпусков проекта restic, который входит в состав агента. Затем он проверяет сумму архива. Агент устанавливает только restic 0.18.1 и новее и отказывает выпуску с основной версией выше 0. Неудачная проверка ничего не устанавливает.

Агент хранит бинарный файл в защищённом каталоге:

- Linux: `/opt/restichub-agent/bin/restic`.
- Windows: `%ProgramFiles%\ResticHub\Agent\bin\restic.exe`. Писать туда могут только SYSTEM и группа «Администраторы».

Защищённый каталог конфигурации хранит файл `restic.json` с версией и суммой SHA-256 установленного бинарного файла. При каждом запуске и перед каждым процессом restic агент сверяет бинарный файл с этой записью и отказывает другому файлу (угроза T20). Сервер управления не может задать путь к restic. Если restic отсутствует или не совпадает с записью, служба останавливается с сообщением о следующем шаге: выполните `restichub-agent restic update`.

### Обновление restic

Выполните команду от имени `root` или в PowerShell с повышенными правами:

```sh
restichub-agent restic update
```

Команда скачивает последний выпуск и проверяет его. Она запускает новый файл с командой `version`. Только после этого она заменяет старый файл одним переименованием. Старый файл остаётся в том же каталоге под именем `restic-previous`. Если шаг не удался, старый файл и старая запись остаются прежними. Служба читает запись перед каждым процессом restic, поэтому следующее задание использует новый файл. Если служба установлена, команда перезапускает её. Параметр `--no-restart` оставляет перезапуск вам. В Windows замена не удаётся, пока служба запускает файл. Тогда остановите службу, выполните команду ещё раз и запустите службу.

Команда отказывает выпуску старее установленного. Параметр `--allow-downgrade` разрешает такую установку.

Последний выпуск может не пройти проверки. Примеры: новая основная версия, изменённый формат подписи, ограничение частоты GitHub. Тогда команда берёт новейший поддерживаемый выпуск из последних десяти выпусков GitHub. Если и он не подходит, она использует выпуск, который закреплён в этой сборке агента. Если ни один выпуск не установился, сообщение перечисляет каждую причину. Тогда используйте файлы для автономной установки.

### Автономный хост

Хост без доступа к GitHub использует файлы, которые вы перенесли с другого компьютера. Скачайте на странице выпуска restic нужной версии три файла:

- `restic_<version>_linux_amd64.bz2` (Linux) или `restic_<version>_windows_amd64.zip` (Windows). Для хоста ARM используйте `arm64`.
- `SHA256SUMS`
- `SHA256SUMS.asc`

Не переименовывайте архив, потому что его имя задаёт версию. Затем выполните любую из команд `register`, `install-service` или `restic update` с параметрами:

```sh
restichub-agent restic update \
  --restic-archive ./restic_0.19.1_linux_amd64.bz2 \
  --restic-sums ./SHA256SUMS \
  --restic-sums-sig ./SHA256SUMS.asc
```

Агент проверяет эти файлы так же, как скачанные.

### Прокси для скачивания

Скачивание учитывает `HTTPS_PROXY` и `NO_PROXY` процесса, который выполняет команду. Прокси должен быть адресом `http://`, например `http://proxy.example:3128`. Агент открывает через него туннель `CONNECT`, поэтому сеанс TLS и все проверки остаются между агентом и GitHub. Прокси с именем пользователя и паролем задайте как `http://user:password@proxy.example:3128`. Особый символ в имени или пароле запишите escape-последовательностью с процентом, например `%40` вместо `@`. Адрес прокси IPv6 пишите в квадратных скобках, например `http://[2001:db8::1]:3128`.

`sudo` удаляет эти переменные. Сохраните их так: `sudo --preserve-env=HTTPS_PROXY,NO_PROXY restichub-agent restic update`.

GitHub ограничивает число запросов без токена. Если GitHub отвечает ограничением частоты, агент сообщает об этом. Повторите позже или используйте файлы для автономной установки.

## Настройки прокси

Репозиторий за прокси использует прокси хоста. Агент передаёт дочернему процессу restic переменные `HTTPS_PROXY`, `HTTP_PROXY` и `NO_PROXY` из собственного окружения, а на Linux и macOS — и их запись строчными буквами. Задайте эти переменные в окружении службы агента, а не в задании.

Дочерний процесс restic не получает других переменных агента, поэтому задание не может перенаправить трафик репозитория (FR-AG-06).
