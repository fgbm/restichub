Эта страница объясняет, что защищает ResticHub, что он защитить не может и что вы делаете, чтобы уменьшить остаточный риск. Полная модель угроз лежит в каталоге `design` репозитория проекта.

## Остаточный риск прямого доступа к репозиторию

Агент читает репозиторий и пишет в него напрямую. Данные резервных копий не проходят через сервер управления. Поэтому на время одного задания сервер управления передаёт агенту пароль репозитория и учётные данные хранилища. Агент их не сохраняет.

Во время задания человек с правами root на хосте может использовать пароль. Он может удалить снимки и, если хранилище разрешает, данные репозитория. ResticHub принимает этот риск. Убрать его нельзя, потому что restic нужен пароль для записи.

Риск уменьшают меры на стороне хранилища. Меры ниже ограничивают ущерб от взломанного хоста.

## Меры защиты

Примените все меры, которые поддерживает ваше хранилище.

1. **Версионирование бакета.** Включите версионирование в репозитории S3. Удалённый объект остаётся как старая версия.
2. **Правила жизненного цикла.** Задайте правило, которое хранит старые версии заданное время. Тогда удаление не стирает данные сразу.
3. **Отдельные учётные данные для каждой группы хостов.** Создайте учётные данные хранилища для каждой группы хостов. Взломанный хост получит доступ только к репозиторию своей группы.
4. **Отдельный агент обслуживания.** Только хост обслуживания выполняет `forget`, `prune` и `check`. Выделите для этой роли отдельный хост. См. [Репозитории](/restichub/ru/concepts/repositories/). Не используйте хост с пользовательским ПО.
5. **Вторая копия.** Копируйте важные репозитории командой `restic copy` в репозиторий, к которому у агентов нет доступа. Запускайте копирование с хоста, который контролируете только вы.

## Другие действия

- Храните ключ шифрования ключей (KEK) отдельно от резервной копии базы данных. KEK защищает пароли репозиториев, ключи подписи заданий и ключи удостоверяющего центра. Без него восстановленная база не содержит пригодных секретов.
- Сохраните пароль репозитория вне ResticHub. Если сервер управления потерян, без пароля снимки не открыть.
- Включайте режим доверия для скриптов сервера только на хосте, который вы готовы разрешить контролировать с сервера управления. См. [Скрипты сервера](/restichub/ru/guides/scripts/).
- Поставьте перед конечной точкой регистрации обратный прокси-сервер с ограничением частоты. См. [Предел частоты регистрации агентов](/restichub/ru/operations/enrollment-rate-limit/).
- Отзывайте хост, которому вы не доверяете. См. [Отзыв агента](/restichub/ru/guides/agent-revocation/).

## Краткое описание модели угроз

| Угроза | Что вас защищает | Что остаётся |
|---|---|---|
| Взломанный агент читает или удаляет репозиторий. | Секреты существуют только на время одного задания. Меры на стороне хранилища. | Вы принимаете риск. Примените меры выше. |
| Взломанный сервер управления отправляет вредные шаги. | Шаги типизированы. Восстановление пишет только в разрешённые каталоги. Скрипт выполняется только там, где включён режим доверия. | Сервер управления всё же может отправить шаги restic, например `forget` с коротким хранением. Восстановление в каталог, который охватывает системные или пользовательские файлы, например `/` или `/home`, может привести к выполнению кода. Задавайте узкие каталоги восстановления. |
| Сетевой злоумышленник меняет или повторяет задание. Сервер без ключа подписи отправляет задание. | Сервер управления подписывает каждое задание. Агент проверяет подпись, адресата, срок действия и журнал повторов. | Известных проблем нет. |
| Кто-то пишет в базу данных и добавляет задания. | Права доступа к базе и журнал аудита. Подпись задания здесь не помогает: сервер управления подписывает каждое задание по состоянию базы, а ключ подписи лежит в базе под защитой KEK. | Тот, кто может писать в базу или владеет KEK, заставит сервер управления отправить любой типизированный шаг. Ограничьте доступ к базе. |
| Кто-то копирует дамп базы данных. | Шифрование секретов с KEK вне базы. | Если KEK и дамп утекли вместе, утекли все секреты. |
| Один агент выдаёт себя за другой агент или другую организацию. | Личность берётся из сертификата mTLS. Построчная защита разделяет организации. | Известных проблем нет. |
| Кто-то крадёт токен регистрации. | Токен действует один раз и истекает. | Ложный агент получает задания своей организации, пока вы его не отзовёте. |
| Кто-то перегружает конечную точку регистрации. | Предел частоты для адреса и для токена. | Распределённая атака. Используйте обратный прокси-сервер. |
