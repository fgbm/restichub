---
title: Обновление
description: Обновление сервера управления и агентов на Linux и Windows до нового выпуска, например с 0.1.0-rc.4.
---

Сначала обновите сервер управления, затем агенты. Сервер управления принимает агент предыдущей младшей версии протокола, поэтому агенты продолжают работать, пока вы обновляете их по одному. См. [Версии агента и сервера управления](/restichub/ru/reference/agent-version-compatibility/).

## Перед началом

1. Прочитайте раздел «Upgrade notes» каждого выпуска между вашей и новой версией на [странице выпусков](https://github.com/fgbm/restichub/releases).
2. Проверьте новый выпуск и прочитайте дайджест его образа. См. [Проверка выпуска](/restichub/ru/operations/verify-a-release/).
3. Сделайте резервную копию сервера управления. См. [Резервная копия сервера управления](/restichub/ru/operations/back-up-the-control-plane/).

## Обновление сервера управления

:::caution
Не пропускайте резервную копию. Миграции нового выпуска меняют базу данных. Резервная копия — единственный путь назад к старому выпуску.
:::

1. Перейдите в каталог выпуска:

   ```sh
   cd /opt/restichub
   ```

2. Получите тег нового выпуска, например `v0.1.0`:

   ```sh
   git fetch --depth 1 origin tag v0.1.0
   ```

3. Переключитесь на тег:

   ```sh
   git checkout v0.1.0
   ```

4. В файле `deploy/reference/.env` задайте в `RESTICHUB_IMAGE` новую ссылку на образ с дайджестом.
5. Перейдите в каталог эталонного стека:

   ```sh
   cd deploy/reference
   ```

6. Загрузите образ и перезапустите стек:

   ```sh
   docker compose pull
   docker compose up -d
   ```

7. Дождитесь, когда `docker compose ps cp` покажет `(healthy)`.

Служба `migrate` применяет новые миграции до запуска сервера управления. Агенты подключаются снова сами.

Проверьте результат:

- `curl -fsS https://restichub.example.com/healthz` выводит `ok`.
- Через несколько минут экран «Хосты» снова показывает хосты «В сети».
- Агент со старым пакетом показывает в своей строке текст `агент 0.1.0-rc.4, есть 0.1.0`.

## Обновление агента на Linux

Регистрировать хост заново не нужно. Учётные данные агента, запись о restic и режим доверия сохраняются.

1. Загрузите на хост новый пакет агента:

   ```sh
   curl -LO https://github.com/fgbm/restichub/releases/download/v<version>/restichub-agent-<version>-linux-amd64.tar.gz
   ```

2. Распакуйте его в пустой каталог:

   ```sh
   mkdir agent-new && tar -xzf restichub-agent-<version>-linux-amd64.tar.gz -C agent-new
   ```

3. Установите новый агент:

   ```sh
   sudo ./agent-new/restichub-agent install-service
   ```

Команда останавливает службу, копирует новую программу, запускает службу и ждёт подключения. Для хоста ARM используйте пакет `linux-arm64`.

## Обновление агента на Windows

1. Загрузите `restichub-agent-<version>-windows-amd64.zip` со страницы выпуска.
2. Распакуйте архив в пустую папку, например в «Загрузки».
3. Запустите PowerShell через «Запуск от имени администратора» и перейдите в эту папку.
4. Установите новый агент:

   ```powershell
   .\restichub-agent.exe install-service
   ```

Команда останавливает службу, копирует новую программу в `%ProgramFiles%\ResticHub\Agent` и запускает службу. Она также исправляет права доступа к `%ProgramData%\ResticHub`, которые оставил старый агент, и создаёт заново `%ProgramFiles%\ResticHub`, если старый агент или ручное копирование оставили эту папку открытой. Если команда остановилась с сообщением, см. [Команды и файлы агента](/restichub/ru/reference/agent-commands/#обновление-агента).

Если выполняется задание, команда не может остановить службу. Дождитесь конца задания и выполните команду снова.

Команда не может перенести открытую папку `%ProgramFiles%\ResticHub`, пока процесс держит открытым файл или каталог в ней. Не переходите в PowerShell в папку внутри `%ProgramFiles%\ResticHub`. Если папку держит другой процесс, команда исправляет папку на месте и запускает службу. Затем она печатает предупреждение с именем этого процесса. До перезагрузки этот процесс может добавить файл в папку. Если вы видите предупреждение, выполните эти шаги:

1. Перезагрузите компьютер.
2. Снова выполните `install-service` от имени администратора.
3. Убедитесь, что в выводе нет строк, которые начинаются с `repaired` или `moved`.

Если команда остановилась, потому что в папке есть файл, который агент не знает, служба остаётся остановленной. Проверьте этот файл и удалите его. Затем выполните команду снова.

## Проверка агентов

1. Откройте «Хосты».
2. Прочитайте вторую строку каждой записи. Актуальный агент показывает только версию, например `агент 0.1.0`.
3. Если хост показывает «Агент устарел», обновите агент этого хоста.

## Возврат к старому выпуску

Если новый сервер управления не запускается, вернитесь к старому выпуску:

1. Остановите стек командой `docker compose down`.
2. Переключитесь на тег старого выпуска и задайте в `.env` старую ссылку на образ.
3. Восстановите базу данных из резервной копии раздела «Перед началом». См. [Резервная копия сервера управления](/restichub/ru/operations/back-up-the-control-plane/#восстановление-на-новом-хосте).
4. Запустите стек командой `docker compose up -d`.

Обновляйте агенты только после того, как новый сервер управления заработал.

## Особенности обновления с 0.1.0-rc.4

- При первом запуске выполняются три миграции базы данных. Они добавляют индексы и поля списков, а также сброс пароля учётной записи платформы.
- На Windows команды `install-service` и `register` исправляют права доступа к `%ProgramData%\ResticHub`. Прочитайте вывод: команда печатает одну строку на каждый каталог верхнего уровня, а также по строке на каждое удаление и каждое предупреждение. Чтобы увидеть каждый исправленный объект, добавьте параметр `--verbose`. Открытую папку `%ProgramFiles%\ResticHub` команда переносит и создаёт заново, поэтому запускайте команду из распакованного пакета. Если эту папку держит процесс, команда исправляет её на месте и печатает предупреждение. Тогда перезагрузите компьютер и выполните команду снова.
- Служба Windows перезапускается после каждого сбоя: через 5, 30 и затем 60 секунд. После кода 78 служба не перезапускается, как и на Linux.
- Служба Windows не запускается, если её учётные данные могла изменить другая учётная запись. Причину служба записывает в журнал событий `ResticHub`, её же показывает `status`. До этого выпуска такая служба подключалась, а каждое задание завершалось ошибкой «restic не запустился».

### Хосты Windows, которым нужна повторная регистрация

Выпуски 0.1.0-rc.2, 0.1.0-rc.3 и 0.1.0-rc.4 создают недостающие уровни `%ProgramData%\ResticHub` и `%ProgramFiles%\ResticHub` с правами только для SYSTEM и «Администраторов». Каталогов с унаследованными правами они не создают. У открытого доступа две причины. Сборка агента до 0.1.0-rc.2 создавала `%ProgramData%\ResticHub` с правами `%ProgramData%`. Папку создали вручную, например при ручном копировании агента в `%ProgramFiles%\ResticHub\Agent`.

На таком хосте один раз выполните следующие шаги:

1. Запустите `install-service` из нового пакета от имени администратора.
2. Если команда сообщает `the identity of this host could be changed by another account`, создайте токен командой «Зарегистрировать заново» на странице хоста.
3. От имени администратора выполните `restichub-agent register --force --url <URL> --token <TOKEN>`. Команда сначала исправляет все каталоги и удаляет старые учётные данные только после всех проверок.
4. Если команда напечатала `repaired the access control of ... under C:\ProgramData\ResticHub...`, перезагрузите компьютер. Программа, которая открыла этот каталог до исправления, сохраняет права своего дескриптора до перезагрузки. Через этот дескриптор она может вернуть свою запись доступа. Тогда служба отклоняет учётные данные и завершается с кодом 78.
5. После перезагрузки снова выполните `install-service`. В выводе не должно быть строк, которые начинаются с `repaired`. Если такая строка есть, программа с правами администратора меняет права на каталог, например средство управления или синхронизации. Найдите и остановите эту программу, затем повторите шаги 4 и 5.

Хосту, который впервые зарегистрирован выпуском 0.1.0-rc.2 или более поздним на чистом компьютере, эти шаги не нужны: достаточно `install-service`.
- Служба Windows пишет журнал в файлы с ротацией в `%ProgramData%\ResticHub\Agent-logs` и в журнал событий `ResticHub`. См. [Журналы агента](/restichub/ru/reference/agent-logs/).
- Локальный репозиторий привязан к своему хосту. Задание локального репозитория на другом хосте сервер управления отклоняет с причиной `not_repository_host`. Если несколько хостов использовали один общий сетевой диск (NFS или SMB) как локальный репозиторий, перенесите этот репозиторий на rest-server или SFTP. Как найти и исправить старые планы, см. [Репозитории, сохранённые до этого правила](/restichub/ru/guides/add-a-repository/#репозитории-сохранённые-до-этого-правила).

### Локальные репозитории в Linux

Новый агент в Linux пишет локальный репозиторий только ниже корня репозиториев. Юнит systemd теперь также задаёт `ProtectHome=read-only`, поэтому `/home`, `/root` и `/run/user` доступны службе только для чтения. Старый юнит оставлял эти каталоги доступными для записи. Поэтому локальный репозиторий ниже `/home` или `/root` раньше работал, а после обновления агент отклоняет его задания с причиной `repository_path_denied`. Кроме того, `install-service` записывает юнит заново и удаляет ручные изменения.

Выполните эти шаги на каждом хосте Linux с локальным репозиторием:

1. Откройте «Репозитории» и найдите каждый репозиторий этого хоста с типом бэкенда «Локальный путь».
2. Проверьте путь каждого репозитория. Если владелец родительского каталога — другая учётная запись, например `/home/<user>`, перенесите репозиторий в каталог, владелец которого — root. Агент отклоняет такой корень: эта учётная запись может заменить каталог ссылкой. Пример:

   ```sh
   sudo systemctl stop restichub-agent
   sudo install -d -o root -g root -m 0755 /srv/restichub
   sudo mv /home/<user>/backup /srv/restichub/fs-01
   sudo chown -R root:root /srv/restichub/fs-01
   ```

3. Запишите каждый родительский каталог репозиториев отдельной строкой в файл `/etc/restichub-agent-repository-roots.txt`, например `/srv/restichub`. Владелец файла — root, другие учётные записи не должны иметь права записи: `sudo chmod 0644 /etc/restichub-agent-repository-roots.txt`.
4. Выполните `sudo restichub-agent install-service`. Команда добавит каждый корень в `ReadWritePaths` и запустит службу.
5. Если вы перенесли репозиторий, откройте его в разделе «Репозитории» и введите новый путь в поле «Путь».
6. Запустите «Проверить доступ» для каждого локального репозитория. Результат должен быть «Репозиторий готов.».

Корнем репозиториев не может быть `/`, системный каталог, например `/etc` или `/usr`, или каталог агента. Корень восстановления и корень репозиториев не могут содержать друг друга. Исключение — корень восстановления `/`. Команда `install-service` останавливается с сообщением, в котором указана строка файла.

При корне восстановления `/` восстановление на месте ниже `/home` или `/root` теперь завершается ошибкой `read-only file system`. Корень восстановления `/home` или `/root` этого не меняет, и теперь `install-service` отклоняет такой корень. Используйте каталог ниже него, владелец которого — root. Восстановите файлы в другой корень, например в `/var/lib/restichub-restore`, и скопируйте их на место. См. [Корни восстановления](/restichub/ru/guides/restore/#корни-восстановления).
