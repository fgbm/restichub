title: Обновление
description: Обновление сервера управления и агентов на Linux и Windows до нового выпуска, например с 0.1.0-rc.4.
---

Сначала обновите сервер управления, затем агенты. Сервер управления принимает агент предыдущей младшей версии протокола, поэтому агенты продолжают работать, пока вы обновляете их по одному. См. [Версии агента и сервера управления](/restichub/ru/reference/agent-version-compatibility/).

## Перед началом

1. Прочитайте раздел «Upgrade notes» каждого выпуска между вашей и новой версией на [странице выпусков](https://github.com/fgbm/restichub/releases).
2. Проверьте каталог `/opt/restichub`. Если в нём есть каталог `.git`, сервер установлен через `git clone`. Тогда вместо шагов обновления выполните шаги раздела [Перенос сервера, установленного через git](#перенос-сервера-установленного-через-git).

## Обновление сервера управления

Сервер обновляет скрипт `install.sh` нового выпуска. Он проверяет выпуск теми же проверками, что и при установке. Затем он делает резервную копию, заменяет файлы выпуска и запускает новый образ.

:::caution[Внимание]
Сохраните резервную копию, которую делает скрипт. Миграции нового выпуска меняют базу данных. Резервная копия — единственный путь назад к старому выпуску.
:::

1. Откройте на сервере сеанс `tmux` или `screen`. Если SSH-соединение оборвётся, сеанс не даст остановить скрипт.
2. Задайте версию нового выпуска:

   ```sh
   VERSION=<version>
   ```

3. Запустите скрипт нового выпуска:

   ```sh
   curl -fsSL "https://github.com/fgbm/restichub/releases/download/v${VERSION}/install.sh" | sudo bash -s -- --upgrade
   ```

   Скрипт печатает `The upgrade to <version> is complete`, версию схемы до и после обновления и каталог резервной копии. Чтобы проверить скрипт до запуска, выполните шаги раздела [Установка с проверкой скрипта](/restichub/ru/getting-started/install-control-plane/#установка-с-проверкой-скрипта) с параметром `--upgrade`.

4. Скопируйте дамп базы данных из каталога резервной копии на другой хост.

Скрипт выполняет эти действия:

1. Проверяет `cosign`, архив выпуска и образ нового выпуска.
2. Останавливается, если блокировку `/run/restichub-install.lock` держит другой запуск `install.sh`. Также останавливается, если прошлый запуск завершился ошибкой и оставил файл `/etc/restichub/INSTALL-FAILED`.
3. Останавливается, если в `/opt/restichub` есть файл переопределения, например `compose.override.yaml`, или если файл окружения задаёт переменную `COMPOSE_`. С таким файлом или переменной новый стек может запуститься на другой базе данных.
4. Запоминает базу данных работающего стека: том `restichub_pgdata`, системный идентификатор PostgreSQL, версию схемы и число пользователей.
5. Сверяет файл KEK, который использует работающий сервер управления, с `/etc/restichub/secrets/restichub_kek`. Сравниваются только суммы SHA-256.
6. Создаёт новый каталог `/var/backups/restichub/<время>` с правами `700`. Параметр `--backup-dir` задаёт другой родительский каталог. Это должен быть абсолютный путь вне `/opt/restichub` и `/etc/restichub`. Права существующего родительского каталога скрипт не меняет.
7. Проверяет свободное место. В каталоге резервной копии и в каталоге данных Docker должно быть по два размера базы данных.
8. Копирует в каталог резервной копии файл окружения и старые файлы выпуска. Делает там дамп базы данных и читает все данные дампа командой `pg_restore -f /dev/null`.
9. Записывает команды возврата в файл `ROLLBACK.txt` в каталоге резервной копии. Затем заменяет файлы в `/opt/restichub` и записывает новый образ в `RESTICHUB_IMAGE`.
10. Запускает только PostgreSQL и сверяет том и системный идентификатор с запомненными. Если они отличаются, скрипт останавливает новый стек до миграций.
11. Запускает стек. Служба `migrate` применяет новые миграции до запуска сервера управления.
12. Ждёт, пока сервер управления не станет работоспособным, и сверяет запущенный образ с проверенным. Если в базе данных были пользователи, а сервер управления печатает новый токен установки, скрипт останавливается. Такой сервер управления не использует старую базу данных.
13. Если `Caddyfile` изменился, запускает новый контейнер `caddy`. Работающий контейнер видит старый файл.

Если действие после резервного копирования завершилось ошибкой, скрипт печатает команды, которые снова запускают старый выпуск, и записывает их в `ROLLBACK.txt`. Текст говорит, запускалась ли миграция:

- `No migration ran` — команды не восстанавливают дамп.
- `The schema moved <старая> -> <новая>` — команды сначала восстанавливают дамп. Старый выпуск не работает с новой схемой.

Скрипт также записывает файл `/etc/restichub/INSTALL-FAILED`. Новый запуск останавливается, пока вы не вернётесь к старому выпуску и не удалите этот файл. Параметр `--force-after-failure` запускает скрипт и с этим файлом. Используйте параметр, только если знаете причину ошибки: новый запуск делает резервную копию того состояния, которое оставил неудачный запуск.

Агенты подключаются снова сами. См. [Возврат к старому выпуску](#возврат-к-старому-выпуску).

### Старые резервные копии

Скрипт не удаляет старые резервные копии. Каждый запуск добавляет каталог в `/var/backups/restichub`. Чтобы удалить старую резервную копию, выполните эти шаги:

1. Убедитесь, что новый выпуск работает и копия самого нового дампа лежит на другом хосте.
2. Выведите каталоги резервных копий:

   ```sh
   sudo ls /var/backups/restichub
   ```

3. Удалите ненужный каталог:

   ```sh
   sudo rm -rf /var/backups/restichub/<время>
   ```

### Обновление вручную

Используйте эти шаги, только если скрипт запустить нельзя. Шаги меняют только образ. Если раздел «Upgrade notes» называет изменение файлов выпуска, используйте скрипт.

1. Проверьте новый выпуск и получите ссылку на его образ по шагам страницы [Проверка выпуска](/restichub/ru/operations/verify-a-release/).
2. Сделайте дамп базы данных. См. [Резервная копия базы данных](/restichub/ru/operations/back-up-the-control-plane/#резервная-копия-базы-данных).
3. Откройте оболочку root (`sudo -i`) и перейдите в каталог стека:

   ```sh
   cd /opt/restichub
   ```

4. Скопируйте файл окружения:

   ```sh
   cp -p /etc/restichub/.env "/etc/restichub/.env.$(date -u +%Y%m%dT%H%M%SZ)"
   ```

5. Задайте в оболочке проверенную ссылку на образ:

   ```sh
   NEW_IMAGE=ghcr.io/fgbm/restichub-cp@sha256:<digest>
   ```

6. Запишите ссылку в файл окружения:

   ```sh
   sed -i "s|^RESTICHUB_IMAGE=.*|RESTICHUB_IMAGE=${NEW_IMAGE}|" /etc/restichub/.env
   ```

7. Загрузите образ и перезапустите стек:

   ```sh
   docker compose pull
   docker compose up -d
   ```

8. Дождитесь, когда `docker compose ps cp` покажет `(healthy)`.

### Проверка новой версии

1. В оболочке root в каталоге `/opt/restichub` выведите образ запущенного сервера управления:

   ```sh
   docker inspect --format '{{.Config.Image}}' "$(docker compose ps -q cp)"
   ```

   Команда печатает ссылку на образ нового выпуска.

2. Убедитесь, что `curl -fsS https://restichub.example.com/healthz` выводит `ok`.
3. Войдите в веб-интерфейс. Откройте меню учётной записи и выберите «О ResticHub». Поле «Версия» показывает новую версию.
4. Для проверки из скрипта прочитайте `GET /api/v1/about` с токеном API. Поле `version` содержит новую версию.
5. Через несколько минут экран «Хосты» снова показывает хосты «В сети».
6. Агент со старым пакетом показывает в своей строке текст `агент 0.1.0-rc.4, есть 0.1.0`.

## Перенос сервера, установленного через git

Прежняя версия этого руководства устанавливала сервер управления через `git clone` в каталог `/opt/restichub`. На таком сервере файл окружения и KEK лежат в `/opt/restichub/deploy/reference`. Команда `git clean` или новый клон в этом каталоге удаляет KEK. Параметр `--migrate-from-git` скрипта `install.sh` переносит сервер на раскладку скрипта и обновляет его до версии скрипта.

:::caution[Внимание]
Скрипт копирует KEK и никогда не удаляет KEK клона. Удалите клон только после того, как копия KEK окажется вне сервера.
:::

### Перед переносом рабочего сервера

Перед переносом рабочего сервера выполните эти проверки:

1. Убедитесь, что в `/opt/restichub/deploy/reference` нет файла переопределения: `compose.override.yaml`, `compose.override.yml`, `docker-compose.override.yaml` или `docker-compose.override.yml`. Если такой файл есть, скрипт останавливается.
2. Убедитесь, что проект стека называется `restichub`:

   ```sh
   sudo docker compose ls
   ```

3. Убедитесь, что база данных лежит в томе `restichub_pgdata`:

   ```sh
   sudo docker inspect --format '{{range .Mounts}}{{.Name}} {{.Destination}}{{println}}{{end}}' restichub-postgres-1
   ```

   В выводе есть строка `restichub_pgdata /var/lib/postgresql/data`.

4. Скопируйте KEK и файл окружения клона за пределы сервера.
5. Убедитесь, что в `/var/backups` есть свободное место на два размера базы данных.
6. Убедитесь, что `/var/tmp` смонтирован без параметра `noexec`. Параметры показывает команда `findmnt -T /var/tmp`. Скрипт запускает `cosign` из этого каталога.
7. Убедитесь, что на сервере есть `git`. Скрипт сверяет файлы `deploy/reference` с коммитом клона.
8. Выведите тег клона командой `git -C /opt/restichub describe --tags`. Используйте выпуск той же или более новой версии.
9. Используйте шаги раздела [Установка с проверкой скрипта](/restichub/ru/getting-started/install-control-plane/#установка-с-проверкой-скрипта), а не `curl … | sudo bash`.
10. Откройте на сервере сеанс `tmux` или `screen`.

### Перенос сервера

1. Убедитесь, что стек клона запущен. Скрипт делает дамп базы данных из запущенного контейнера PostgreSQL и сверяет KEK работающего сервера управления.
2. Задайте версию нового выпуска:

   ```sh
   VERSION=<version>
   ```

3. Запустите проверенный скрипт нового выпуска с параметром `--migrate-from-git`:

   ```sh
   sudo bash install.sh --migrate-from-git /opt/restichub
   ```

   Скрипт печатает `The server uses the files of this script now`, версию схемы до и после переноса и первые 8 символов суммы SHA-256 ключа KEK.

4. Выполните шаги 1–7 раздела [Копия KEK вне сервера](/restichub/ru/getting-started/install-control-plane/#копия-kek-вне-сервера). После переноса скрипт не ждёт слова `saved`, потому что использует KEK клона.
5. Выполните шаги раздела [Проверка новой версии](#проверка-новой-версии).
6. Дождитесь, пока экран «Хосты» не покажет каждый хост «В сети». Затем удалите старый клон. Скрипт печатает команду с каталогом, например:

   ```sh
   sudo rm -rf /opt/restichub.git-backup-<время>
   ```

Скрипт выполняет эти действия:

1. Проверяет `cosign`, архив выпуска и образ. До этого он ничего не меняет.
2. Останавливается, если у клона есть файл переопределения, переменная `COMPOSE_` в файле окружения или изменение файла `deploy/reference`, который отслеживает `git`. Также останавливается, если файл KEK или файл окружения клона — символическая ссылка.
3. Запоминает базу данных работающего стека, как при обновлении. Работающий стек должен быть запущен из `deploy/reference/compose.yaml` клона, а база данных должна лежать в томе `restichub_pgdata`.
4. Копирует `deploy/reference/.env` и `deploy/reference/secrets/restichub_kek` клона в `/etc/restichub`. Файлу окружения задаёт права `600` и владельца root, файлу KEK — права `400` и владельца uid 10001. Сверяет сумму SHA-256 каждой копии с исходным файлом.
5. Делает дамп базы данных в `/var/backups/restichub/<время>` и читает все данные дампа командой `pg_restore -f /dev/null`.
6. Записывает `ROLLBACK.txt` в каталог резервной копии и переименовывает клон в `/opt/restichub.git-backup-<время>`.
7. Записывает файлы выпуска в `/opt/restichub` и запускает стек с тем же именем проекта `restichub`, как при обновлении. Стек использует те же тома, поэтому данные остаются.

Если действие после переименования завершилось ошибкой, скрипт печатает команды, которые снова запускают стек клона, и записывает их в `ROLLBACK.txt`. См. [Возврат после переноса с git](#возврат-после-переноса-с-git).

## Обновление агента на Linux

Регистрировать хост заново не нужно. Учётные данные агента, запись о restic и режим доверия сохраняются.

1. Загрузите на хост новый пакет агента:

   ```sh
   curl -LO https://github.com/fgbm/restichub/releases/download/v<version>/restichub-agent-<version>-linux-amd64.tar.gz
   ```

2. Распакуйте его в пустой каталог:

   ```sh
   mkdir agent-new && tar -xzf restichub-agent-<version>-linux-amd64.tar.gz -C agent-new
   ```

3. Установите новый агент:

   ```sh
   sudo ./agent-new/restichub-agent install-service
   ```

Команда останавливает службу, копирует новую программу, запускает службу и ждёт подключения. Как и в Windows, команда отказывается работать, пока в службе выполняется задание, с сообщением `cannot stop the service`. Дождитесь конца задания и выполните команду снова. Для хоста ARM используйте пакет `linux-arm64`.

## Обновление агента на Windows

1. Загрузите `restichub-agent-<version>-windows-amd64.zip` со страницы выпуска.
2. Распакуйте архив в пустую папку, например в «Загрузки».
3. Запустите PowerShell через «Запуск от имени администратора» и перейдите в эту папку.
4. Установите новый агент:

   ```powershell
   .\restichub-agent.exe install-service
   ```

Команда останавливает службу, копирует новую программу в `%ProgramFiles%\ResticHub\Agent` и запускает службу. Она также исправляет права доступа к `%ProgramData%\ResticHub`, которые оставил старый агент, и создаёт заново `%ProgramFiles%\ResticHub`, если старый агент или ручное копирование оставили эту папку открытой. Если администратор открыл `%ProgramData%\ResticHub\Agent` в проводнике, команда удаляет запись, которую проводник добавил для этой учётной записи, и печатает предупреждение. Регистрировать хост заново из-за этой записи не нужно (см. [Папки агента в проводнике](/restichub/ru/reference/agent-commands/#папки-агента-в-проводнике)). Если команда остановилась с сообщением, см. [Команды и файлы агента](/restichub/ru/reference/agent-commands/#обновление-агента).

Если выполняется задание, команда отказывается работать с сообщением `cannot stop the service`, и служба продолжает задание. Дождитесь конца задания и выполните команду снова. Если агент не может прочитать журнал заданий, сообщение называет и его. Запись, которую в журнале оставил сбой, команде не мешает: служба помечает её при запуске, и отказывает только задание работающей службы. Если остановить службу, агент отменяет выполняемое задание и ждёт его, поэтому restic снимает блокировку репозитория до завершения процесса. Если restic не отвечает на сигнал остановки, блокировка остаётся до истечения её срока.

Команда не может перенести открытую папку `%ProgramFiles%\ResticHub`, пока процесс держит открытым файл или каталог в ней. Не переходите в PowerShell в папку внутри `%ProgramFiles%\ResticHub`. Если папку держит другой процесс, команда исправляет папку на месте и запускает службу. Затем она печатает предупреждение с именем этого процесса. До перезагрузки этот процесс может добавить файл в папку. Поэтому служба запускается только вручную, пока вы не выполните эти шаги:

1. Закройте этот процесс или уберите его из программ, которые запускаются при входе в систему.
2. Перезагрузите компьютер командой «Перезагрузка», а не «Завершение работы». После перезагрузки служба не запускается автоматически.
3. Снова выполните `install-service` от имени администратора.
4. Убедитесь, что в выводе нет строк, которые начинаются с `repaired` или `moved`. Этот запуск снова включает автоматический запуск службы.

Файлы, которые агент не знает, команда удаляет из открытой папки так же, как при её переносе. Для каждого удалённого файла команда печатает отдельную строку.

## Проверка агентов

1. Откройте «Хосты».
2. Прочитайте вторую строку каждой записи. Актуальный агент показывает только версию, например `агент 0.1.0`.
3. Если хост показывает «Агент устарел», обновите агент этого хоста.

## Возврат к старому выпуску

Если новый сервер управления не запускается, вернитесь к старому выпуску. Если `install.sh --upgrade` завершился ошибкой, он печатает эти команды с каталогом своей резервной копии и записывает их в `ROLLBACK.txt` в этом каталоге.

:::danger[Опасно]
Восстановление дампа удаляет базу данных нового выпуска. Задания и изменения после резервного копирования будут потеряны. Если хост зарегистрировался после резервного копирования, зарегистрируйте его снова.
:::

1. Прочитайте `/var/backups/restichub/<время>/ROLLBACK.txt`. Файл говорит, запускалась ли миграция.
2. Откройте оболочку root (`sudo -i`) и остановите стек:

   ```sh
   cd /opt/restichub && docker compose down
   ```

3. Верните файл окружения старого выпуска. В нём лежит старая ссылка на образ:

   ```sh
   cp -p /var/backups/restichub/<время>/restichub.env /etc/restichub/.env
   ```

4. Верните старые файлы выпуска:

   ```sh
   cd / && rm -rf /opt/restichub && cp -a /var/backups/restichub/<время>/release /opt/restichub
   ```

5. Если в тексте написано `No migration ran`, перейдите к шагу 7.
6. Восстановите дамп. Не запускайте `docker compose down -v`: команда удалит и тома Caddy.

   ```sh
   cd /opt/restichub
   docker volume rm restichub_pgdata
   docker compose up -d --wait postgres
   docker compose run --rm -T db-bootstrap
   docker compose exec -T postgres pg_restore -U restichub -d restichub --exit-on-error < /var/backups/restichub/<время>/restichub-<время>.dump
   ```

7. Запустите стек:

   ```sh
   cd /opt/restichub && docker compose up -d
   ```

8. Удалите отметку неудачного запуска:

   ```sh
   rm -f /etc/restichub/INSTALL-FAILED
   ```

## Возврат после переноса с git

Если `install.sh --migrate-from-git` завершился ошибкой после переименования клона, он печатает эти команды и записывает их в `ROLLBACK.txt` в каталоге резервной копии. В каталоге резервной копии лежит дамп. Клон лежит в `/opt/restichub.git-backup-<время>`.

1. Прочитайте `/var/backups/restichub/<время>/ROLLBACK.txt`. Файл говорит, запускалась ли миграция.
2. Откройте оболочку root (`sudo -i`) и остановите новый стек:

   ```sh
   cd /opt/restichub && docker compose down
   ```

3. Удалите файлы выпуска и верните клон:

   ```sh
   cd / && rm -rf /opt/restichub
   mv /opt/restichub.git-backup-<время> /opt/restichub
   ```

4. Если в тексте написано `No migration ran`, перейдите к шагу 6.
5. Восстановите дамп в стеке клона:

   ```sh
   cd /opt/restichub/deploy/reference
   docker volume rm restichub_pgdata
   docker compose up -d --wait postgres
   docker compose run --rm -T db-bootstrap
   docker compose exec -T postgres pg_restore -U restichub -d restichub --exit-on-error < /var/backups/restichub/<время>/restichub-<время>.dump
   ```

6. Запустите стек клона:

   ```sh
   cd /opt/restichub/deploy/reference && docker compose up -d
   ```

7. Удалите отметку неудачного запуска:

   ```sh
   rm -f /etc/restichub/INSTALL-FAILED
   ```

Чтобы перенести сервер позже, запустите скрипт снова. Скрипт принимает копии в `/etc/restichub`, которые оставил неудачный запуск. Он сверяет их с файлами клона без строки `RESTICHUB_IMAGE`.

Обновляйте агенты только после того, как новый сервер управления заработал.

## Особенности обновления с 0.1.0-rc.4

### Сервер управления

- Делайте резервную копию базы данных от имени суперпользователя PostgreSQL стека, как показано в разделе [Резервная копия сервера управления](/restichub/ru/operations/back-up-the-control-plane/#резервная-копия-базы-данных). Команда из документации 0.1.0-rc.4, `pg_dump -U restichub_owner`, не работает. На таблицах включена защита на уровне строк, поэтому дамп останавливается с ошибкой `query would be affected by row-level security policy`.
- При первом запуске выполняются десять миграций базы данных (с 0049 по 0058). Миграции с 0049 по 0055 добавляют индексы и поля списков, сброс пароля учётной записи платформы, имя пользователя rest-server и состояние потока хоста. Пустой адрес электронной почты учётной записи миграция удаляет. Миграция 0055 заменяет уникальные ключи имён. Миграции 0056 и 0057 переносят репозиторий в план и добавляют параметры профиля. Миграция 0058 добавляет приоритет профиля. См. разделы ниже.
- Имена теперь могут быть любым текстом. Имя профиля, плана или канала оповещений — от 1 до 100 символов: любые буквы, пробелы, эмодзи. Имя уникально в организации, регистр букв не важен. Ранее созданные имена остаются допустимыми.
- Имена сравниваются функцией PostgreSQL `lower()`, поэтому результат зависит от параметра `LC_CTYPE` базы данных. Эталонный стек использует `en_US.utf8`. При локали `C` к нижнему регистру приводятся только буквы ASCII. Тогда имена «Ночной» и «НОЧНОЙ» могут существовать одновременно.
- В одном расположении хранится один репозиторий. Сервер управления отклоняет новый или изменённый репозиторий, если его расположение занято другим репозиторием организации. Существующие дубликаты сервер не удаляет: он пишет предупреждение в журнал, а список репозиториев показывает отметку «Общее расположение». Удалите лишние записи в ResticHub. Удаление записи никогда не удаляет данные restic. См. [Добавление репозитория](/restichub/ru/getting-started/add-a-repository/).
- Локальный репозиторий привязан к своему хосту. Задание локального репозитория на другом хосте сервер управления отклоняет с причиной `not_repository_host`. Если несколько хостов использовали один общий сетевой диск (NFS или SMB) как локальный репозиторий, перенесите этот репозиторий на rest-server или SFTP. Как найти и исправить старые планы, см. [Репозитории, сохранённые до этого правила](/restichub/ru/getting-started/add-a-repository/#репозитории-сохранённые-до-этого-правила).
- Для каждого репозитория REST-сервера с паролем укажите имя учётной записи в поле «Имя пользователя». См. [Имя пользователя rest-server](/restichub/ru/reference/agent-version-compatibility/#имя-пользователя-rest-server).
- Скрипты и другие клиенты API получают новые коды ошибок. Отказ в удалении возвращает код с причиной вместо `conflict`, например `repository_in_use` или `profile_in_use`. Новому локальному репозиторию нужно поле `maintenance_agent_id`. Занятое имя пользователя или адрес электронной почты возвращают `username_taken` или `email_taken`. См. [Коды статусов и причин](/restichub/ru/reference/status-codes/).

### Репозиторий в плане

- Репозиторий хранит план, а профиль его не хранит. Миграция 0056 переносит репозиторий каждого профиля в его планы. Профиль без плана теряет репозиторий, и следующий план профиля выбирает репозиторий заново. Страница плана не показывает уведомления о переносе.
- План локального репозитория на другом хосте сервер отклоняет с полем `agent_id` и причиной `not_repository_host`. Удаление репозитория, который использует план, сервер отклоняет с кодом `repository_in_use` и списком планов в `blockers`.
- Планы репозитория делят его политику хранения. Задание хранения получает один шаг `forget` на каждый отдельный профиль планов репозитория, а сведения об агенте берёт из планов этого профиля в этом репозитории.
- `POST /api/v1/profiles` и `PATCH /api/v1/profiles/{id}` больше не принимают `repository_id`. Запрос с этим полем сервер отклоняет как неизвестное поле. В ответе профиля поля `repository_id` тоже нет.
- `POST /api/v1/plans` и `PATCH /api/v1/plans/{id}` требуют `repository_id`. Отсутствующее или пустое значение даёт `400` с полем `repository_id` и причиной `empty`.
- Маршрут `POST /api/v1/profiles/{id}/preview` удалён. Используйте `POST /api/v1/profiles/preview` с полями `agent_id` и необязательным `repository_id`. Без права записи профиля передайте ещё `profile_id`: сервер соберёт сохранённый профиль.

### Параметры профиля

- Профиль объявляет параметры. Хост хранит значения, план может переопределить значение. В редакторе профиля есть раздел «Параметры», на странице хоста — «Значения параметров», на странице плана — «Параметры профиля». Миграция 0057 добавляет объявления и значения. У существующего профиля нет объявленных параметров, поэтому ни один план не меняется.
- У переменной скрипта новый вид «Параметр профиля». Текстовое значение приходит агенту как маскированное. Агент из более старого пакета получает его как секретное значение и маскирует так же. См. [Версии агента и сервера управления](/restichub/ru/reference/agent-version-compatibility/#маскированные-значения-скриптов).
- Секретное значение параметра задаёт, меняет и удаляет только администратор. Текстовые значения задаёт и оператор. Удалить план с секретным значением тоже может только администратор.
- Сохранение, после которого у плана нет значения обязательного параметра, даёт `400` с кодом `parameter_missing` или `parameter_missing_in_plans`. См. [Коды статусов и причин](/restichub/ru/reference/status-codes/#отказы-по-параметрам).

### Приоритет профиля

- У профиля есть параметр `options.priority` со значениями `normal` и `low`. Миграция 0058 задаёт каждому существующему профилю значение `normal`, поэтому приоритет выполняемых заданий не меняется.
- Значение `low` действует на шаг `backup` и на шаг `forget` профиля. Шаги `prune` и `check` сохраняют обычный приоритет.
- `PATCH /api/v1/profiles/{id}` заменяет параметры целиком. Запрос без `options.priority` задаёт значение `normal`. Клиент API, который отправляет параметры профиля, отправляет и приоритет.

### Все агенты

- Служба завершается с кодом 78, если её учётные данные, её программа или restic небезопасны. Служба также завершается, если restic отсутствует или не совпадает со своей записью. Учётные данные служба проверяет снова при каждом новом подключении. После кода 78 служба не перезапускается. Причину показывает `status`. Если restic отсутствует, выполните `install-service --restic-archive <ARCHIVE>`.

### Агенты Windows

- На Windows команды `install-service` и `register` исправляют права доступа к `%ProgramData%\ResticHub`. Прочитайте вывод: команда печатает одну строку на каждый каталог верхнего уровня, а также по строке на каждое удаление и каждое предупреждение. Чтобы увидеть каждый исправленный объект, добавьте параметр `--verbose`. Открытую папку `%ProgramFiles%\ResticHub` команда переносит и создаёт заново, поэтому запускайте команду из распакованного пакета. Если эту папку держит процесс, команда исправляет её на месте и печатает предупреждение. Пока вы не перезагрузите компьютер и не выполните команду снова, служба запускается только вручную.
- Для перезагрузки выбирайте «Перезагрузка», а не «Завершение работы». При быстром запуске Windows завершение работы сохраняет сеанс системы, и агент не видит перезагрузку.
- Служба Windows перезапускается после каждого сбоя: через 5, 30 и затем 60 секунд. После кода 78 служба не перезапускается, как и на Linux.
- Служба Windows не запускается, если её учётные данные могла изменить другая учётная запись. Причину служба записывает в журнал событий `ResticHub`, её же показывает `status`. До этого выпуска такая служба подключалась, а каждое задание завершалось ошибкой «restic не запустился».
- Служба Windows пишет журнал в файлы с ротацией в `%ProgramData%\ResticHub\Agent-logs` и в журнал событий `ResticHub`. См. [Журналы агента](/restichub/ru/reference/agent-logs/).
- Перед восстановлением в непустой каталог агент проверяет пути, которые записывает восстановление. Ссылка, которая ведёт за пределы целевого каталога, останавливает шаг восстановления. Файл с несколькими именами тоже останавливает шаг. Удалите ссылку или восстановите файлы в пустой каталог. См. [Каталоги восстановления](/restichub/ru/guides/restore/#каталоги-восстановления).

### Хосты Windows, которым нужна повторная регистрация

Выпуски 0.1.0-rc.2, 0.1.0-rc.3 и 0.1.0-rc.4 создают недостающие уровни `%ProgramData%\ResticHub` и `%ProgramFiles%\ResticHub` с правами только для SYSTEM и «Администраторов». Каталогов с унаследованными правами они не создают. У открытого доступа две причины. Сборка агента до 0.1.0-rc.2 создавала `%ProgramData%\ResticHub` с правами `%ProgramData%`. Папку создали вручную, например при ручном копировании агента в `%ProgramFiles%\ResticHub\Agent`.

На таком хосте один раз выполните следующие шаги:

1. Запустите `install-service` из нового пакета от имени администратора.
2. Если команда сообщает `the identity of this host could be changed by another account`, создайте токен командой «Зарегистрировать заново» на странице хоста.
3. В папке пакета от имени администратора выполните `.\restichub-agent.exe register --force --url <URL> --token <TOKEN>`. Команда сначала исправляет все каталоги и удаляет старые учётные данные только после всех проверок.
4. Если команда напечатала `repaired the access control of ... under C:\ProgramData\ResticHub...`, перезагрузите компьютер. Программа, которая открыла этот каталог до исправления, сохраняет права своего дескриптора до перезагрузки. Через этот дескриптор она может вернуть свою запись доступа. Тогда служба отклоняет учётные данные и завершается с кодом 78.
5. После перезагрузки снова выполните `install-service`. В выводе не должно быть строк, которые начинаются с `repaired`. Если такая строка есть, программа с правами администратора меняет права на каталог, например средство управления или синхронизации. Найдите и остановите эту программу, затем повторите шаги 4 и 5.

Хосту, который впервые зарегистрирован выпуском 0.1.0-rc.2 или более поздним на чистом компьютере, эти шаги не нужны: достаточно `install-service`.

### Агенты Linux

Команда `install-service` записывает юнит systemd заново и удаляет ручные изменения. Новый юнит задаёт фильтр системных вызовов (`SystemCallFilter=@system-service`) и скрывает другие процессы (`ProtectProc=invisible`). Системный вызов вне фильтра завершается с ошибкой `EPERM`. Поэтому серверный скрипт не может использовать отладочные инструменты, например `strace` или `perf`. См. [Скрипты сервера](/restichub/ru/guides/scripts/).

Новый юнит также не задаёт `RestrictSUIDSGID`. На хосте со старым юнитом восстановление файла с битом setuid или setgid завершалось ошибкой. Такое восстановление записало файл без бита setuid или setgid. Повторите восстановление после `install-service`. В поле «Существующие файлы» выберите «Заменять каждый файл» или «Заменять файл, который отличается» либо восстановите в пустой каталог. С режимом «Оставлять каждый существующий файл» или «Заменять файл, который старше снимка» restic пропускает файл, который оставило неудачное восстановление. Тогда задание получает статус «Успешно», но у файла нет бита setuid или setgid.

Новый юнит также оставляет службе привилегию `CAP_SETFCAP`. На хосте со старым юнитом восстановление файла с файловой привилегией (file capability), например `ping`, завершалось ошибкой. Задание получало статус «Не выполнено». Выполните `install-service` из нового пакета. Затем повторите восстановление. В поле «Существующие файлы» выберите «Заменять каждый файл» или «Заменять файл, который отличается» либо восстановите в пустой каталог. С режимом «Оставлять каждый существующий файл» или «Заменять файл, который старше снимка» restic пропускает файл, который оставило неудачное восстановление. Тогда задание получает статус «Успешно», но у файла нет файловой привилегии.

### Локальные репозитории в Linux

Новый агент в Linux пишет локальный репозиторий только ниже корня репозиториев. Юнит systemd теперь также задаёт `ProtectHome=read-only`, поэтому `/home`, `/root` и `/run/user` доступны службе только для чтения. Старый юнит оставлял эти каталоги доступными для записи. Поэтому локальный репозиторий ниже `/home` или `/root` раньше работал, а после обновления агент отклоняет его задания с причиной `repository_path_denied`. Кроме того, `install-service` записывает юнит заново и удаляет ручные изменения.

Выполните эти шаги на каждом хосте Linux с локальным репозиторием:

1. Откройте «Репозитории» и найдите каждый репозиторий этого хоста с типом бэкенда «Локальный путь».
2. Проверьте путь каждого репозитория. Если владелец родительского каталога — другая учётная запись, например `/home/<user>`, перенесите репозиторий в каталог, владелец которого — root. Агент отклоняет такой корень: эта учётная запись может заменить каталог ссылкой. Пример:

   ```sh
   sudo systemctl stop restichub-agent
   sudo install -d -o root -g root -m 0755 /srv/restichub
   sudo mv /home/<user>/backup /srv/restichub/fs-01
   sudo chown -R root:root /srv/restichub/fs-01
   ```

3. Запишите каждый родительский каталог репозиториев отдельной строкой в файл `/etc/restichub-agent-repository-roots.txt`, например `/srv/restichub`. Владелец файла — root, другие учётные записи не должны иметь права записи: `sudo chmod 0644 /etc/restichub-agent-repository-roots.txt`.
4. Выполните `sudo /opt/restichub-agent/bin/restichub-agent install-service`. Команда добавит каждый корень в `ReadWritePaths` и запустит службу.
5. Если вы перенесли репозиторий, откройте его в разделе «Репозитории» и введите новый путь в поле «Путь».
6. Запустите «Проверить доступ» для каждого локального репозитория. Результат должен быть «Репозиторий готов.».

Корнем репозиториев не может быть `/`, системный каталог, например `/etc` или `/usr`, или каталог агента. Каталог восстановления и корень репозиториев не могут содержать друг друга. Исключение — каталог восстановления `/`. Команда `install-service` останавливается с сообщением, в котором указана строка файла.

При каталоге восстановления `/` восстановление на месте ниже `/home` или `/root` теперь завершается ошибкой `read-only file system`. Каталог восстановления `/home` или `/root` этого не меняет, и теперь `install-service` отклоняет такой каталог. Используйте каталог ниже него, владелец которого — root. Восстановите файлы в другой каталог, например в `/var/lib/restichub-restore`, и скопируйте их на место. См. [Каталоги восстановления](/restichub/ru/guides/restore/#каталоги-восстановления).
