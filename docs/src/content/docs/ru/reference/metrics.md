Сервер управления отдаёт метрики для Prometheus по адресу `GET /metrics` в текстовом формате Prometheus.

## Доступ

Адрес не публичный: нужны учётные данные с ролью не ниже Наблюдателя. Идентификаторы агентов, планов и репозиториев — данные организации, поэтому анонимному клиенту сервер управления их не отдаёт. Сессия Администратора платформы в платформенной организации получает HTTP 403, потому что в этой организации нет заданий. Переключитесь на нужную организацию или используйте её токен.

Для опроса используйте API-токен с ролью Наблюдатель. Токен принадлежит одной организации: в ответе только метрики этой организации. Чтобы читать метрики нескольких организаций, создайте токен в каждой и добавьте для каждого токена отдельное задание опроса.

1. Создайте в организации API-токен с ролью Наблюдатель.
2. Сохраните токен в файл, который может читать только пользователь Prometheus.
3. Добавьте задание опроса, которое берёт токен из файла как bearer-токен.

```yaml
scrape_configs:
  - job_name: restichub
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/restichub-token
    static_configs:
      - targets: ['restichub.example.com']
```

## Метрики

У каждой метрики есть метка `tenant` с идентификатором организации. В идентификаторе нет персональных данных.

| Метрика | Тип | Метки | Значение |
|---|---|---|---|
| `restichub_last_success_timestamp_seconds` | gauge | `tenant`, `plan` | Unix-время последней успешной резервной копии плана. Если у плана ещё не было успешной копии, значения нет. |
| `restichub_job_duration_seconds` | histogram | `tenant`, `kind` | Длительность выполненных заданий. Границы: 1, 5, 15, 30, 60, 120, 300, 600, 1800 и 3600 секунд. |
| `restichub_job_dispatch_delay_seconds` | histogram | `tenant` | Время от момента, когда задание может запуститься, до его первой отправки агенту. Границы: 0,05; 0,1; 0,25; 0,5; 1; 2; 3; 5; 10 и 30 секунд. |
| `restichub_jobs_total` | counter | `tenant`, `status` | Задания, достигшие статуса `succeeded`, `failed`, `expired` или `dead_letter`. |
| `restichub_agent_up` | gauge | `tenant`, `agent` | 1, если у агента открыто соединение, иначе 0. |
| `restichub_repo_lock_held` | gauge | `tenant`, `repository` | 1, если ожидающее или выполняющееся задание репозитория сообщило о блокировке, иначе 0. |
| `restichub_plan_schedule_failed` | gauge | `tenant`, `plan` | 1, если последний проход планировщика по плану завершился ошибкой. У плана без ошибки значения нет. |
| `restichub_maintenance_schedule_failed` | gauge | `tenant`, `repository`, `task` | 1, если последний проход планировщика по расписанию обслуживания завершился ошибкой. У расписания без ошибки значения нет. |
| `restichub_agent_connections_refused_total` | counter | `tenant`, `reason` | Соединения агентов, которые порт агентов закрыл на пределе. Причина: `cap` — предел соединений `RESTICHUB_AGENT_MAX_CONNECTIONS`; `anonymous_share` или `anonymous_per_ip` — пределы для соединений без клиентского сертификата; `handshakes` или `handshakes_per_ip` — пределы для незавершённых рукопожатий TLS. Только в режиме одной организации. |
| `restichub_agent_accept_errors_total` | counter | `tenant` | Ошибки порта агентов при приёме соединения, например когда у процесса нет свободного файлового дескриптора. Только в режиме одной организации. |

Сервер управления кеширует итоги организации на 15 секунд, поэтому при интервале опроса меньше 15 секунд одни и те же значения приходят дважды. Значение `restichub_agent_up` всегда актуально.

Порт агентов обслуживает все организации, поэтому в режиме нескольких организаций счётчики порта агентов в ответе отсутствуют. Отказы и ошибки приёма видны в журнале сервера управления в любом режиме. Если за минуту были отказы или ошибки приёма, сервер управления пишет в журнал одно предупреждение. В нём указано число отказов по каждой причине и число ошибок приёма за эту минуту.

Если проход по плану или по расписанию обслуживания завершается ошибкой, сервер управления пишет ошибку в журнал и записывает ошибку в план или в расписание. Страница плана и страница репозитория показывают ошибку.

Ошибка базы данных временная. Сервер управления сохраняет время запуска и повторяет проход после паузы. Первая пауза — 5 секунд. После каждой неудачной попытки пауза удваивается, но не превышает 10 минут. После восстановления базы данных политика пропущенных запусков плана определяет, какие задания создаст сервер управления.

Недопустимое выражение cron, неизвестный часовой пояс и расписание без времени запуска — постоянная ошибка. Сервер управления не повторяет попытку, пока пользователь не изменит выражение cron, часовой пояс или признак включения. План остаётся включённым, оповещение RPO остаётся активным. Сводка считает такой план находящимся под угрозой.

Сервер управления пишет в журнал аудита запись `schedule_failed` от имени системы, когда возникает ошибка, и `schedule_recovered`, когда её снимает успешный проход. Успешный проход или правка выражения cron, часового пояса или признака включения убирает ошибку и её значение.

Чтобы получать оповещение, если план или расписание обслуживания завершилось ошибкой, используйте выражение:

```
restichub_plan_schedule_failed == 1 or restichub_maintenance_schedule_failed == 1
```

Чтобы получать оповещение, если у плана сутки нет успешной резервной копии, используйте выражение:

```
time() - restichub_last_success_timestamp_seconds > 86400
```
