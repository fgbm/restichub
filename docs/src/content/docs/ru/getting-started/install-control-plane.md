title: Установка сервера управления
description: Установка сервера управления, веб-интерфейса и порта агентов на один сервер с помощью Docker Compose.
---

Сервер управления работает на одном сервере Linux. На этой странице описана установка на этот сервер сервера управления, PostgreSQL, веб-интерфейса и порта агентов. Шаги используют эталонный набор из каталога `deploy/reference` репозитория и Docker Compose. Для крупной установки нужен отдельный проект.

## Части системы

| Часть | Назначение |
|---|---|
| Сервер управления | Хранит конфигурацию, создаёт задания по расписанию, отвечает на запросы API и отдаёт веб-интерфейс |
| PostgreSQL | Хранит данные установки |
| Обратный прокси (Caddy) | Принимает HTTPS-подключения к веб-интерфейсу и сам получает для него сертификат |
| Порт агентов | Принимает подключения агентов на отдельном порту |

## Перед началом

- Подготовьте сервер Linux с памятью не менее 2 ГБ и доступом в интернет.
- Установите на сервер Docker Engine, плагин Compose и `git`.
- Выберите доменное имя для сервера управления, например `restichub.example.com`.
- Создайте запись DNS для этого имени. Используйте тип A и публичный адрес сервера:

  ```text
  restichub.example.com.  A  203.0.113.10
  ```

- Откройте на межсетевом экране сервера эти порты:

| Порт | Протокол | Назначение |
|---|---|---|
| 22 | TCP | Администрирование по SSH |
| 80 | TCP | Проверка домена для выпуска сертификата обратным прокси |
| 443 | TCP | Веб-интерфейс, API и регистрация агентов |
| 8443 | TCP | Порт агентов |

Обратный прокси получает публичный сертификат для домена при первом запуске. Он использует протокол ACME. До запуска набора запись DNS должна указывать на сервер, а порты 80 и 443 должны быть доступны из интернета.

## Получение дайджеста образа

Устанавливайте образ выпуска по дайджесту. Тег может переместиться, дайджест — нет.

1. Откройте [страницу выпусков](https://github.com/fgbm/restichub/releases) и выберите выпуск.
2. Найдите ссылку на образ в разделе «Contents». Ссылка имеет вид `ghcr.io/fgbm/restichub-cp@sha256:<digest>`.
3. Проверьте образ по шагам страницы [Проверка выпуска](/restichub/ru/operations/verify-a-release/).

## Установка

Выполняйте шаги в оболочке root (`sudo -i`). Файл окружения и файл ключа может читать только их владелец, а владельцем файла ключа должен быть пользователь сервера управления (uid 10001).

1. Получите тег выпуска в каталог `/opt/restichub`. Укажите тег выпуска, например `v0.1.0-rc.4`:

   ```sh
   git clone --depth 1 --branch v0.1.0-rc.4 https://github.com/fgbm/restichub.git /opt/restichub
   ```

2. Перейдите в каталог эталонного набора:

   ```sh
   cd /opt/restichub/deploy/reference
   ```

3. Создайте файл окружения. Укажите свой домен, свой адрес почты и ссылку на образ с дайджестом:

   ```sh
   ./init-env.sh restichub.example.com admin@example.com ghcr.io/fgbm/restichub-cp@sha256:<digest>
   ```

   Скрипт выводит `wrote .env`.

4. Запустите набор:

   ```sh
   docker compose up -d
   ```

5. Убедитесь, что сервер управления работает:

   ```sh
   docker compose ps cp
   ```

   В колонке `STATUS` есть `(healthy)`. Служба `migrate` применяет миграции базы данных до запуска сервера управления, поэтому первый запуск может занять минуту.

6. Убедитесь, что обратный прокси получил сертификат:

   ```sh
   curl -fsS https://restichub.example.com/healthz
   ```

   Команда выводит `ok`. Если команда показывает ошибку TLS, прочитайте журнал прокси командой `docker compose logs caddy`.

7. Прочитайте одноразовый токен настройки:

   ```sh
   docker compose logs cp | grep setup_token
   ```

Набор работает из рабочей копии тега выпуска. Ему нужны и другие файлы репозитория: служба `db-bootstrap` читает файл `crates/restichub-db/sql/bootstrap-roles.sql`. Не копируйте каталог `deploy/reference` отдельно.

## Первый администратор

:::danger[Опасно]
Токен настройки — секрет. Не отправляйте его на общий терминал или в чат. Токен нужен один раз, при первом входе, и действует один день.
:::

1. Откройте `https://restichub.example.com` в браузере. Откроется экран «Первоначальная настройка».
2. Введите токен в поле «Токен настройки».
3. Введите имя пользователя и пароль длиной не менее 12 символов.
4. Нажмите «Создать администратора».
5. Войдите с новым именем пользователя и паролем.

## Файл окружения

Набор берёт настройки из одного файла — `.env` рядом с `compose.yaml`. Скрипт `init-env.sh` создаёт этот файл со случайными секретами. Права на файл — `600`. Скрипт не перезаписывает существующий файл.

| Значение | Содержимое |
|---|---|
| `POSTGRES_USER` | Суперпользователь PostgreSQL набора |
| `POSTGRES_PASSWORD` | Пароль этого суперпользователя |
| `POSTGRES_DB` | Имя базы данных установки |
| `RESTICHUB_OWNER_PASSWORD` | Пароль учётной записи владельца. Его используют миграции |
| `RESTICHUB_RUNTIME_PASSWORD` | Пароль рабочей учётной записи. Его использует сервер управления |
| `RESTICHUB_DOMAIN` | Доменное имя сервера управления |
| `RESTICHUB_ACME_EMAIL` | Адрес электронной почты для сертификата |
| `RESTICHUB_IMAGE` | Ссылка на образ выпуска с дайджестом |
| `RESTICHUB_AGENT_ENDPOINT` | Адрес порта агентов, к которому подключаются агенты. Скрипт задаёт `https://<домен>:8443` |
| `RESTICHUB_TENANCY_MODE` | `single` или `multi`. Скрипт задаёт `single` |
| `RESTICHUB_TRUSTED_PROXIES` | Сеть обратного прокси в форме CIDR |

Необязательное значение `RESTICHUB_AGENT_PORT` меняет внешний порт агентов. По умолчанию — 8443. Остальные настройки сервера управления перечислены на странице [Переменные окружения](/restichub/ru/reference/environment-variables/).

Ключа шифрования ключей в `.env` нет. `init-env.sh` записывает его в файл `secrets/restichub_kek` с правами `400`, а Docker подключает файл как секрет. Сервер управления читает его через `RESTICHUB_KEK_FILE`. Ключ открывает пароли репозиториев и удостоверяющий центр установки. Владельцем файла должен быть пользователь сервера управления (uid 10001). Сервер отказывается читать файл, доступный другим пользователям. Если вы запустили `init-env.sh` не от root, выполните после него `sudo chown 10001:10001 secrets/restichub_kek`.

:::caution[Внимание]
Не передавайте ключ в переменной окружения `RESTICHUB_KEK`. `docker inspect` и окружение процесса показывают её значение. Переменная работает для совместимости, но мы её не рекомендуем.
:::

## Обновление

:::caution[Внимание]
Прочитайте замечания об обновлении в новом выпуске до начала работ. Выпуск может изменить файлы набора или файл окружения.
:::

1. Проверьте новый выпуск и прочитайте дайджест его образа, как в разделе [Получение дайджеста образа](#получение-дайджеста-образа).
2. Сделайте [резервную копию](#резервная-копия) базы данных.
3. Перейдите в рабочую копию:

   ```sh
   cd /opt/restichub
   ```

4. Получите новый тег выпуска, например `v0.1.0`:

   ```sh
   git fetch --depth 1 origin tag v0.1.0
   ```

5. Переключитесь на этот тег:

   ```sh
   git checkout v0.1.0
   ```

6. В файле `deploy/reference/.env` задайте в `RESTICHUB_IMAGE` новую ссылку на образ с дайджестом.
7. Перейдите в каталог эталонного набора:

   ```sh
   cd deploy/reference
   ```

8. Загрузите образ и перезапустите набор:

   ```sh
   docker compose pull
   docker compose up -d
   ```

Служба `migrate` применяет новые миграции до запуска сервера управления. Убедитесь, что `docker compose ps cp` показывает `(healthy)`.

## Резервная копия

Сервер управления хранит пароли репозиториев в базе данных. Ключ шифрования ключей их открывает. Удостоверяющий центр установки тоже лежит в базе данных, поэтому одна копия базы данных хранит всю установку.

1. Сделайте копию базы данных:

   ```sh
   docker compose exec -T postgres pg_dump -U restichub_owner restichub > restichub.sql
   ```

2. Скопируйте файл на другой хост.
3. Сохраните копию ключа шифрования ключей в другом месте, например в менеджере паролей. Ключ лежит в файле `secrets/restichub_kek`.
4. Не храните ключ вместе с копией базы данных. Если злоумышленник получит копию и ключ вместе, он раскроет все секреты.

:::danger[Опасно]
Потеря базы данных или ключа шифрования ключей лишает вас паролей репозиториев и удостоверяющего центра установки. Restic не может открыть репозиторий без его пароля. Храните копии на другом хосте.
:::

## Порт агентов

Агенты подключаются к отдельному порту с взаимной проверкой сертификатов (mTLS). Сервер управления сам расшифровывает это соединение, поэтому обратный прокси не должен стоять перед этим портом.

Первый запрос регистрации агент отправляет на домен, порт 443. Обратный прокси отвечает на этот запрос со своим публичным сертификатом. Затем агент получает корневой удостоверяющий центр установки и проверяет по нему порт агентов.

:::caution[Внимание]
Порт агентов должен быть доступен из каждой сети с агентами. Проверьте правила межсетевого экрана сервера и всего сетевого пути.
:::

Задайте в `RESTICHUB_AGENT_ENDPOINT` адрес, к которому обращаются агенты. Сервер управления выпускает для порта агентов сертификат, в котором этот хост указан как дополнительное имя (SAN).

Зарегистрируйте каждый хост так, как описано в разделе [Регистрация агента](/restichub/ru/getting-started/add-a-host/).
