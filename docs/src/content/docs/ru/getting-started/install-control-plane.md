Сервер управления работает на одном сервере Linux. На этой странице описана установка на этот сервер сервера управления, PostgreSQL, веб-интерфейса и порта агентов. Скрипт выпуска `install.sh` устанавливает эталонный стек с помощью Docker Compose. Для крупной установки нужен отдельный проект.

## Части системы

| Часть | Назначение |
|---|---|
| Сервер управления | Хранит конфигурацию, создаёт задания по расписанию, отвечает на запросы API и отдаёт веб-интерфейс |
| PostgreSQL | Хранит данные установки |
| Обратный прокси (Caddy) | Принимает HTTPS-подключения к веб-интерфейсу и сам получает для него сертификат |
| Порт агентов | Принимает подключения агентов на отдельном порту |

## Перед началом

- Подготовьте сервер Linux с памятью не менее 2 ГБ и доступом в интернет. Архитектура сервера — `x86_64` или `arm64`.
- Установите на сервер Docker Engine и плагин Compose по [руководству Docker](https://docs.docker.com/engine/install/). `git` на сервере не нужен.
- Убедитесь, что на сервере есть `curl`, `sudo`, GNU coreutils и GNU tar. С инструментами BusyBox скрипт не работает.
- Убедитесь, что `/var/tmp` смонтирован без параметра `noexec`. Скрипт запускает `cosign` из этого каталога. Чтобы использовать другой каталог, задайте для скрипта переменную `TMPDIR`.
- Откройте на сервере сеанс `tmux` или `screen`. Если SSH-соединение оборвётся, сеанс не даст остановить скрипт.
- Выберите доменное имя для сервера управления, например `restichub.example.com`.
- Создайте запись DNS для этого имени. Используйте тип A и публичный адрес сервера:

  ```text
  restichub.example.com.  A  203.0.113.10
  ```

- Откройте на межсетевом экране сервера эти порты:

| Порт | Протокол | Назначение |
|---|---|---|
| 22 | TCP | Администрирование по SSH |
| 80 | TCP | Проверка домена для выпуска сертификата обратным прокси |
| 443 | TCP | Веб-интерфейс, API и регистрация агентов |
| 8443 | TCP | Порт агентов |

Обратный прокси получает публичный сертификат для домена при первом запуске. Он использует протокол ACME. До запуска скрипта запись DNS должна указывать на сервер, а порты 80 и 443 должны быть доступны из интернета.

## Установка

1. Откройте [страницу выпусков](https://github.com/fgbm/restichub/releases) и найдите версию выпуска, например `1.2.0`.
2. Задайте версию в оболочке:

   ```sh
   VERSION=<version>
   ```

3. Запустите скрипт выпуска. Укажите свой домен и свой адрес почты:

   ```sh
   curl -fsSL "https://github.com/fgbm/restichub/releases/download/v${VERSION}/install.sh" | sudo bash -s -- --domain restichub.example.com --email admin@example.com
   ```

   Скрипт печатает `The control plane is healthy and runs the verified image` и путь к ключу шифрования ключей (KEK).

4. Выполните шаги раздела [Копия KEK вне сервера](#копия-kek-вне-сервера). Скрипт ждёт, пока вы не введёте `saved`.

Скрипт выполняет эти действия:

1. Проверяет, что он запущен от root и что Docker Engine и Docker Compose версии 2 или новее отвечают. Проверяет, что порты 80, 443 и 8443 свободны. Блокировку `/run/restichub-install.lock` держит только один запуск скрипта.
2. Останавливается, если сервер не пустой: есть файл KEK, файл окружения, том `restichub_pgdata` или том либо контейнер проекта `restichub`. Сообщение называет найденное. Для установленного сервера используйте `--upgrade`, для сервера, установленного через `git clone`, — `--migrate-from-git`.
3. Скачивает `cosign` и сверяет его сумму SHA-256 с заданным значением.
4. Скачивает архив `restichub-deploy-<version>.tar.gz` и проверяет его подпись. Подпись должна принадлежать рабочему процессу выпуска на теге версии.
5. Читает из архива ссылку на образ и проверяет подпись образа с той же идентичностью.
6. Записывает файл окружения и KEK в `/etc/restichub`, а файлы выпуска — в `/opt/restichub`.
7. Запускает стек, ждёт, пока сервер управления не станет работоспособным, и сверяет запущенный образ с проверенным.

Если проверка не прошла, скрипт останавливается до любых изменений на сервере. Ни один параметр скрипта не отключает проверку. Если установка завершилась ошибкой после записи файлов, скрипт печатает команды, которые удаляют только файлы и тома этого запуска.

## Установка с проверкой скрипта

Команда из раздела [Установка](#установка) запускает скрипт до его проверки. Она доверяет HTTPS-соединению с GitHub. Чтобы сначала проверить скрипт, выполните эти шаги:

1. Получите `cosign` по шагам раздела «Получение cosign» страницы [Проверка выпуска](/restichub/ru/operations/verify-a-release/#получение-cosign).
2. Задайте версию выпуска:

   ```sh
   VERSION=<version>
   ```

3. Скачайте скрипт и его пакет подписи:

   ```sh
   curl -fsSLO "https://github.com/fgbm/restichub/releases/download/v${VERSION}/install.sh"
   curl -fsSLO "https://github.com/fgbm/restichub/releases/download/v${VERSION}/install.sh.sigstore.json"
   ```

4. Проверьте подпись скрипта:

   ```sh
   cosign verify-blob \
     --bundle install.sh.sigstore.json \
     --certificate-identity "https://github.com/fgbm/restichub/.github/workflows/release.yml@refs/tags/v${VERSION}" \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com \
     install.sh
   ```

   Команда печатает `Verified OK`.

5. Выведите сумму SHA-256 скрипта:

   ```sh
   sha256sum install.sh
   ```

6. Сравните значение со строкой `install.sh` в разделе «Install the control plane» описания выпуска. Не запускайте скрипт, если значения различаются.
7. Запустите скрипт:

   ```sh
   sudo bash install.sh --domain restichub.example.com --email admin@example.com
   ```

Для запуска без терминала, например из средства автоматизации, добавьте `--kek-saved`. Этим параметром вы подтверждаете, что средство автоматизации копирует KEK и файл окружения за пределы сервера. Без терминала и без этого параметра скрипт отказывается запускаться.

## Копия KEK вне сервера

:::danger[Опасно]
Скопируйте KEK и файл окружения за пределы сервера сейчас. Без KEK никто не расшифрует пароли репозиториев и ключи в базе данных. Резервная копия базы данных без KEK бесполезна.
:::

1. Во втором терминале на сервере запишите каталог `/etc/restichub` в архив, который можете читать только вы:

   ```sh
   rm -f ~/restichub-config.tar.gz
   (umask 077 && sudo tar -czf - -C /etc restichub > ~/restichub-config.tar.gz)
   ```

   Первая команда удаляет старый архив: `umask` не меняет права существующего файла.

2. На своей рабочей станции скопируйте архив с сервера:

   ```sh
   scp admin@restichub.example.com:restichub-config.tar.gz .
   ```

3. На сервере удалите архив:

   ```sh
   rm ~/restichub-config.tar.gz
   ```

4. На рабочей станции выведите первые 8 символов суммы SHA-256 ключа из архива:

   ```sh
   tar -xzOf restichub-config.tar.gz restichub/secrets/restichub_kek | sha256sum | cut -c1-8
   ```

5. Убедитесь, что значение совпадает со значением, которое напечатал скрипт.
6. Положите архив в менеджер паролей или в сейф. Храните его отдельно от резервных копий базы данных.
7. Удалите архив с рабочей станции.
8. В терминале скрипта введите `saved`. После `install.sh --migrate-from-git` пропустите этот шаг: скрипт не ждёт этого слова, потому что использует KEK клона.

## Проверка установки

Выполняйте шаги в оболочке root (`sudo -i`). Файл окружения может читать только root, поэтому каждой команде `docker compose` нужны права root.

1. Перейдите в каталог стека:

   ```sh
   cd /opt/restichub
   ```

2. Убедитесь, что сервер управления работает:

   ```sh
   docker compose ps cp
   ```

   В колонке `STATUS` есть `(healthy)`.

3. Убедитесь, что обратный прокси получил сертификат:

   ```sh
   curl -fsS https://restichub.example.com/healthz
   ```

   Команда выводит `ok`. Если команда показывает ошибку TLS, прочитайте журнал прокси командой `docker compose logs caddy`.

4. Прочитайте одноразовый токен настройки:

   ```sh
   docker compose logs cp | grep setup_token
   ```

## Файлы установки

| Место | Содержимое | Владелец и права |
|---|---|---|
| `/opt/restichub` | Файлы выпуска: `compose.yaml`, `Caddyfile`, `bootstrap-roles.sql`, `install.sh` и ссылка на образ `IMAGE`. Ссылка `.env` указывает на `/etc/restichub/.env`. Каждое обновление заменяет каталог. | root, `755` |
| `/etc/restichub/.env` | Файл окружения с паролями | root, `600` |
| `/etc/restichub/secrets/restichub_kek` | KEK | uid 10001, `400` |
| Том Docker `restichub_pgdata` | База данных | Docker |
| Тома Docker `restichub_caddy_data` и `restichub_caddy_config` | Сертификат и состояние Caddy | Docker |

Не храните свои файлы в `/opt/restichub`. Обновление заменяет этот каталог.

## Первый администратор

:::danger[Опасно]
Токен настройки — секрет. Не отправляйте его на общий терминал или в чат. Токен нужен один раз, при первом входе, и действует один день.
:::

1. Откройте `https://restichub.example.com` в браузере. Откроется экран «Первоначальная настройка».
2. Введите токен в поле «Токен настройки».
3. Введите имя пользователя и пароль длиной не менее 12 символов.
4. Нажмите «Создать администратора».
5. Войдите с новым именем пользователя и паролем.

## Файл окружения

Стек берёт настройки из одного файла — `/etc/restichub/.env`. Compose находит его по ссылке `/opt/restichub/.env`. Скрипт `install.sh` создаёт этот файл со случайными секретами. Права на файл — `600`. Скрипт не перезаписывает существующий файл. Каждое значение он записывает в одинарных кавычках, поэтому Compose не подставляет переменную вместо `$` в значении.

| Значение | Содержимое |
|---|---|
| `POSTGRES_USER` | Суперпользователь PostgreSQL стека |
| `POSTGRES_PASSWORD` | Пароль этого суперпользователя |
| `POSTGRES_DB` | Имя базы данных установки |
| `RESTICHUB_OWNER_PASSWORD` | Пароль учётной записи владельца. Его используют миграции |
| `RESTICHUB_RUNTIME_PASSWORD` | Пароль рабочей учётной записи. Его использует сервер управления |
| `RESTICHUB_DOMAIN` | Доменное имя сервера управления |
| `RESTICHUB_ACME_EMAIL` | Адрес электронной почты для сертификата |
| `RESTICHUB_IMAGE` | Ссылка на образ выпуска с дайджестом |
| `RESTICHUB_AGENT_ENDPOINT` | Адрес порта агентов, к которому подключаются агенты. Скрипт задаёт `https://<домен>:8443` |
| `RESTICHUB_TENANCY_MODE` | `single` или `multi`. Скрипт задаёт `single` |
| `RESTICHUB_TRUSTED_PROXIES` | Сеть обратного прокси в форме CIDR |

Необязательное значение `RESTICHUB_AGENT_PORT` меняет внешний порт агентов. По умолчанию — 8443. Остальные настройки сервера управления перечислены на странице [Переменные окружения](/restichub/ru/reference/environment-variables/).

KEK в файле окружения нет. `install.sh` записывает его в файл `/etc/restichub/secrets/restichub_kek` с правами `400`, а Docker подключает файл как секрет. Сервер управления читает его через `RESTICHUB_KEK_FILE`. Ключ открывает пароли репозиториев и удостоверяющий центр установки. Владельцем файла должен быть пользователь сервера управления (uid 10001). Сервер отказывается читать файл, доступный другим пользователям.

:::caution[Внимание]
Не передавайте ключ в переменной окружения `RESTICHUB_KEK`. `docker inspect` и окружение процесса показывают её значение. Переменная работает для совместимости, но мы её не рекомендуем.
:::

## Обновление

См. [Обновление](/restichub/ru/guides/upgrade/). Скрипт `install.sh --upgrade` делает резервную копию до изменений на сервере. Сервер, установленный через `git clone`, переходит на новую раскладку командой `install.sh --migrate-from-git`.

## Мониторинг

Опрашивайте `/readyz` внешним мониторингом. Для контейнера и балансировщика используйте `/healthz`. См. [Мониторинг сервера управления](/restichub/ru/operations/monitor-the-control-plane/).

## Резервная копия

Сохраните базу данных и KEK и храните их раздельно. См. [Резервная копия сервера управления](/restichub/ru/operations/back-up-the-control-plane/).

## Порт агентов

Агенты подключаются к отдельному порту с взаимной проверкой сертификатов (mTLS). Сервер управления сам расшифровывает это соединение, поэтому обратный прокси не должен стоять перед этим портом.

Первый запрос регистрации агент отправляет на домен, порт 443. Обратный прокси отвечает на этот запрос со своим публичным сертификатом. Затем агент получает корневой удостоверяющий центр установки и проверяет по нему порт агентов.

:::caution[Внимание]
Порт агентов должен быть доступен из каждой сети с агентами. Проверьте правила межсетевого экрана сервера и всего сетевого пути.
:::

Задайте в `RESTICHUB_AGENT_ENDPOINT` адрес, к которому обращаются агенты. Сервер управления выпускает для порта агентов сертификат, в котором этот хост указан как дополнительное имя (SAN).

Каждое соединение агента занимает один файловый дескриптор сервера управления. При запуске сервер управления поднимает мягкий предел открытых файлов до жёсткого и записывает предел в журнал. Если предел мал для `RESTICHUB_AGENT_MAX_CONNECTIONS`, в журнале появляется предупреждение. В эталонном compose-файле у сервиса `cp` задано `ulimits: nofile` со значением 65536. В другой среде запуска задайте такой же предел (для systemd — `LimitNOFILE=65536`).

Зарегистрируйте каждый хост так, как описано в разделе [Регистрация агента](/restichub/ru/getting-started/add-a-host/).
