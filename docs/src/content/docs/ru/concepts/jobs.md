---
title: Задания
description: Как очередь отправляет задания агентам, ограничивает их и повторяет.
---

Задание — один запуск плана или одна ручная операция. Сервер управления хранит задания в очереди в базе данных. Диспетчер очереди отправляет каждое задание агенту, который на связи, по открытому потоку (FR-SC-03, ADR-0010).

## Состояния задания

| Состояние | Значение |
|---|---|
| В очереди (`queued`) | Задание в очереди. Сервер управления его не отправил. |
| Отправлено (`sent`) | Сервер управления отправил задание. Агент его не подтвердил. |
| Выполняется (`running`) | Агент подтвердил задание и выполняет его. |
| Успешно (`succeeded`) | Все шаги выполнены успешно. |
| Ошибка (`failed`) | Шаг завершился ошибкой, задание отменили или сервер управления его отклонил. Код результата и причина дают подробности. |
| Срок истёк (`expired`) | Задание ждало в очереди дольше срока жизни в очереди. Выполняющееся задание никогда не истекает. |
| Остановлено (`dead_letter`) | Репозиторий оставался заблокированным после последнего повтора. |

Задание в конечном состоянии больше не меняется.

## Доставка

Диспетчер собирает каждое задание в момент отправки. Он снова компилирует сохранённый профиль плана с фактами агента. Если профиль больше не компилируется, задание завершается с причиной `compile_failed`. Сервер управления никогда не отправляет сохранённую команду.

Задание несёт только секреты своего репозитория (AC-PR-03). Сервер управления читает каждый секрет в момент отправки и пишет запись аудита `secret_delivered`. Запись не содержит значения секрета (AC-RP-03).

Сервер управления всегда передаёт `--retry-lock` с командой restic (FR-SC-05).

Сервер управления подписывает каждое задание. Агент проверяет подпись до выполнения задания (FR-PR-03).

## Аренда и повторная отправка

Отправляя задание, сервер управления начинает аренду. Аренда по умолчанию — 60 секунд, наименьшая — 15 секунд. Если агент не подтвердил задание до конца аренды, сервер управления отправляет задание снова (FR-PR-06, AC-PR-04). Он отправляет те же подписанные байты и не собирает задание заново, поэтому изменение профиля не меняет уже отправленное задание. Каждая отправка пишет записи аудита `secret_delivered`. Если агент отвечает, что занят, сервер управления отправляет задание снова через 10 секунд; такой ответ не считается отправкой. Идентификатор задания каждый раз тот же. Агент ведёт журнал и выполняет известное задание один раз.

Если сервер управления пять раз отправил задание без подтверждения, задание завершается с причиной `not_acknowledged`.

Если агент не на связи, задание остаётся в очереди. Для такого агента сервер управления не читает секреты.

## Барьеры репозитория

Некоторым операциям нужен репозиторий целиком. Это `init`, `check`, `forget`, `prune`, `unlock` и `unlock_all`. Очередь называет их исключительными (FR-SC-04).

- Исключительное задание начинается, только когда в репозитории нет других заданий.
- Пока выполняется исключительное задание, другие задания в репозитории не начинаются.
- Очередь хранит порядок заданий. Задание, которое ждёт репозиторий, блокирует задания, поставленные после него. Очистка не ждёт вечно за потоком новых резервных копий.

В одном репозитории одновременно могут работать несколько резервных копий. Наибольшее число задаёт лимит репозитория.

## Лимиты

Очередь применяет три лимита (FR-SC-08, AC-SC-08):

| Лимит | По умолчанию | Параметр |
|---|---|---|
| Заданий на одном агенте | 2 | `RESTICHUB_QUEUE_AGENT_LIMIT` |
| Резервных копий в одном репозитории | 4 | `RESTICHUB_QUEUE_REPOSITORY_LIMIT` |
| Заданий в одной организации | 100 | `RESTICHUB_QUEUE_GLOBAL_LIMIT` |

Те же значения можно задать в секции `[queue]` файла конфигурации ключами `agent_limit`, `repository_limit` и `global_limit`. Задание, которое превысило лимит, ждёт в очереди.

## Повторы при блокировке

Restic завершается с кодом 11, когда другая операция держит блокировку репозитория. Сервер управления не отказывается от плана. Он снова ставит задание в очередь с задержкой (FR-SC-05, AC-SC-05).

Сервер управления завершает задание, которое сообщило о блокировке, и ставит в очередь новое задание с новым идентификатором. Агент ведёт журнал и возвращает сохранённый результат для известного идентификатора, поэтому повтору нужен свой идентификатор. У нового задания тот же план и то же время запуска, а счётчик попыток больше на единицу. Первая задержка — 30 секунд. С каждым повтором задержка удваивается. Наибольшая задержка — один час. После пяти ответов о блокировке задание переходит в конечное состояние `dead_letter`, а сервер управления пишет запись аудита `job_dead_letter`. Используйте эту запись как оповещение.

| Параметр | По умолчанию |
|---|---|
| `RESTICHUB_QUEUE_LOCK_RETRY_LIMIT` | 5 |
| `RESTICHUB_QUEUE_LOCK_RETRY_BASE_SECS` | 30 |
| `RESTICHUB_QUEUE_LEASE_SECS` | 60 |

## Устаревшие блокировки

Принудительная остановка restic может оставить блокировку в репозитории. Сервер управления помечает блокировку, когда агент сообщает о возможной устаревшей блокировке или когда агент потерян во время задания. Задание на потерянном агенте завершается с причиной `agent_lost`.

Когда метке исполнилось 30 минут и в репозитории нет ожидающих и выполняющихся заданий, сервер управления ставит в очередь задание `unlock` (FR-SC-06, AC-SC-06). Это задание никогда не снимает блокировки работающей операции. Если позже в репозитории успешно завершилось задание, сервер управления не ставит `unlock`.

Только Администратор может снять все блокировки. Действие отправляет задание `unlock_all`. Для него нужно подтверждение: имя репозитория. Действие отклоняет репозиторий, в котором есть ожидающее или выполняющееся задание. Журнал аудита хранит событие `repository_unlock_all`.

## Отмена

Оператор может отменить задание (FR-SC-09).

- Задание в очереди завершается сразу с результатом `cancelled`.
- Для отправленного или выполняющегося задания сервер управления помечает задание и отправляет агенту сообщение об отмене. Очередь никогда не отправляет помеченное задание. Если агент поздно подтверждает помеченное задание, сервер управления снова отправляет сообщение об отмене. Помеченное задание, которое агент так и не подтвердил, завершается с результатом `cancelled`, когда истекает аренда. Если агент выполняющегося задания не на связи, сервер управления отвечает HTTP 409 `agent_offline`.
- Задание `unlock_all` может отменить только Администратор.
- Задание в конечном состоянии отменить нельзя.

## Отклонённые задания

Если сервер управления не может собрать задание, задание завершается с кодом причины:

| Причина | Значение |
|---|---|
| `compile_failed` | Профиль больше не компилируется для агента. |
| `agent_facts_invalid` | Сведения об агенте непригодны. |
| `step_missing` | В профиле больше нет шага этого задания. |
| `agent_revoked` | Агент отозван. |
| `plan_missing`, `plan_changed` | План удалён или перенесён на другой агент. |
| `profile_missing`, `repository_missing`, `repository_changed` | Объект задания удалён или изменён. |
| `secret_unavailable` | Секрет репозитория нельзя прочитать. |
| `signing_failed` | Сервер управления не смог подписать задание. |

## Роли

| Роль | Право |
|---|---|
| Администратор, Оператор | Запускать план и отменять задание. У плана может быть один ожидающий ручной запуск: второй запуск даёт HTTP 409 `already_queued`. |
| Администратор | Запускать `unlock_all`. |
| Наблюдатель | Читать задания. |

Приостановленная организация не отправляет заданий. Её агенты остаются на связи (AC-TN-03).

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/jobs` | Список заданий, сначала новые. Параметры `plan_id`, `repository_id`, `agent_id` и `status` фильтруют список. Параметры `cursor` и `limit` листают список. |
| `GET /api/v1/jobs/{id}` | Прочитать одно задание. |
| `POST /api/v1/jobs/{id}/cancel` | Отменить задание. |
| `POST /api/v1/plans/{id}/run` | Запустить план сейчас. |
| `POST /api/v1/repositories/{id}/unlock-all` | Снять все блокировки репозитория. Тело содержит `confirm` с именем репозитория. |

Задание другой организации даёт HTTP 404.
