---
title: Задания
description: Как очередь отправляет задания агентам, ограничивает их и повторяет.
---

Задание — один запуск плана или одна ручная операция. Сервер управления хранит задания в очереди в базе данных. Диспетчер очереди отправляет каждое задание агенту, который на связи, по уже открытому соединению.

## Состояния задания

| Состояние | Значение |
|---|---|
| В очереди (`queued`) | Задание в очереди. Сервер управления его не отправил. |
| Отправлено (`sent`) | Сервер управления отправил задание. Агент его не подтвердил. |
| Выполняется (`running`) | Агент подтвердил задание и выполняет его. |
| Успешно (`succeeded`) | Все шаги выполнены успешно. |
| Ошибка (`failed`) | Шаг завершился ошибкой, задание отменили или сервер управления его отклонил. Код результата и причина дают подробности. |
| Срок истёк (`expired`) | Задание ждало в очереди дольше окна приёма. Выполняющееся задание никогда не истекает. |
| Остановлено (`dead_letter`) | Репозиторий оставался заблокированным после последнего повтора. |

Задание в конечном состоянии больше не меняется.

## Доставка

Диспетчер собирает каждое задание в момент отправки: заново строит команды из сохранённого профиля плана и сведений об агенте. Если команды из профиля построить уже нельзя, задание завершается с причиной `compile_failed`. Сервер управления никогда не хранит готовую команду, чтобы отправить её позже.

Задание несёт только секреты своего репозитория. Сервер управления читает каждый секрет в момент отправки и пишет запись аудита `secret_delivered`. Запись не содержит значения секрета.

Сервер управления всегда передаёт `--retry-lock` с командой restic.

Сервер управления подписывает каждое задание. Агент проверяет подпись до выполнения задания.

## Время на подтверждение и повторная отправка

Отправив задание, сервер управления ждёт подтверждения от агента. По умолчанию это 60 секунд, наименьшее значение — 15 секунд. Если агент не подтвердил задание за это время, сервер управления отправляет задание снова. Он отправляет те же подписанные байты и не собирает задание заново, поэтому изменение профиля не меняет уже отправленное задание. Каждая отправка добавляет в журнал аудита запись `secret_delivered`. Если агент отвечает, что занят, сервер управления отправляет задание снова через 10 секунд; такой ответ не считается отправкой. Идентификатор задания каждый раз тот же. Агент помнит выполненные задания и не выполняет одно задание дважды.

Если сервер управления пять раз отправил задание без подтверждения, задание завершается с причиной `not_acknowledged`.

Если агент не на связи, задание остаётся в очереди. Для такого агента сервер управления не читает секреты.

## Исключительные операции

Некоторым операциям нужен весь репозиторий. Это `init`, `check`, `forget`, `prune`, `unlock` и `unlock_all`. Очередь называет их исключительными.

- Исключительное задание начинается, только когда в репозитории нет других заданий.
- Пока выполняется исключительное задание, другие задания в репозитории не начинаются.
- Очередь хранит порядок заданий. Задание, которое ждёт освобождения репозитория, не пропускает вперёд задания, поставленные после него. Поэтому очистка не будет бесконечно ждать за потоком новых резервных копий.

В одном репозитории одновременно могут идти несколько резервных копий. Наибольшее число задаёт лимит репозитория.

## Лимиты

Очередь применяет три лимита:

| Лимит | По умолчанию | Параметр |
|---|---|---|
| Заданий на одном агенте | 2 | `RESTICHUB_QUEUE_AGENT_LIMIT` |
| Резервных копий в одном репозитории | 4 | `RESTICHUB_QUEUE_REPOSITORY_LIMIT` |
| Заданий в одной организации | 100 | `RESTICHUB_QUEUE_GLOBAL_LIMIT` |

Те же значения можно задать в секции `[queue]` файла конфигурации ключами `agent_limit`, `repository_limit` и `global_limit`. Задание, которое не укладывается в лимит, ждёт в очереди.

## Ограничения по времени

У выполняющегося задания нет фиксированного предельного времени. Первая резервная копия большого диска может идти много часов. Пока restic продолжает работу, задание продолжается.

### Окно приёма

У задания в очереди есть окно приёма. У ручного задания окно — один час. У планового задания окно — 24 часа, а подпись задания никогда не действует дольше 23 часов. После этого времени агент отклоняет задание. Пока задание ждёт или отправлено, его карточка показывает конец окна как «Принять до». Выполняющееся задание не истекает.

### Тайм-аут простоя

Агент следит за ходом каждого шага. Шаг идёт, пока меняется число обработанных байт или файлов, меняется список текущих файлов или restic печатает новую строку текста. Повторная строка состояния не считается ходом.

Агент останавливает шаг, который не двигался дольше тайм-аута простоя. Остановка идёт в два этапа: сначала агент посылает мягкий сигнал, затем после паузы принудительно завершает все дочерние процессы. Задание завершается с причиной `stalled`.

| Шаг | Тайм-аут простоя по умолчанию |
|---|---|
| `backup`, `restore` и короткие шаги | 60 минут |
| `check`, `prune` | 6 часов, в том числе внутри задания копирования |

Профиль задаёт тайм-аут простоя для своих заданий. Параметр называется «Остановить без прогресса» и лежит в разделе «Ограничения» профиля. Значение — от 5 до 10080 минут. Шаги `check` и `prune` в таком задании ждут дольше: берётся большее из этого значения и 6 часов.

### Предельная длительность

Профиль задаёт предельную длительность. По умолчанию — 48 часов (2880 минут). Ноль отключает ограничение. Если задание идёт дольше, агент останавливает его, даже если работа продолжается. Задание завершается с причиной `max_duration_exceeded`. Значение — от 0 до 43200 минут. Карточка задания показывает ограничения выполняющегося задания.

### Переменные окружения

Оператор может изменить значения по умолчанию. Значения указываются в секундах.

| Переменная | Где | Действие |
|---|---|---|
| `RESTICHUB_JOB_STALL_TIMEOUT_SECS` | сервер управления | Тайм-аут простоя для нового профиля. От 300 до 604800. |
| `RESTICHUB_JOB_MAX_DURATION_SECS` | сервер управления | Предельная длительность для нового профиля. От 0 до 2592000. Ноль — без ограничения. |
| `RESTICHUB_JOB_STALL_TIMEOUT_SECS` | агент | Тайм-аут простоя задания, у которого он не задан, для всех шагов. От 60 до 604800. |
| `RESTICHUB_JOB_HARD_CEILING_SECS` | сервер управления | Время, после которого сервер управления завершает выполняющееся задание с ошибкой при любых ограничениях профиля. От 3600. По умолчанию — 31 день. |

Сервер управления игнорирует значение, которое не число или выходит за диапазон. Существующий профиль сохраняет свои значения.

### Потерянные задания

Сервер управления не отменяет выполняющееся задание из-за времени работы. Он завершает задание с причиной `agent_lost` в двух случаях:

- Агент не в сети, и сервер управления 30 минут не получал от него сообщений.
- Агент подключается снова и не называет задание в сообщении hello: он перезапустился и потерял задание.

Задание с предельной длительностью также завершается с причиной `timed_out`, если оно идёт больше предельной длительности на 10 минут, а агент не сообщил о завершении. Задание без предельной длительности завершается с той же причиной по жёсткому пределу. У заданий обслуживания (forget, prune, check) предельная длительность — 48 часов. В каждом из этих случаев сервер управления помечает блокировку репозитория как возможно устаревшую.

Более старый агент не знает тайм-аут простоя и не останавливает шаг, который завис. Такому агенту сервер управления отправляет предельную длительность профиля или фиксированное ограничение в 12 часов, если у профиля его нет. Карточка задания показывает для такого агента только предельную длительность.

## Повторы при блокировке

Restic завершается с кодом 11, когда другая операция держит блокировку репозитория. Сервер управления не отказывается от плана и ставит задание в очередь заново, с задержкой.

Сервер управления завершает задание, которое сообщило о блокировке, и ставит в очередь новое задание с новым идентификатором. Агент возвращает сохранённый результат для уже известного идентификатора, поэтому повтору нужен свой идентификатор. У нового задания тот же план и то же время запуска, а номер попытки на единицу больше. Первая задержка — 30 секунд. С каждым повтором задержка удваивается. Наибольшая задержка — один час. После пяти ответов о блокировке задание переходит в конечное состояние `dead_letter`, а сервер управления добавляет в журнал аудита запись `job_dead_letter`. На эту запись можно настроить оповещение.

| Параметр | По умолчанию |
|---|---|
| `RESTICHUB_QUEUE_LOCK_RETRY_LIMIT` | 5 |
| `RESTICHUB_QUEUE_LOCK_RETRY_BASE_SECS` | 30 |
| `RESTICHUB_QUEUE_LEASE_SECS` | 60 |

## Устаревшие блокировки

Если restic остановить принудительно, в репозитории может остаться блокировка. Сервер управления помечает блокировку, когда агент сообщает о возможной устаревшей блокировке или когда агент потерян во время задания. Задание на потерянном агенте завершается с причиной `agent_lost`. Выполняющееся задание, которое остаётся дольше предельной длительности и 10 минут запаса, завершается с причиной `timed_out`, и его блокировка тоже помечается. Агент сам останавливает зависший шаг и шаг, который превысил предельную длительность. После принудительной остановки он сообщает `possible_stale_lock`. Отправленное задание, которое агент не подтвердил вовремя, завершается с причиной `unacknowledged_expired`, и его блокировка тоже помечается.

Когда метке исполнилось 30 минут и в репозитории нет ожидающих и выполняющихся заданий, сервер управления ставит в очередь задание `unlock`. Это задание никогда не снимает блокировки работающей операции. Если позже в репозитории успешно завершилось задание, сервер управления не ставит `unlock`.

Только Администратор может снять все блокировки. Действие отправляет задание `unlock_all`. Для него нужно подтверждение: имя репозитория. Действие отклоняет репозиторий, в котором есть ожидающее или выполняющееся задание. Журнал аудита записывает событие `repository_unlock_all`.

## Отмена

Оператор может отменить задание.

- Задание в очереди завершается сразу с результатом `cancelled`.
- Для отправленного или выполняющегося задания сервер управления помечает задание и отправляет агенту сообщение об отмене. Очередь никогда не отправляет помеченное задание. Если агент поздно подтверждает помеченное задание, сервер управления снова отправляет сообщение об отмене. Помеченное задание, которое агент так и не подтвердил, завершается с результатом `cancelled`, когда истекает время на подтверждение. Если агент выполняющегося задания не на связи, сервер управления отвечает HTTP 409 `agent_offline`.
- Задание `unlock_all` может отменить только Администратор.
- Задание в конечном состоянии отменить нельзя.

## Отклонённые задания

Если сервер управления не может собрать задание, задание завершается с кодом причины:

| Причина | Значение |
|---|---|
| `compile_failed` | Команды из профиля для этого агента построить нельзя. |
| `agent_facts_invalid` | Сведения об агенте неверны. |
| `agent_capability_missing` | Агент слишком старый для шага. Он не знает поле, которое нужно шагу. |
| `forget_without_tags` | У шага политики хранения нет фильтра по тегам. Сервер управления такой шаг не отправляет. |
| `step_missing` | В профиле больше нет шага этого задания. |
| `agent_revoked` | Агент отозван. |
| `plan_missing`, `plan_changed` | План удалён или перенесён на другой агент. |
| `profile_missing`, `repository_missing`, `repository_changed` | Объект задания удалён или изменён. |
| `secret_unavailable` | Секрет репозитория нельзя прочитать. |
| `signing_failed` | Сервер управления не смог подписать задание. |

## Шаги, итоги и ход выполнения

Агент сообщает о каждом шаге задания типизированным результатом. Сервер управления хранит одну строку для каждого шага: статус, код завершения, время и код ошибки. Агент может отправить результат дважды: повторная запись не меняет сохранённую строку.

Шаг резервного копирования содержит также итоги restic: новые, изменённые и неизменённые файлы, данные, добавленные в репозиторий, обработанные файлы и байты, длительность и идентификатор снимка. Сервер управления хранит эти значения как есть, а веб-интерфейс показывает их без изменений. Шаги `check`, `forget`, `snapshots` и `stats` имеют свои типизированные итоги.

Пока шаг выполняется, агент отправляет ход выполнения: число файлов и байт, процент и файл, который обрабатывается сейчас. Сервер управления хранит только последний ход выполнения каждого задания. Карточка задания показывает его для задания в состоянии `sent` или `running` и удаляет, когда задание заканчивается. Пока задание может измениться, веб-интерфейс запрашивает его каждые две секунды.

## Журнал задания

Агент отправляет журнал задания частями. Перед отправкой он удаляет из журнала все секреты. Журнал одного задания занимает не более 1 МиБ. Сервер управления хранит каждую строку журнала отдельной записью. У строки есть номер, шаг, источник (`stdout`, `stderr` или `agent`) и уровень. Сервер управления определяет уровень по тексту строки: `error`, `warn` или `info`. Агент не отправляет время строки, поэтому сохранённое время — это время, когда сервер управления сохранил строку.

После перезапуска агент отправляет конец журнала повторно. Агент нумерует части отдельно для каждого источника. Сервер управления хранит номер части вместе со строкой. Он игнорирует часть, которую уже сохранил, в каком бы порядке части ни пришли. Поэтому повторно отправленный конец журнала не создаёт дубликатов.

Каждая строка считается как её текст, один перевод строки и 64 байта накладных расходов. Для каждого задания сервер управления сохраняет не больше 1 МиБ по такому счёту и не больше 100 000 строк, чтобы пустые строки не заполнили базу данных. Потом он перестаёт сохранять строки и помечает журнал как усечённый. Веб-интерфейс показывает примечание. Сервер управления удаляет из строки управляющие символы, кроме табуляции. Он также удаляет символы форматирования Unicode (категория Cf, например U+202E). Он обрезает строку до 8192 символов.

Завершённое задание принимает от агента записи шагов и журнала только в течение срока хранения журналов после своего завершения.

Хранилище журналов — отдельный компонент с интерфейсом `LogStore`. По умолчанию используется вариант `database`. Вариант `s3` запланирован на выпуск 1.0.

### Срок хранения журналов

Сервер управления удаляет строки журнала старше срока хранения. Очистка запускается каждый час. Задание, его шаги и итоги остаются: исчезает только текст журнала. Тогда карточка задания сообщает, что журнал удалён.

| Параметр | По умолчанию | Переменная |
|---|---|---|
| Дней хранения текста журнала | 30 | `RESTICHUB_LOG_RETENTION_DAYS` |

Файл конфигурации содержит то же значение как `log_retention_days`. Значение одинаково для всех организаций. Значение меньше 1 поднимается до 1. Значение больше 36500 останавливает запуск.

## Роли

| Роль | Право |
|---|---|
| Администратор, Оператор | Запускать план и отменять задание. У плана может быть один ожидающий ручной запуск: второй запуск даёт HTTP 409 `already_queued`. |
| Администратор | Запускать `unlock_all`. |
| Наблюдатель | Читать задания, их шаги и журналы. |

Приостановленная организация не отправляет заданий. Её агенты остаются на связи.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/jobs` | Список заданий, сначала новые. Параметры `plan_id`, `repository_id`, `agent_id` и `status` фильтруют список. Параметры `cursor` и `limit` листают список. |
| `GET /api/v1/jobs/{id}` | Прочитать одно задание с его шагами, итогами и, для выполняющегося задания, ходом выполнения. |
| `GET /api/v1/jobs/{id}/logs` | Прочитать страницу журнала. Параметр `after_seq` — номер последней строки, которая у вас есть, а `limit` — размер страницы (от 1 до 2000, по умолчанию 500). Берите `seq` последней строки как следующий `after_seq`. |
| `POST /api/v1/jobs/{id}/cancel` | Отменить задание. |
| `POST /api/v1/plans/{id}/run` | Запустить план сейчас. |
| `POST /api/v1/repositories/{id}/unlock-all` | Снять все блокировки репозитория. Тело содержит `confirm` с именем репозитория. |

Задание другой организации даёт HTTP 404.
