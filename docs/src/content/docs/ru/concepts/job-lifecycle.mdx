Задание — один запуск плана или одна ручная операция. Сервер управления хранит задания в очереди в базе данных. Диспетчер очереди отправляет каждое задание агенту, который на связи, по уже открытому соединению.

## Состояния задания

<Diagram name="job-lifecycle" label="Состояния задания и переходы между ними" />

Схема не показывает повторную отправку. Задание остаётся в `sent`, пока сервер управления отправляет его снова после истечения времени на подтверждение или после ответа «занят». Повтор при блокировке завершает задание как `failed` и ставит в очередь новое задание. После последней попытки задание переходит в `dead_letter`. «Отменено» и «Успешно» с предупреждениями — не отдельные сохраняемые состояния. Их показывает таблица ниже.

| Состояние в веб-интерфейсе | Хранимое состояние | Значение |
|---|---|---|
| <Ui k="jobs.status.queued" /> | `queued` | Задание в очереди. Сервер управления его не отправил. |
| <Ui k="jobs.status.sent" /> | `sent` | Сервер управления отправил задание. Агент его не подтвердил. |
| <Ui k="jobs.status.running" /> | `running` | Агент подтвердил задание и выполняет его. |
| <Ui k="jobs.status.succeeded" />, зелёным цветом | `succeeded` | Все шаги выполнены успешно. |
| <Ui k="jobs.status.succeeded_with_warnings" />, жёлтым цветом | `succeeded` | Все шаги выполнены, restic сообщил предупреждения. Список показывает метку с этим названием. Подсказка показывает «<Ui k="jobs.statusFull.succeeded_with_warnings" />». Код результата — `succeeded_with_warnings`. |
| <Ui k="jobs.status.failed" /> | `failed` | Шаг завершился ошибкой или сервер управления отклонил задание. Код результата и причина дают подробности. |
| <Ui k="jobs.status.cancelled" /> | `failed` | Оператор отменил задание, либо остановилась служба агента, либо перезапуск прервал резервное копирование. Код результата — `cancelled`. |

Задание в конечном состоянии больше не меняется.

## Доставка

Диспетчер собирает каждое задание в момент отправки: заново строит команды из сохранённого профиля плана и сведений об агенте. Если команды из профиля построить уже нельзя, задание завершается с причиной `compile_failed`. Сервер управления никогда не хранит готовую команду, чтобы отправить её позже.

Задание несёт только секреты своего репозитория. Сервер управления читает каждый секрет в момент отправки и пишет запись аудита `secret_delivered`. Запись не содержит значения секрета.

Сервер управления передаёт `--retry-lock` с шагом `backup`, `forget`, `prune` и `check`. Значение — 4 минуты. Остальные шаги идут без этого флага: `init`, `snapshots`, `ls`, `restore`, `unlock`, `unlock_all`, `stats`, `test_access` и `script`. Это меньше самого короткого тайм-аута простоя профиля. Поэтому restic сам завершает ожидание блокировки с кодом 11 раньше, чем агент остановит шаг как зависший. Затем сервер управления повторяет задание.

Сервер управления подписывает каждое задание. Агент проверяет подпись до выполнения задания.

## Время на подтверждение и повторная отправка

Отправив задание, сервер управления ждёт подтверждения от агента. По умолчанию это 60 секунд, наименьшее значение — 15 секунд. Если агент не подтвердил задание за это время, сервер управления отправляет задание снова. Он отправляет те же подписанные байты и не собирает задание заново, поэтому изменение профиля не меняет уже отправленное задание. Каждая отправка добавляет в журнал аудита запись `secret_delivered`. Если агент отвечает, что занят, сервер управления отправляет задание снова через 10 секунд; такой ответ не считается отправкой. Идентификатор задания каждый раз тот же. Агент помнит выполненные задания и не выполняет одно задание дважды.

Если сервер управления пять раз отправил задание без подтверждения, задание завершается с причиной `not_acknowledged`.

Если агент не на связи, задание остаётся в очереди. Для такого агента сервер управления не читает секреты.

## Исключительные операции

Некоторым операциям нужен весь репозиторий. Это `init`, `check`, `forget`, `prune`, `unlock` и `unlock_all`. Очередь называет их исключительными.

- Исключительное задание начинается, только когда в репозитории нет других заданий.
- Пока выполняется исключительное задание, другие задания в репозитории не начинаются.
- Очередь хранит порядок заданий. Задание, которое ждёт освобождения репозитория, не пропускает вперёд задания, поставленные после него. Поэтому очистка не будет бесконечно ждать за потоком новых резервных копий.

В одном репозитории одновременно могут идти несколько резервных копий. Наибольшее число задаёт лимит репозитория.

## Лимиты

Очередь применяет три лимита:

| Лимит | По умолчанию | Параметр |
|---|---|---|
| Заданий на одном агенте | 2 | `RESTICHUB_QUEUE_AGENT_LIMIT` |
| Резервных копий в одном репозитории | 4 | `RESTICHUB_QUEUE_REPOSITORY_LIMIT` |
| Заданий в одной организации | 100 | `RESTICHUB_QUEUE_GLOBAL_LIMIT` |

Те же значения можно задать в секции `[queue]` файла конфигурации ключами `agent_limit`, `repository_limit` и `global_limit`. Задание, которое не укладывается в лимит, ждёт в очереди.

## Ограничения по времени

У выполняющегося задания нет фиксированного предельного времени. Первая резервная копия большого диска может идти много часов. Пока restic продолжает работу, задание продолжается.

### Окно приёма

У задания в очереди есть окно приёма. У ручного задания окно — один час. У планового задания окно — 24 часа, а подпись задания никогда не действует дольше 23 часов. После этого времени агент отклоняет задание. Пока задание ждёт или отправлено, его карточка показывает конец окна как «Принять до». Выполняющееся задание не истекает.

### Тайм-аут простоя

Агент следит за ходом каждого шага. Шаг идёт, пока меняется число обработанных байт или файлов, меняется общее число байт или файлов, меняется список текущих файлов или restic печатает новую строку текста. Повторная строка состояния не считается ходом. На шаге `restore` ходом считается и число пропущенных файлов или байт: restic читает и сверяет файлы, которые уже есть в целевой папке, и считает их там. На шаге `backup` или `restore` строка в стандартном потоке ошибок ходом не считается. Там restic сообщает о предупреждении по одному файлу или о повторе запроса к недоступному репозиторию. Такая строка о работе ничего не говорит. Остальные шаги не печатают сообщений о ходе, пока работают, поэтому строка в любом из двух потоков считается ходом.

Шаг `restore` с проверкой файлов печатает последнюю строку состояния и сводку до проверки. Во время проверки он не печатает ничего, поэтому агент не видит, какие файлы читает restic. Агент даёт этой фазе 24 часа от строки сводки или большее значение тайм-аута простоя шага. Проверку, которая идёт дольше, он останавливает как зависшую, в том числе исправную. Остановить задание может и отмена. Если проверке нужно больше 24 часов, увеличьте переменную `RESTICHUB_JOB_STALL_TIMEOUT_SECS` на агенте, не более 7 суток. Проверка, которая идёт неделю и дольше, — это задача планирования: разделите восстановление или откажитесь от проверки.

Шаг `backup` с ограничением отдачи не увеличивает число байт, пока restic выгружает пакет: когда слоты выгрузки заполнены, restic перестаёт читать файлы. Поэтому агент поднимает тайм-аут простоя такого шага минимум до удвоенного времени выгрузки пакета при этом ограничении. Пакет содержит не больше 128 МиБ: это наибольший размер, который пишет restic. При 50 КиБ/с поднятое значение — 87 минут, при 500 КиБ/с — 9 минут. Больший тайм-аут простоя задания агент сохраняет. Карточка задания показывает тайм-аут простоя профиля, он меньше поднятого значения.

Агент останавливает шаг, который не двигался дольше тайм-аута простоя. Остановка идёт в два этапа: сначала агент посылает мягкий сигнал, затем после паузы принудительно завершает все дочерние процессы. Задание завершается с причиной `stalled`.

| Шаг | Тайм-аут простоя по умолчанию |
|---|---|
| `backup`, `restore` и короткие шаги | 60 минут |
| `check`, `prune` | 6 часов, в том числе внутри задания копирования |
| Фаза проверки у `restore` | 24 часа от строки сводки |
| `backup` с ограничением отдачи | Не меньше удвоенного времени выгрузки пакета в 128 МиБ при этом ограничении |

Профиль задаёт тайм-аут простоя для своих заданий. Параметр называется «Остановить, если нет прогресса, минут» и лежит в разделе «Лимиты выполнения» профиля. Значение — от 5 до 10080 минут. Шаги `check` и `prune` в таком задании ждут дольше: берётся большее из этого значения и 6 часов. Задание `backup` с ограничением отдачи ждёт большее из этого значения и поднятого значения выше.

У задания `restore` нет профиля, поэтому в него не попадают ни тайм-аут простоя, ни предельная длительность. Тайм-аут простоя агент берёт из переменной `RESTICHUB_JOB_STALL_TIMEOUT_SECS` или из значения по умолчанию для `restore`. Карточка задания говорит, что действует значение по умолчанию на агенте, без числа. Значение больше 24 часов даёт фазе проверки более широкое окно.

### Предельная длительность

Профиль задаёт предельную длительность. Параметр называется «Максимальная длительность, часов» и лежит в разделе «Лимиты выполнения» профиля. По умолчанию — 48 часов. Ноль отключает ограничение. Если задание идёт дольше, агент останавливает его, даже если работа продолжается. Задание завершается с причиной `max_duration_exceeded`. Значение — от 0 до 720 часов. Карточка задания показывает ограничения выполняющегося задания (см. [Просмотр и отмена заданий](/restichub/ru/guides/jobs/)).

### Переменные окружения

Оператор может изменить значения по умолчанию. Значения указываются в секундах. Страница [Переменные окружения](/restichub/ru/reference/environment-variables/) перечисляет все переменные.

| Переменная | Где | Действие |
|---|---|---|
| `RESTICHUB_JOB_STALL_TIMEOUT_SECS` | сервер управления | Тайм-аут простоя для нового профиля. От 300 до 604800. |
| `RESTICHUB_JOB_MAX_DURATION_SECS` | сервер управления | Предельная длительность для нового профиля. От 0 до 2592000. Ноль — без ограничения. |
| `RESTICHUB_JOB_STALL_TIMEOUT_SECS` | агент | Тайм-аут простоя задания, у которого он не задан, для всех шагов. От 300 до 604800. Фаза проверки у `restore` ждёт большее из этого значения и 24 часов. |
| `RESTICHUB_JOB_HARD_CEILING_SECS` | сервер управления | Время, после которого сервер управления завершает выполняющееся задание с ошибкой при любых ограничениях профиля. По умолчанию — 31 день (2678400). Значение меньше 3600 становится равным 3600. |

Для тайм-аута простоя и предельной длительности сервер управления игнорирует значение, которое не число или выходит за диапазон. Он округляет значение вверх до целых минут. Существующий профиль сохраняет свои значения.

### Потерянные задания

Сервер управления не отменяет выполняющееся задание из-за времени работы. Он завершает задание с причиной `agent_lost` в двух случаях. В обоих случаях задание создаёт оповещение о задании, потому что сервер управления не отличает сбой агента от потерянного хоста:

- Агент не в сети, и сервер управления 30 минут не получал от него сообщений.
- Агент подключается снова и не называет задание в сообщении hello: он перезапустился и потерял задание.

Задание с предельной длительностью также завершается с причиной `timed_out`, если оно идёт больше предельной длительности на 10 минут, а агент не сообщил о завершении. Задание без предельной длительности завершается с той же причиной по жёсткому пределу. У заданий обслуживания (forget, prune, check) предельная длительность — 48 часов. В каждом из этих случаев сервер управления помечает блокировку репозитория как возможно устаревшую.

### Прерванные задания

Когда служба агента останавливается, агент останавливает выполняющееся задание и сообщает, что оно отменено. Перезапуск может прервать задание со скриптом. Агент не запускает такое задание снова, потому что скрипт не должен выполняться дважды. Агент отвечает с причиной `interrupted`.

Сервер управления завершает прерванное резервное копирование как отменённое и сохраняет причину `interrupted`. Задание не создаёт оповещение о задании, потому что пропущенную копию показывает оповещение RPO. Любое другое прерванное задание (проверка, forget, prune, init, проверка доступа и восстановление) завершается с ошибкой и создаёт оповещение о задании, потому что другое оповещение его не покрывает. Карточка задания показывает причину отменённого задания, если она есть.

Более старый агент не знает тайм-аут простоя и не останавливает шаг, который завис. Такому агенту сервер управления отправляет предельную длительность профиля или фиксированное ограничение в 12 часов, если у профиля его нет. Карточка задания показывает для такого агента только предельную длительность.

## Повторы при блокировке

Restic завершается с кодом 11, когда другая операция держит блокировку репозитория. Сервер управления не отказывается от плана и ставит задание в очередь заново, с задержкой.

Сервер управления завершает задание, которое сообщило о блокировке, и ставит в очередь новое задание с новым идентификатором. Агент возвращает сохранённый результат для уже известного идентификатора, поэтому повтору нужен свой идентификатор. У нового задания тот же план и то же время запуска, а номер попытки на единицу больше. Первая задержка — 30 секунд. С каждым повтором задержка удваивается. Наибольшая задержка — один час. После пяти ответов о блокировке задание переходит в конечное состояние `dead_letter`, а сервер управления добавляет в журнал аудита запись `job_dead_letter`. На эту запись можно настроить оповещение.

| Параметр | По умолчанию |
|---|---|
| `RESTICHUB_QUEUE_LOCK_RETRY_LIMIT` | 5 |
| `RESTICHUB_QUEUE_LOCK_RETRY_BASE_SECS` | 30 |
| `RESTICHUB_QUEUE_LEASE_SECS` | 60 |

## Устаревшие блокировки

Если restic остановить принудительно, в репозитории может остаться блокировка. Сервер управления помечает блокировку, когда агент сообщает о возможной устаревшей блокировке или когда агент потерян во время задания. Задание на потерянном агенте завершается с причиной `agent_lost`. Сервер управления считает агента потерянным, только если читал подключённых агентов без перерыва две минуты. Поэтому после своего запуска и после отказа базы данных агент имеет это время, чтобы подключиться снова. Выполняющееся задание, которое остаётся дольше предельной длительности и 10 минут запаса, завершается с причиной `timed_out`, и его блокировка тоже помечается. Отзыв хоста завершает его выполняющееся задание с причиной `agent_revoked` и тоже помечает блокировку. Если хост обслуживания репозитория отозван, сервер управления запускает `unlock` на другом активном хосте. У локального репозитория другого хоста нет: метка остаётся, и панель показывает её. Агент сам останавливает зависший шаг и шаг, который превысил предельную длительность. После принудительной остановки он сообщает `possible_stale_lock`. Отправленное задание, которое агент не подтвердил вовремя, завершается с причиной `unacknowledged_expired`, и его блокировка тоже помечается.

Когда метке исполнилось 30 минут и в репозитории нет ожидающих и выполняющихся заданий, сервер управления ставит в очередь задание `unlock`. Это задание никогда не снимает блокировки работающей операции. Если после метки успешно завершилось задание, которое берёт исключительную блокировку restic или снимает блокировки, сервер управления не ставит `unlock`. Резервная копия работает рядом с блокировкой, поэтому её успех не доказывает, что блокировка снята.

Только Администратор может снять все блокировки. Действие отправляет задание `unlock_all`. Для него нужно подтверждение: имя репозитория. Действие отклоняет репозиторий, в котором есть ожидающее или выполняющееся задание. Журнал аудита записывает событие `repository_unlock_all`.

## Шаги, итоги и ход выполнения

Агент сообщает о каждом шаге задания типизированным результатом. Сервер управления хранит одну строку для каждого шага: статус, код завершения, время и код ошибки. Агент может отправить результат дважды: повторная запись не меняет сохранённую строку. Если сервер управления не может сохранить результат шага или результат задания, потому что база данных недоступна, он закрывает поток агента. Агент подключается снова и отправляет результаты заданий, которые хранит его журнал. Журнал не хранит результат шага выполняющегося задания, поэтому такой результат шага повторно не приходит.

Шаг резервного копирования содержит также итоги restic: новые, изменённые и неизменённые файлы, данные, добавленные в репозиторий, обработанные файлы и байты, длительность и идентификатор снимка. Сервер управления хранит эти значения как есть, а веб-интерфейс показывает их без изменений. Шаги `check`, `forget`, `snapshots` и `stats` имеют свои типизированные итоги.

Пока шаг выполняется, агент отправляет ход выполнения: число файлов и байт, процент и файл, который обрабатывается сейчас. Сервер управления хранит только последний ход выполнения каждого задания. Карточка задания показывает его для задания в состоянии `sent` или `running` и удаляет, когда задание заканчивается. Пока задание может измениться, веб-интерфейс запрашивает его каждые две секунды.

## Журнал задания

Агент отправляет журнал задания частями. Перед отправкой он удаляет из журнала все секреты. Журнал одного задания занимает не более 1 МиБ. Сервер управления хранит каждую строку журнала отдельной записью. У строки есть номер, шаг, источник (`stdout`, `stderr` или `agent`) и уровень. Сервер управления определяет уровень по тексту строки: `error`, `warn` или `info`. Агент не отправляет время строки, поэтому сохранённое время — это время, когда сервер управления сохранил строку.

Агент хранит каждую часть журнала в защищённом файле очереди на своём диске, пока сервер управления не подтвердит, что сохранил её. После потери соединения или перезапуска агент по порядку отправляет все неподтверждённые части. Агент нумерует части отдельно для каждого источника. Сервер управления хранит номер части вместе со строкой. Он игнорирует часть, которую уже сохранил, поэтому повторная часть не создаёт дубликатов строк. Подтверждённые части агент удаляет со своего диска.

Очередь всех заданий на одном узле занимает не более 64 МиБ. Чтобы изменить предел, задайте на агенте `RESTICHUB_LOG_SPOOL_MAX_BYTES`. Если сервер управления недоступен так долго, что очередь заполнена, агент отбрасывает самые новые строки. Затем он добавляет в журнал одну строку, например `120 log lines were dropped because the agent log spool was full or not writable`. Остановившееся соединение не задерживает отмену задания. Сервер управления подтверждает части только агенту, который это поддерживает. Старый агент или старый сервер управления работают как раньше: после перезапуска агент повторно отправляет последние 64 КиБ журнала.

Каждая строка считается как её текст, один перевод строки и 64 байта накладных расходов. Для каждого задания сервер управления сохраняет не больше 1 МиБ по такому счёту и не больше 100 000 строк. Так пустые строки не заполнят базу данных. Потом он перестаёт сохранять строки и помечает журнал как усечённый. Веб-интерфейс показывает примечание. Сервер управления удаляет из строки управляющие символы, кроме табуляции. Он также удаляет символы форматирования Unicode (категория Cf, например U+202E). Он обрезает строку до 8192 символов.

Завершённое задание принимает от агента записи шагов и журнала только в течение срока хранения журналов после своего завершения.

Хранилище журналов — отдельный компонент с интерфейсом `LogStore`. По умолчанию используется вариант `database`. Вариант `s3` запланирован на выпуск 1.0.

### Срок хранения журналов

Сервер управления удаляет строки журнала старше срока хранения. Очистка запускается каждый час. Задание, его шаги и итоги остаются: исчезает только текст журнала. Тогда карточка задания сообщает, что журнал удалён.

| Параметр | По умолчанию | Переменная |
|---|---|---|
| Дней хранения текста журнала | 30 | `RESTICHUB_LOG_RETENTION_DAYS` |

Файл конфигурации содержит то же значение как `log_retention_days`. Значение одинаково для всех организаций, а сервер управления считает срок только по возрасту строк. Ограничение по объёму и свой срок для каждой организации запланированы на выпуск 1.0. Значение меньше 1 поднимается до 1. Значение больше 36500 останавливает запуск.

## Роли

| Роль | Право |
|---|---|
| Администратор, Оператор | Запускать план и отменять задание. У плана может быть один ожидающий ручной запуск: второй запуск даёт HTTP 409 `already_queued`. |
| Администратор | Запускать `unlock_all`. |
| Наблюдатель | Читать задания, их шаги и журналы. |

Приостановленная организация не отправляет заданий. Её агенты остаются на связи.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/jobs` | Список заданий, сначала новые. Параметры `plan_id`, `repository_id`, `agent_id` и `kind` фильтруют список, каждый принимает список через запятую, не больше 50 значений. Параметр `status` фильтрует по одному статусу. Параметр `group` выбирает вкладку состояния: `running`, `failed` (без отменённых заданий), `succeeded` (без заданий с предупреждениями) или `succeeded_with_warnings`. Параметр `q` ищет часть имени плана, хоста или репозитория, не больше 200 символов. Параметры `from` и `to` (RFC 3339) ограничивают время создания, значение `to` не может быть раньше `from`. Параметры `sort` (`created_at`, `started_at`, `finished_at`, `duration`, `status`, `plan`, `host`) и `order` (`asc`, `desc`) задают порядок. При сортировке по `duration` незавершённое задание стоит в конце. Параметры `cursor` и `limit` листают список в порядке по умолчанию, параметр `offset` (от 0 до 10000) читает страницу по номеру. Поле `total` содержит число заданий, которые подходят под фильтры, но не больше 10000. Если подходит больше заданий, поле `total_capped` равно `true`. Поле `counts` содержит число всех заданий (`all`) и заданий каждой вкладки состояния с остальными фильтрами. Параметры `status` и `group` его не меняют. |
| `GET /api/v1/jobs/{id}` | Прочитать одно задание с его шагами, итогами и, для выполняющегося задания, ходом выполнения. |
| `GET /api/v1/jobs/{id}/logs` | Прочитать страницу журнала. Параметр `after_seq` — номер последней строки, которая у вас есть, а `limit` — размер страницы (от 1 до 2000, по умолчанию 500). Берите `seq` последней строки как следующий `after_seq`. |
| `POST /api/v1/jobs/{id}/cancel` | Отменить задание. |
| `POST /api/v1/plans/{id}/run` | Запустить план сейчас. |
| `POST /api/v1/repositories/{id}/unlock-all` | Снять все блокировки репозитория. Тело содержит `confirm` с именем репозитория. |

Задание другой организации даёт HTTP 404.
