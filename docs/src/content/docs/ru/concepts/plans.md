---
title: Планы
description: Назначение профиля на хост по расписанию.
---

План назначает один профиль на один агент по расписанию. Расписание хранит сервер управления, он же создаёт задания. Агент не хранит расписание.

## Поля плана

| Поле | Значение |
|---|---|
| Имя | Имя плана. Любой текст длиной от 1 до 100 символов. Уникально в организации, регистр букв не важен. Пока вы не ввели имя, новый план получает имя `<хост> | <профиль>`. |
| Профиль | Описание резервного копирования, из которого сервер управления собирает каждое задание. В поле видны репозиторий каждого профиля и тип хранилища. Для локального репозитория видно также хост репозитория. Поиск находит профиль по имени профиля или репозитория. |
| Хост | Агент, который выполняет план. |
| Выражение cron | Пять полей: минута, час, день месяца, месяц, день недели. |
| Часовой пояс | Имя IANA, например `Europe/Berlin`. |
| Пропущенные запуски | Правило для момента запуска, который сервер управления пропустил. |
| Запускать по расписанию | Переключатель в заголовке раздела «Расписание». Когда он выключен, планировщик не создаёт заданий плана, а рядом с именем плана стоит плашка «Отключён». Кнопка «Запустить сейчас» по-прежнему запускает задание. Оповещения о пропущенной копии и о точке восстановления молчат. |

Профиль и агент принадлежат одной организации. Перед записью плана сервер управления проверяет, что сохранённый профиль можно собрать для операционной системы агента. Если в профиле нет пути для этой системы, план не сохраняется.

## Локальный репозиторий

Путь локального репозитория есть только на хосте репозитория. Поэтому план профиля, который пишет в локальный репозиторий, выполняется только на хосте репозитория. Страница плана предлагает только этот хост и выбирает его при выборе профиля. Хост сохранённого плана страница сама не меняет. Если сохранённый план выполняется на другом хосте, поле «Хост» показывает ошибку, пока вы не выберете хост репозитория. Другой хост сервер управления отклоняет с причиной `not_repository_host` в поле «Хост». Сервер управления также не переводит профиль на локальный репозиторий, пока план профиля выполняется на другом хосте. См. [Локальный репозиторий](/restichub/ru/getting-started/add-a-repository/#локальный-репозиторий).

## Расписание

Сервер управления рассчитывает каждый момент запуска из выражения cron и часового пояса. Задание хранит план и момент запуска. На каждый момент запуска создаётся одно задание. Пара «план, момент запуска» уникальна, поэтому два экземпляра сервера управления не создадут два задания на один момент.

При переходе на летнее время и обратно действуют такие правила:

- Если запуск назначен на фиксированное время, которого не существует из-за перевода часов вперёд, он выполняется один раз, сразу после перевода.
- Если запуск назначен на фиксированное время, которое повторяется из-за перевода часов назад, он выполняется один раз, при первом наступлении этого времени.
- Запуск по интервалу, например `0 * * * *` или `*/15`, не привязан к показаниям часов. Он выполняется в обе половины повторяющегося часа.

## Пропущенные запуски

Момент запуска считается пропущенным, если сервер управления не создал для него задание, например из-за простоя. Если опоздание укладывается в короткое допустимое окно, запуск считается своевременным и выполняется всегда. Правило пропущенных запусков применяется только к более старым моментам. Что произойдёт, определяет правило плана:

| Правило | Результат |
|---|---|
| Запускать каждый пропущенный | Одно задание на каждый более старый пропущенный момент. За один проход обрабатываются последние 100 моментов запуска. |
| Запускать только последний пропущенный | Одно задание на последний более старый пропущенный момент. |
| Пропускать пропущенные запуски | Заданий для более старых пропущенных моментов нет. |

У планового задания есть срок годности: 24 часа после момента запуска. Если задание истекло бы сразу после создания, сервер управления его не создаёт. Просроченное задание переходит в состояние `expired`.

Приостановленная организация не создаёт заданий. План с отозванным агентом тоже не создаёт заданий.

## Доставка

Плановое задание создаётся в состоянии `queued`. Очередь отправляет его агенту, который на связи. Страница [Задания](/restichub/ru/concepts/job-lifecycle/) описывает очередь, лимиты и повторы. При удалении плана его задания из очереди завершаются с результатом `cancelled`.

## Запуск вручную

Действие «Запустить сейчас» сразу ставит в очередь одно задание плана. К нему применяются те же правила, что и к плановому заданию. Отключённый план тоже можно запустить вручную. Перед постановкой в очередь сервер управления проверяет, что профиль можно собрать для этого агента.

## Роли

| Роль | Право |
|---|---|
| Администратор, Оператор | Создавать, изменять, удалять и запускать план. |
| Наблюдатель | Читать план и предпросматривать расписание. |

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/plans` | Список планов. Параметры `cursor` и `limit` листают список. |
| `POST /api/v1/plans` | Создать план. |
| `GET /api/v1/plans/{id}` | Прочитать один план. |
| `PATCH /api/v1/plans/{id}` | Изменить план. |
| `DELETE /api/v1/plans/{id}` | Удалить план. |
| `POST /api/v1/plans/{id}/run` | Сразу поставить в очередь одно задание плана. Ответ содержит задание. |
| `GET /api/v1/plans/{id}/next-runs?count=5` | Следующие моменты запуска в UTC. |
| `POST /api/v1/plans/preview` | Следующие моменты запуска для несохранённого расписания, в UTC. Тело содержит `cron`, `time_zone` и `count`. |

План другой организации даёт HTTP 404. Платформенная организация получает на любую операцию с планом ответ HTTP 403.
