The Restore screen lists the snapshots of a repository, shows the files of a snapshot and restores them. An Operator or an Admin can use it. A Viewer cannot.

The data of a restore goes from the repository to the target agent. It does not go through the control plane. The target agent gets the secrets of this repository for the restore job only. Each delivery writes the audit record `secret_delivered`. The start of a restore writes the audit record `restore_start`. The record names the repository, the snapshot, the target agent and the target path. A snapshot list or a tree page that starts a job writes the audit record `browse_start`. It names the repository and the agent that reads it, because that agent gets the repository secrets.

## Requirements

- The repository must be initialized.
- The agent that you select must be online.
- The agent must announce the capability `restore-v1`. This capability is in the agent packages that include the Restore screen. An agent without it can list snapshots, but the control plane refuses the file tree and the restore with the reason `agent_capability_missing`. Update the agent package to fix this.
- A repository with a local path accepts its repository host only. The data stays on that host, and the restore writes to that host.
- The target path must lie inside a restore root of the agent (see [Restore roots](#restore-roots)).

## List the snapshots

1. Open **Restore**.
2. Select a repository in the page header. An agent runs `restic snapshots` once for the whole repository, and the screen shows all snapshots. If the control plane already holds a stored list, the screen shows it with its age.
3. Narrow the list with the search field and the filters above the list. The filters apply at once, on the loaded list. There is no search button.
   - **Search by path**: type a part of a path. A snapshot matches when any of its backup paths contains the text. The search ignores case.
   - **Host** and **Tag**: select one or more values. The menus list the values that the loaded snapshots hold, with the number of snapshots for each value. A tag that comes from a profile shows the name of the profile.
   - **Period**: select 24 hours, 7 days, 30 days, 90 days or all time. **Custom range…** takes two dates, and the range includes both days.
4. Each filter that you set shows as a chip. Click the cross on a chip to remove it. Click **Reset** to remove all filters.
5. Click the refresh button to run the list job again and read the current snapshots from the repository. The text next to it shows the age of the list.

The list shows a heading for each day and the size of each snapshot on the right. Several values of one filter match any of them. Different filters must all match. For example, the host `nas` or `ws`, with the tag `daily`, shows the snapshots of either host that carry the tag `daily`.

The address of the page keeps the repository and the filters. On a snapshot page, the breadcrumbs `<organization> / Restore / <repository> / Snapshot <id>` return to the same view. The screen has an empty state for each case: no repository, no snapshots in the repository, and no snapshot that matches the filters.

The API keeps its filter parameters. The control plane applies the date range, and restic applies the host, the tag and the path. The screen filters the loaded list by the same rules. The result agrees with `restic snapshots --json` for the same filters. When a repository holds more snapshots than a result can carry, the screen shows a warning and keeps the newest snapshots.

## Browse a snapshot

Select a snapshot to open its page. The page shows the snapshot identifier, time, host, paths and tags, and the file tree. Select the repository in the breadcrumbs to return to the list with the same filters. A folder, a link and each type of file have their own icon. A link shows its target and has no size. The tree scrolls inside a box, and the footer under it shows the selected paths. The screen shows one directory at a time. The agent reads the directory and returns a page of at most 1000 entries. Select **Load more** to read the next page. A directory with one million files shows its first page in less than 5 seconds.

The control plane keeps a page for 10 minutes. If you open the same directory again in that time, the screen shows the stored page and no job runs. A request that is the same as a job that still waits or runs gets that job. The control plane keeps a snapshot list for one hour. The Jobs list does not show the browse jobs.

One person can send 60 list and page requests in one minute. Each control plane instance counts this limit on its own. One agent holds at most 8 waiting browse jobs. A further request gives HTTP 429 `rate_limited`. The agent runs at most two browse jobs at the same time, and they never make a backup wait.

## Restore files

<Screen name="restore-snapshot" alt="The page of a snapshot with the tree of files and the button Restore" />

1. Select the files and directories that you need in the tree. If you select nothing, the restore uses the whole snapshot.
2. Click **Restore…**.
3. Select the target host ("Target host"). The default is the host of the snapshot when that host is active. Otherwise it is the maintenance host of the repository.
4. Check the target path. The screen suggests a new folder in the first restore root of the agent, for example `/var/lib/restichub-restore/a1b2c3d4`. The path must be absolute and must lie inside a restore root. On a Windows host, the path has the Windows format, for example `C:\ProgramData\ResticHub-Restore\a1b2c3d4`. The button at the end of the field returns the suggested path. If the agent has more than one restore root, click a root below the field to use it.
5. If you selected no path, you can enter paths to exclude. Use restic patterns, one pattern on each line.
6. Select what to do with a file that exists in the target. For "Replace every file", the screen shows a warning.
7. Read the summary at the right side of the dialog. In a narrow window, the summary is below the fields.
8. Click **Start restore**. The screen opens the job.

<Screen name="restore-dialog" alt="The restore dialog with the target host, the target path and the restore roots" />

The job detail shows the block "Restore parameters". The block names the snapshot, the target host and path, the paths, the overwrite mode, and the verify and dry run settings. The detail also shows the progress while the restore runs. After it ends, the detail shows how many files and bytes the agent restored and how many it skipped.

| Option | Meaning |
|---|---|
| "Existing files": "Replace every file" (`always`) | Replace each file that exists. |
| "Existing files": "Replace a file that differs" (`if-changed`) | Replace a file whose content differs. |
| "Existing files": "Replace a file that is older than the snapshot" (`if-newer`) | Replace a file that is older than the copy in the snapshot. |
| "Existing files": "Keep every existing file" (`never`) | Keep each file that exists. |
| "Dry run" | Check the restore. The agent writes no file and changes no file. |
| "Verify after the restore" | After the restore, the agent reads the restored files again and compares them with the snapshot. You cannot use it with a dry run, because a dry run writes no file. |

restic does not accept an include list and an exclude list in one restore. The screen restores the files that you select, and the API refuses a request that has both lists.

The screen escapes the characters `*`, `?` and `[` in a path that you select, so the path matches itself only. A snapshot is selected by its identifier. The screen and the API do not accept `latest`, because it can change between two reads.

## Restore roots

The agent runs as root on Linux and as LocalSystem on Windows. It restores only below a *restore root*. Only root or Administrators set the roots on the host. The control plane and the jobs cannot change them.

| System | Default root |
|---|---|
| Linux | `/var/lib/restichub-restore` |
| Windows | `C:\ProgramData\ResticHub-Restore` |

`install-service` creates the default root with access for the service account only. The agent reports its roots to the control plane. The screen suggests the first root, and the control plane refuses a target outside the roots with HTTP 409 `restore_target_denied`. The agent checks the target again and has the last word. It rejects the job with the reason `restore_target_denied`.

To add a root, write one absolute path on each line of the file `/etc/restichub-agent-restore-roots.txt` (Windows: `C:\ProgramData\ResticHub\Agent-restore-roots.txt`). A line that starts with `#` is a comment. On Linux the agent ignores a line with a quotation mark, a backslash, `%`, a space or a control character. The agent logs a warning for such a line and for a line that is not an absolute path. `install-service` refuses these lines and names the line number. Only root or Administrators can own and write the file. The agent ignores a file that another account can change. Create each root directory, then run `restichub-agent install-service` again. The command adds the roots to `ReadWritePaths` of the systemd unit. Without this step, systemd keeps the root read-only and the restore fails. On Linux the agent writes a warning to the log at each start for a root that the installed unit cannot write.

Local repositories on Linux have their own roots file, `/etc/restichub-agent-repository-roots.txt`, with the same rules. A repository root is not a restore root. A restore never writes into a repository root, and `install-service` refuses a restore root and a repository root when one holds the other. The restore root `/` stays allowed. See [A local repository on Linux](/restichub/getting-started/add-a-repository/#a-local-repository-on-linux).

A root must be writable only by root or Administrators. The root and each existing parent directory must belong to root or Administrators. No group or other account may write there. The agent ignores a root that does not follow this rule and logs a warning, and `install-service` refuses it. Such an account could replace a directory with a link and lead a restore out of the root.

A root of `/` allows a restore to any other directory, for example `/srv/data`. A file of the agent, a parent of one and a path inside one stay refused. The target `/` is not possible, because it holds the files of the agent. Set the root `/` only when you want this. The screen shows a warning for a system path such as `/etc`. The root `/` does not make `/home`, `/root` and `/run/user` writable, because the unit sets `ProtectHome=read-only`. A restore root `/home` or `/root` does not change this, because systemd keeps these directories read-only. Thus the agent ignores such a root and logs a warning, and `install-service` refuses it and names the line number. Use a directory below it that root owns. Also an in-place restore below `/home` or `/root` is not possible. Restore to another root, for example the default root, and copy the files to their place.

The agent always refuses a target that is, holds or lies inside its own files. These are the configuration directory, the cache directory, and the directory of the agent and restic binaries. It follows symbolic links first. A root of `/` does not change this rule.

On Windows, right before restic starts, the agent also looks at the paths that the restore writes. It lists the snapshot and checks each selected file and folder in the target, and each parent folder of it inside the target. A symbolic link or a junction on such a path must lead to a place inside the target. A file on such a path must have no other name (hard link). If not, the restore step fails and names the path. The reason is that restic on Windows writes a file through a file link. An earlier restore or a local user can leave such a link. A link on another path, for example in a folder that the restore does not select, does not stop the restore. Remove the link, or restore into an empty directory. A dry run and a restore into an empty or new directory skip this check. The check obeys the cancel and the time limit of the step. A restore that writes more than 1,000,000 entries into a directory that is not empty fails. Then narrow the includes or restore into an empty directory. Linux needs no such check: restic on Linux replaces a link with the file or the folder of the snapshot.

### The default root of an earlier version

An earlier agent for Windows used `C:\ProgramData\ResticHub\Restore` as the default root. That directory lies in the tree of the agent, where the agent sets the access of each directory itself. The agent no longer uses it as a default root. It does not move or change the data in it. A restore to that directory fails with the reason `restore_target_denied`, until you add the root again. Restore to the new default root, or write the old path on one line of the file `C:\ProgramData\ResticHub\Agent-restore-roots.txt`.

## API

| Method and path | Role | Use |
|---|---|---|
| `POST /api/v1/repositories/{id}/snapshots` | Operator | Starts a job that lists the snapshots. |
| `GET /api/v1/repositories/{id}/snapshots` | Viewer | Reads the list of a job (`job`), or the newest stored list. The parameters `from` and `to` filter by date. |
| `POST /api/v1/repositories/{id}/ls` | Operator | Starts a job that lists one directory of a snapshot. A stored page answers with HTTP 200. |
| `GET /api/v1/repositories/{id}/ls` | Operator | Reads the page of a job (`job`). |
| `POST /api/v1/repositories/{id}/restore` | Operator | Starts a restore and returns the job. |

A restore and a tree page need a snapshot identifier of 8 to 64 lower-case hexadecimal characters. A restore with `dry_run` and `verify` together gives HTTP 400. An offline agent gives HTTP 409 `agent_offline`. An agent that is too old gives HTTP 409 `agent_capability_missing`. A target outside the roots of the agent gives HTTP 409 `restore_target_denied`. A repository of another organization gives HTTP 404.

`GET /api/v1/agents` lists the `restore_roots` of each agent.
